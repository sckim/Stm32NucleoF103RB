Arduino 계층의 Blink: pinMode · digitalWrite · delay 뒤의 레지스터

Arduino API는 칩을 몰라도 LED를 깜빡이게 해 주지만, 그 대가로 어떤 레지스터가 언제 바뀌는지가 보이지 않는다. 이 예제설명은 STM32duino 코어가 pinMode를 RCC_APB2ENR·GPIOA_CRL 설정으로, digitalWrite를 BSRR/BRR 쓰기로 바꾸는 과정을 빌드 산출물로 확인하고, 같은 Blink를 HAL·LL·레지스터로 구현한 세 예제와 비교한다. 대상 폴더는 01_BlinkArduino이다.

1. 문제: 세 줄짜리 Blink 뒤에서 무슨 일이 일어나는가

Arduino 코드는 pinMode, digitalWrite, delay 세 함수만으로 LED를 점멸한다. 같은 코드가 AVR(Uno)에서도 STM32에서도 동작하는 것은 프레임워크가 칩마다 다른 레지스터 조작을 감추기 때문이다. 이 예제설명은 그 감춰진 부분이 STM32F103에서 정확히 어떤 레지스터 쓰기인지 확인하고, 시리즈의 나머지 세 예제(HAL, LL, 레지스터)와 비교할 기준점을 만든다. 학습 목표는 다음과 같다.

  • setup() 1회 + loop() 무한 반복 구조가 코어의 main() 안에서 호출되는 함수임을 설명한다.
  • LED_BUILTIN → D13 → PA5로 이어지는 핀 번호 변환을 따라간다.
  • digitalWrite(HIGH)가 GPIOA_BSRR, digitalWrite(LOW)가 GPIOA_BRR 쓰기가 됨을 확인한다.
  • 네 계층의 코드량·이식성·하드웨어 가시성·빌드 프레임워크(platformio.ini의 framework) 차이를 표로 비교한다.
이 예제의 동작

setup()에서 PA5를 출력으로 설정한 뒤, loop()가 HIGH → 500 ms 대기 → LOW → 500 ms 대기를 반복한다. LD2는 1초 주기(1 Hz, 듀티 50 %)로 점멸한다.

2. 핵심 개념: 같은 Blink, 네 가지 계층

시리즈의 네 예제는 모두 LD2(PA5)를 점멸한다. 차이는 사용자가 어느 높이에서 하드웨어를 부르는가이다. Arduino 계층은 핀을 보드의 번호(D13)로 부르고, 클럭·포트 설정·타이머를 전부 프레임워크가 맡는다.

그림 1. 네 예제는 같은 하드웨어(PA5의 출력 레지스터)에 도달하지만 출발하는 계층이 다르다. 굵은 주황 경로가 이 예제설명의 예제이며, 위 계층일수록 그 아래 계층을 모두 거친다.

4. 직접 만져 보기: loop()와 1 ms 틱

아래 시뮬레이터는 loop()의 네 줄을 1 ms SysTick 틱 단위로 실행한다. delay()는 시작 시각을 기억한 뒤 경과 틱이 목표 이상이 될 때까지 기다린다.

  1. 초기 상태에서 SysTick 1 ms를 누르며 uwTick과 경과 시간이 늘어나는 것을 본다.
  2. SysTick 100 ms를 다섯 번 누르면 delay(500)이 끝나고 digitalWrite(LOW)가 BRR에 쓰는 순간을 볼 수 있다.
  3. HIGH/LOW 시간을 바꾸어 주기·주파수·듀티가 어떻게 바뀌는지 확인한다 (예: 100 / 900 → 1 Hz, 듀티 10 %).
  4. loop() 한 바퀴는 남은 대기를 한 번에 진행하여 다음 digitalWrite(HIGH)까지 간다.

시뮬레이터 모델: 1 ms마다 SysTick ISR이 uwTick을 1 증가시키고, delay(ms)는 (uwTick − start) < ms인 동안 기다린다. digitalWrite의 실행 시간(수 µs)은 무시한다. 실제 delay()는 시작 시점이 틱 사이 어디인지에 따라 ms−1 ~ ms 사이로 끝난다.

코어는 출력 속도를 HIGH(MODE = 11)로 먼저 쓰지만, 이어지는 LL_GPIO_SetPinMode가 CNF와 MODE 4비트를 함께 덮어써서 최종값은 MODE5 = 01(10 MHz)이다. 결과적으로 04_BlinkReg가 직접 쓰는 값(0x1 << 20)과 같다. HAL/LL 예제는 Low 속도(MODE5 = 10, 2 MHz)를 쓴다. LED 점멸에는 차이가 없다.

7. 코드 읽기

외부 부품은 필요 없다. 보드의 LD2만 사용하며 시리얼 출력은 없다.

src/main.c — 핀 선택과 setup()
#include <Arduino.h>
// Nucleo-F103RB 보드의 온보드 녹색 LED는 PA5 핀에 연결되어 있음
// 아두이노 핀 맵 기준으로는 D13 핀에 해당함
const int ledPin = LED_BUILTIN; // 또는 13 또는 PA5 로 직접 지정 가능

void setup() {
    // 1. PA5 핀(D13)을 출력(OUTPUT) 모드로 설정
    // 내부적으로 GPIOA 클록 활성화 및 CRL/CRH 레지스터 제어가 자동으로 수행됨
    pinMode(ledPin, OUTPUT);
}
  1. LED_BUILTIN은 변형 헤더가 정의한 핀 번호이며 이 보드에서는 PA5(D13)를 가리킨다.
  2. pinMode 한 줄이 포트 클럭 허용과 CRL 설정을 모두 수행한다.
  3. 주석의 "CRL/CRH"는 핀 번호에 따라 둘 중 하나를 쓴다는 뜻이다. PA5는 0~7번이므로 CRL이다.
src/main.c — loop()
void loop() {
    // 2. 핀 출력을 HIGH(3.3V)로 인가하여 LED 켜기
    digitalWrite(ledPin, HIGH);

    // 3. SysTick 타이머 기반의 정밀 500ms 딜레이 가동
    delay(500);

    // 4. 핀 출력을 LOW(0V)로 인가하여 LED 끄기
    digitalWrite(ledPin, LOW);

    delay(500);
}
  1. HIGH는 BSRR의 BS5, LOW는 BRR의 BR5에 1을 쓴다. 둘 다 ODR을 읽지 않는 원자적 쓰기이다.
  2. delay(500)은 블로킹 대기이다. 대기 중 CPU는 다른 일을 하지 않는다.
  3. loop()가 끝나면 코어가 다시 호출하므로 한 바퀴 = 1000 ms이다.

업로드 후 LD2가 0.5초 켜지고 0.5초 꺼진다. 로직 분석기(AD2 등)로 D13(CN5 6번 핀)을 측정하면 1.000 Hz 부근, 듀티 50 %의 구형파가 보인다. 빌드 로그의 Flash 사용량은 약 13 KB로, 같은 동작의 레지스터 예제(약 0.7 KB)보다 크다.

8. 실험

실험 A. 듀티 바꾸기

delay(100) / delay(900)으로 바꾸어 주기는 1 s로 유지하고 켜짐 시간만 줄인다. 시뮬레이터의 듀티 계산과 비교한다.

실험 B. 핀 이름으로 지정

LED_BUILTIN 대신 PA5, 13(D13)을 각각 넣어 빌드하고 동작이 같은지 확인한다. 디버거에서 세 경우 모두 같은 PinName(PA_5)으로 변환되는지 본다.

실험 C. 계층별 Flash 비교

01~04 네 예제를 모두 빌드하고 빌드 로그의 Flash/RAM 사용량을 표로 정리한다. 추상화가 높을수록 커지는 이유(핀 변환 표, HAL 드라이버, 코어 초기화)를 설명한다.

실험 D. 최대 토글 속도

loop()에서 delay를 지우고 digitalWrite만 반복하여 PA5의 토글 주파수를 측정한다. 04_BlinkReg에서 BSRR만 반복했을 때와 비교하면 핀 번호 변환 비용을 알 수 있다.

10. 확인 문제

문제 1. digitalWrite(LED_BUILTIN, LOW)는 어느 레지스터에 어떤 값을 쓰는가?

GPIOA_BRR(0x4001 0814)에 0x0000 0020을 쓴다. BR5 = 1이므로 ODR5만 0이 되고 다른 비트는 변하지 않는다. 같은 효과를 GPIOA_BSRR의 상위 반(0x0020 0000)으로도 낼 수 있다.

문제 2. delay(100), delay(400)으로 바꾸면 주기와 듀티는?

주기 500 ms(2 Hz), 듀티 100/500 = 20 %이다.

문제 3. 같은 소스를 Arduino Uno에서 빌드하면 pinMode가 쓰는 레지스터는 어떻게 달라지는가?

AVR에는 RCC와 CRL이 없다. DDRB의 비트 5(D13 = PB5)를 1로 하고, digitalWrite는 PORTB를 바꾼다. API가 같아도 하드웨어 접근은 프레임워크가 칩별로 다르게 구현한다. 이것이 이식성의 근거이다.

문제 4. 이 예제 폴더에 SystemClock_Config가 없는데 64 MHz로 동작하는 이유는?

STM32duino 코어가 사용자 setup() 전에 보드 변형 파일의 SystemClock_Config()(HSI/2 × 16)를 호출하기 때문이다. 사용자 코드에서 보이지 않는다는 것이 Arduino 계층의 낮은 하드웨어 가시성이다.
