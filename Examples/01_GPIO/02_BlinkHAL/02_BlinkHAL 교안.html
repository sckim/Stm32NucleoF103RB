HAL 계층의 Blink: TogglePin 한 줄과 HAL_Delay의 1 ms 틱

CubeMX가 만든 뼈대 위에 두 줄만 쓰면 LED가 깜빡인다. 그러나 그 두 줄이 어떤 레지스터를 몇 번 읽고 쓰는지, 1000 ms 지연이 실제로 몇 틱인지는 생성 코드와 HAL 라이브러리 안에 숨어 있다. 이 교안은 HAL_GPIO_TogglePin의 ODR→BSRR 원자적 토글과 SysTick 기반 HAL_Delay를 레지스터 수준에서 해석하고, Arduino·LL·레지스터 Blink와 비교한다. 대상 폴더는 02_BlinkHAL이다.

1. 문제: 생성 코드 위에 두 줄을 얹는 구조

HAL 예제의 사용자 코드는 while 루프 안의 두 줄뿐이다. 나머지(클럭 트리, 포트 클럭, 핀 모드, SysTick)는 CubeMX가 Blink.ioc 설정으로 생성한다. 이 구조는 편리하지만 "토글 한 줄"이 어떤 레지스터 연산인지, HAL_Delay(1000)이 왜 정확히 1000 ms가 아닌지가 소스에 드러나지 않는다. 학습 목표는 다음과 같다.

  • HAL_Init() → SystemClock_Config() → MX_GPIO_Init() 초기화 순서와 각 단계가 바꾸는 레지스터를 설명한다.
  • HAL_GPIO_TogglePin이 ODR을 읽어 BSRR에 한 번 쓰는 원자적 토글임을 확인한다.
  • HAL_Delay(N)이 SysTick ISR이 증가시키는 uwTick을 비교하며 N+1틱을 기다리는 이유를 이해한다.
  • USER CODE BEGIN/END 영역 규칙과 framework = stm32cube 빌드 구조를 Arduino·LL·레지스터 계층과 비교한다.
이 예제의 동작

LD2(PA5)를 약 1초(1001 ms)마다 토글한다. 켜짐 1 s + 꺼짐 1 s이므로 점멸 주기는 약 2 s(0.5 Hz)이다. 01_BlinkArduino(1 s 주기)의 두 배이다.

2. 핵심 개념: HAL 계층의 위치

HAL은 주변장치를 핸들·구조체·상태 반환값(HAL_OK)으로 다룬다. GPIO 토글 자체는 레지스터 두 번 접근(ODR 읽기, BSRR 쓰기)으로 끝나지만, 초기화 함수는 구조체 필드를 해석해 CRL/CRH/ODR/EXTI를 설정한다.

그림 1. 네 예제는 같은 하드웨어(PA5의 출력 레지스터)에 도달하지만 출발하는 계층이 다르다. 굵은 주황 경로가 이 교안의 예제이며, 위 계층일수록 그 아래 계층을 모두 거친다.

HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5): odr = GPIOA->ODR BSRR = ((odr & 0x20) << 16) | (~odr & 0x20) ODR5 = 0 → BSRR = 0x0000 0020 (BS5, 켜기) ODR5 = 1 → BSRR = 0x0020 0000 (BR5, 끄기)

위 식은 빌드 산출물(.pio/build/Lecture/firmware.elf)의 HAL_GPIO_TogglePin 역어셈블 결과와 같다 (ldr [r0,#12] = ODR 읽기, str [r0,#16] = BSRR 쓰기). ODR에 직접 XOR을 쓰지 않으므로, 토글 도중 인터럽트가 같은 포트의 다른 핀을 바꾸어도 그 변경을 덮어쓰지 않는다.

4. 직접 만져 보기: HAL_Delay 틱과 토글

아래 시뮬레이터는 while 루프의 두 줄을 1 ms SysTick 틱 단위로 실행한다. 토글할 때마다 ODR을 읽어 BSRR 값을 계산하는 과정을 보여 준다.

  1. SysTick 1 ms를 몇 번 눌러 uwTick이 증가하는 것을 본다. 대기 목표가 N이 아니라 N+1인 것을 확인한다.
  2. 다음 토글까지를 누르면 HAL_Delay가 끝나는 틱까지 진행한 뒤 HAL_GPIO_TogglePin이 실행된다. BSRR 값이 0x0000 0020과 0x0020 0000을 번갈아 갖는지 본다.
  3. N을 1로 바꾸면 실제 대기는 2 ms가 된다. 짧은 지연일수록 +1틱 오차의 비율이 커진다.

시뮬레이터 모델: HAL_Delay(N)은 tickstart = HAL_GetTick()을 저장하고 N에 uwTickFreq(= 1)를 더한 뒤 (HAL_GetTick() − tickstart) < N+1인 동안 기다린다(빌드 산출물로 확인). 실제로는 시작 시점이 틱 사이 어디인지에 따라 N ~ N+1 ms가 된다. 초기 ODR5 = 0은 HAL_GPIO_WritePin(..., GPIO_PIN_RESET)에 따른 것이다.

6. 실행 경로와 SysTick 인터럽트 경로

  1. 1
    Reset_Handler → SystemInit() → main()소프트웨어startup_stm32f103rbtx.s. 리셋 직후는 HSI 8 MHz로 동작한다.
  2. 2
    HAL_Init()소프트웨어Flash 프리페치, NVIC 그룹, SysTick을 현재 클럭(8 MHz) 기준 1 ms로 설정하고 HAL_MspInit()을 호출한다.
  3. 3
    SystemClock_Config()소프트웨어PLL 64 MHz로 전환. HAL_RCC_ClockConfig가 SystemCoreClock을 갱신하고 SysTick을 다시 설정한다.
  4. 4
    MX_GPIO_Init()소프트웨어포트 클럭 허용 → PA5 Low → 핀별 HAL_GPIO_Init.
  5. 5
    while: TogglePin → HAL_Delay(1000)소프트웨어USER CODE 3 영역의 두 줄이 무한 반복된다.
  6. 6
    SysTick 카운터 0 도달 (1 ms마다)하드웨어STK_CTRL.TICKINT = 1이므로 SysTick 예외(번호 15)가 발생한다.

    SysTick_Handler → HAL_IncTick()소프트웨어stm32f1xx_it.c의 진짜 ISR. uwTick += uwTickFreq.

7. 코드 읽기

외부 부품은 필요 없다. 보드의 LD2만 사용하며 시리얼 출력은 없다.

  /* Configure the system clock */

8. 실험

실험 A. +1틱 측정

HAL_Delay(1)로 바꾸고 PA5 토글 간격을 로직 분석기로 측정한다. 1 ms가 아니라 약 2 ms에 가까운 이유를 시뮬레이터의 N+1 목표와 연결해 설명한다.

실험 B. 출력 속도 바꾸기

Blink.ioc에서 PA5의 Maximum output speed를 High로 바꾸어 재생성하고 GPIOA_CRL[23:20]이 0011로 바뀌는지 디버거로 확인한다. USER CODE 영역의 두 줄이 보존되는지도 본다.

실험 C. 클럭 확인

HAL_RCC_GetSysClockFreq(), HAL_RCC_GetPCLK1Freq()의 반환값을 디버거로 읽어 64 MHz, 32 MHz인지 확인한다.

실험 D. 계층 비교

10. 확인 문제

문제 1. ODR = 0x0000 0020일 때 HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5)가 BSRR에 쓰는 값은?

((0x20 & 0x20) << 16) | (~0x20 & 0x20) = 0x0020 0000 | 0 = 0x0020 0000이다. BR5 = 1이므로 PA5가 Low가 된다.

문제 2. HAL_Delay(1000)을 두 번 거친 한 주기(켜짐+꺼짐)는 대략 몇 ms인가?

각 대기가 1000~1001 ms이므로 약 2001~2002 ms이다. 토글·함수 호출 시간은 µs 이하로 무시할 수 있다.

문제 3. HAL_Init()이 SysTick을 설정했는데 SystemClock_Config() 뒤에 다시 설정하는 이유는?

HAL_Init() 시점의 HCLK는 HSI 8 MHz라 LOAD = 7 999였다. PLL 64 MHz로 바꾸면 같은 LOAD로는 틱이 125 µs가 되므로 HAL_RCC_ClockConfig가 HAL_InitTick()을 다시 호출해 LOAD = 63 999로 맞춘다.

문제 4. B1(PC13)이 EXTI로 설정되었는데 버튼을 눌러도 아무 일이 없는 이유는?

EXTI 라인(IMR, RTSR)과 AFIO_EXTICR4는 설정되었지만 NVIC에서 EXTI15_10_IRQn을 허용하지 않았고 콜백도 없다. 요청은 EXTI_PR에 대기 상태로만 남는다.
