UART 수신 인터럽트: RXNE에서 콜백, 그리고 재무장까지

PC에서 보낸 글자는 언제 도착할지 모른다. 폴링으로 기다리면 CPU가 묶이고, 다른 일을 하다 보면 글자를 놓친다. 이 교안은 USART2가 1바이트를 받으면 RXNE 인터럽트로 CPU를 부르고, 진짜 ISR인 USART2_IRQHandler에서 HAL을 거쳐 사용자 콜백까지 이어지는 경로를 레지스터 수준으로 추적한다. 콜백은 플래그만 세우고 main 루프가 LED 제어와 에코를 처리한다. 대상 예제는 02_USART_Interrupt이다.

1. 문제: 언제 올지 모르는 1바이트

HAL_UART_Receive(&huart2, &c, 1, timeout)처럼 폴링으로 받으면 바이트가 올 때까지 CPU가 SR.RXNE만 확인한다. 115200 bps에서 바이트는 86.8 µs마다 올 수 있으므로, 다른 일을 하느라 한 프레임 시간 안에 DR을 읽지 못하면 다음 바이트가 들어올 때 오버런(ORE)으로 데이터가 사라진다. 인터럽트 수신은 바이트가 도착한 순간 하드웨어가 CPU를 불러 DR을 읽게 한다. 학습 목표는 다음과 같다.

  • HAL_UART_Receive_IT()가 켜는 비트(CR1.RXNEIE, CR3.EIE)와 그 결과 생기는 인터럽트 요청을 설명한다.
  • 진짜 ISR(USART2_IRQHandler), HAL 디스패처(HAL_UART_IRQHandler), 사용자 콜백(HAL_UART_RxCpltCallback)을 구분한다.
  • 1바이트 수신이 끝나면 HAL이 RXNEIE를 끄기 때문에 콜백에서 재무장(re-arm)해야 함을 설명한다.
  • 오버런(ORE) 발생 조건과, ISR → main 사이 단일 변수 전달의 한계를 이해한다.
이 예제의 동작

시작 시 안내 문구를 보내고 1바이트 수신 인터럽트를 시작한다. PC 터미널에서 '1'을 보내면 LD2(PA5) 켜짐, '0'은 꺼짐, 't'는 토글이며, 받은 문자는 무엇이든 그대로 되돌려 보낸다(에코). 콜백은 rx_data와 rx_ready만 기록하고 즉시 재무장하며, LED 제어와 에코 송신은 main 루프에서 한다.

2. 핵심 개념: RXNE, RXNEIE, 그리고 재무장

비트위치누가 바꾸는가의미
RXNEUSART_SR 비트 5하드웨어가 1로, DR 읽기로 0시프트 레지스터의 수신 바이트가 DR로 옮겨졌다(읽을 데이터 있음)
OREUSART_SR 비트 3하드웨어가 1로, SR 읽은 뒤 DR 읽기로 0RXNE = 1인 상태에서 다음 바이트 수신이 끝났다. 새 바이트는 버려지고 DR에는 이전 값이 남는다
RXNEIEUSART_CR1 비트 5소프트웨어(HAL)1이면 RXNE = 1 또는 ORE = 1일 때 인터럽트 요청
EIEUSART_CR3 비트 0소프트웨어(HAL)1이면 FE·NE·ORE(멀티버퍼 통신 시) 오류도 인터럽트 요청

HAL의 수신 API는 "정해진 개수를 받으면 끝나는 작업" 단위로 동작한다. HAL_UART_Receive_IT(&huart2, &rx_byte, 1)은 "1바이트를 받아 rx_byte에 넣어라"라는 작업 하나를 시작한다. 1바이트가 들어오면 HAL은 RxXferCount를 0으로 만들고 RXNEIE와 EIE를 끈 뒤 완료 콜백을 부른다. 따라서 콜백 안에서 같은 함수를 다시 불러 작업을 새로 시작하지 않으면 두 번째 바이트부터는 인터럽트가 일어나지 않는다.

그림 1. 위 세 줄은 이 예제의 정상 동작이다. RXNE가 서면 ISR이 DR을 읽어 RXNE를 지우고, HAL이 RXNEIE를 끈 직후 콜백이 다시 켠다(짧은 0 구간). 맨 아래 RXNE*는 콜백에서 재무장을 뺀 경우이다. 두 번째 바이트의 RXNE가 1로 남고, 세 번째 바이트가 오면 ORE가 된다.

오버런(ORE)이 생기는 조건

상황DR을 읽는 주체결과
정상: 인터럽트가 제때 처리됨ISR이 RXNE 직후 읽음바이트 간격(86.8 µs) 안에 처리되면 손실 없음
인터럽트가 오래 막힘 (__disable_irq(), 더 높은 우선순위 ISR이 길게 실행)늦게 읽음다음 바이트 수신 완료 시 RXNE = 1이면 ORE = 1, 새 바이트 손실
재무장 누락아무도 읽지 않음RXNEIE = 0, EIE = 0이라 ORE도 인터럽트를 만들지 못한다. 수신이 멈춘 것처럼 보인다
ORE가 발생했고 재무장 상태ISRHAL이 오류로 보고 수신 작업을 중단한 뒤 HAL_UART_ErrorCallback 호출. 이 예제는 여기서 다시 시작한다

우선순위 해석

HAL 기본 우선순위 그룹(4비트 모두 선점)에서 숫자가 작을수록 높다. SysTick(0)이 USART2(1)보다 높으므로 USART2 ISR 실행 중에도 1 ms 틱은 끼어들어 HAL_GetTick()이 계속 증가한다. NVIC 레지스터로는 NVIC_IPR9의 IRQ38 바이트 = 0x10, NVIC_ISER1 비트 6 = 1이다.

이 예제의 GPIO 초기화에는 01 예제에 있던 B1(PC13) EXTI 설정이 없다. 동작 중인 인터럽트는 USART2와 SysTick 두 개뿐이다.

4. 직접 만져 보기

아래 시뮬레이터는 바이트 도착부터 콜백, main 처리까지를 한 단계씩 진행한다. 하드웨어가 하는 일(보라)과 소프트웨어가 하는 일(파랑)을 구분해 보고, 재무장을 빼면 무엇이 멈추는지 확인한다.

  1. 문자 '1'을 고르고 바이트 도착을 누른다. RXNE = 1이 되고 다음 단계 카드가 표시된다.
  2. ISR 다음 단계를 눌러 NVIC → USART2_IRQHandler → HAL_UART_IRQHandler → 콜백 순서로 진행한다. HAL 단계에서 RXNEIE가 0으로, 콜백에서 다시 1로 바뀌는 것을 본다.
  3. main 루프 1회를 누르면 LD2가 켜지고 에코가 나간다.
  4. 콜백의 재무장 줄 빼기를 체크하고 초기화한 뒤 바이트 두 개를 보낸다. 두 번째 바이트에서 인터럽트가 일어나지 않고, 세 번째에서 ORE가 생기는 것을 확인한다.
  5. 재무장을 다시 켜고, ISR 단계를 진행하지 않은 채 바이트 도착을 두 번 눌러 ORE → HAL_UART_ErrorCallback 경로를 본다. 또 ISR을 끝까지 진행하되 main을 돌리지 않고 두 바이트를 받으면 rx_data가 덮어쓰이는 것을 본다.

6. 인터럽트 경로: 진짜 ISR과 콜백

  1. 1
    프레임 수신 완료 → SR.RXNE = 1하드웨어정지 비트까지 받으면 시프트 레지스터 값이 DR로 옮겨진다. 이미 RXNE = 1이었다면 대신 ORE = 1이 된다.
  2. 2
    RXNEIE = 1 → NVIC USART2_IRQn하드웨어우선순위 판정 후 CPU가 레지스터를 스택에 저장하고 벡터 0x0000 00D8의 주소로 분기한다.
  3. 3
    USART2_IRQHandler() — stm32f1xx_it.c소프트웨어벡터 테이블이 직접 호출하는 진짜 ISR이다. 내용은 HAL_UART_IRQHandler(&huart2) 한 줄이다.
  4. 4
    HAL_UART_IRQHandler() → UART_Receive_IT()소프트웨어SR을 읽고 오류 비트가 없음을 확인한 뒤 DR을 rx_byte에 저장한다(RXNE 해제). 요청한 1바이트를 채웠으므로 RXNEIE·EIE를 끄고 RxState를 READY로 둔다.
  5. 5
    HAL_UART_RxCpltCallback() — main.c소프트웨어ISR 문맥에서 실행되는 사용자 함수. rx_data = rx_byte, rx_ready = 1을 기록하고 HAL_UART_Receive_IT()로 재무장한다.
  6. 6
    main 루프소프트웨어rx_ready를 확인하면 값을 복사하고 플래그를 지운 뒤 LED를 바꾸고 에코를 블로킹 송신한다. 송신 중에도 수신 인터럽트는 계속 동작한다.

7. 코드 읽기

외부 배선은 필요 없다. 시리얼 터미널을 ST-LINK COM 포트, 115200 8N1로 열고 키를 하나씩 누른다. 터미널의 로컬 에코는 꺼 두어야 MCU가 돌려준 글자만 보인다.

main.c — ISR과 main이 공유하는 변수 (USER CODE PV)
static uint8_t rx_byte;               /* HAL_UART_Receive_IT 가 채워 주는 1바이트 버퍼 */
static volatile uint8_t rx_data;      /* 콜백 -> main 으로 전달하는 데이터 */
static volatile uint8_t rx_ready;     /* 콜백 -> main 으로 전달하는 플래그 */
  1. rx_byte는 HAL이 DR 값을 써 넣는 곳이고, main은 직접 읽지 않는다.
  2. rx_data·rx_ready는 콜백이 쓰고 main이 읽으므로 volatile이 필요하다. 없으면 컴파일러가 main 루프 안의 rx_ready 읽기를 레지스터 값으로 대체할 수 있다.
main.c — 시작과 main 루프 (USER CODE 2, 3)
const char *banner = "\r\n[USART2 RX interrupt] 1/0/t 를 입력하세요\r\n";
HAL_UART_Transmit(&huart2, (uint8_t *)banner, (uint16_t)strlen(banner), 100);

/* 수신 인터럽트 시작: USART2->CR1.RXNEIE=1, CR3.EIE=1 (HAL 내부에서 설정) */
HAL_UART_Receive_IT(&huart2, &rx_byte, 1);

while (1)
{
  if (rx_ready)
  {
    uint8_t c = rx_data;
    rx_ready = 0;

    switch (c)
    {
    case '1': HAL_GPIO_WritePin(LD2_GPIO_Port, LD2_Pin, GPIO_PIN_SET);   break;
    case '0': HAL_GPIO_WritePin(LD2_GPIO_Port, LD2_Pin, GPIO_PIN_RESET); break;
    case 't': HAL_GPIO_TogglePin(LD2_GPIO_Port, LD2_Pin);                break;
    default: break;
    }
    HAL_UART_Transmit(&huart2, &c, 1, 100);   /* 에코 (main 문맥에서 블로킹 송신) */
  }
}
  1. 배너 문자열에는 한글이 있어 UTF-8 바이트로 나간다. 터미널 인코딩이 UTF-8이어야 제대로 보인다.
  2. main은 값을 지역 변수 c로 복사한 다음 플래그를 지운다. 이후 콜백이 새 값을 써도 c는 바뀌지 않는다.
  3. 명령 문자는 '1', '0', 't' 세 개이며 대소문자를 구분한다('T'는 에코만 된다).
  4. 에코는 main 문맥의 블로킹 송신이다. ISR 안에서 송신하지 않는다.
main.c — 콜백 (USER CODE 4, ISR 문맥)
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
  if (huart->Instance == USART2)
  {
    rx_data = rx_byte;
    rx_ready = 1;  //flag set: main 루프에서 처리하도록 알림
    HAL_UART_Receive_IT(&huart2, &rx_byte, 1);   /* 다음 바이트를 위해 재무장(필수) */
  }
}

/* 오버런/프레이밍 오류(SR.ORE/FE)가 나면 HAL 이 수신을 중단하므로 여기서 다시 시작한다 */
void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart)
{
  if (huart->Instance == USART2)
  {
    HAL_UART_Receive_IT(&huart2, &rx_byte, 1);
  }
}
  1. 모든 UART 인스턴스가 같은 콜백을 공유하므로 Instance를 검사한다.
  2. 재무장은 RXNEIE·EIE를 다시 켠다. 콜백 진입 시 HAL이 이미 RxState를 READY로 바꿔 두었으므로 이 호출은 BUSY 오류 없이 성공한다.
  3. ErrorCallback이 없으면 ORE 한 번에 수신이 영구히 멈춘다.

8. 실험

실험 A. 재무장 빼기

콜백의 HAL_UART_Receive_IT(&huart2, &rx_byte, 1); 줄을 주석 처리한다. 첫 글자는 동작하고 이후 글자는 반응이 없음을 확인한다. 디버거로 USART2->CR1(0x200C, RXNEIE = 0)과 USART2->SR(RXNE, ORE)을 읽어 시뮬레이터 결과와 비교한다.

실험 B. 인터럽트를 막아 ORE 만들기

main 루프의 처리 부분에 __disable_irq(); for (volatile int i = 0; i < 200000; i++); __enable_irq();를 넣고 여러 글자를 빠르게 입력한다. HAL_UART_ErrorCallback에 카운터를 두어 오버런 횟수를 세고, 처리 지연 시간과 바이트 간격 86.8 µs를 비교한다.

실험 C. 붙여넣기와 단일 변수의 한계

터미널에 1010101010t 같은 긴 문자열을 한 번에 붙여 넣는다. 에코된 글자 수가 보낸 글자 수와 같은지 센다. 에코 송신(86.8 µs)과 다음 바이트 도착 간격이 비슷하므로, main이 늦으면 rx_data가 덮어쓰여 글자가 빠질 수 있다. 이 문제를 03 예제의 링 버퍼가 해결한다.

실험 D. ISR에서 에코하기

에코 송신을 콜백 안으로 옮겨 본다. 동작은 비슷해 보이지만 ISR 안에서 86.8 µs 동안 블로킹하는 구조가 된다. 실험 C와 같은 붙여넣기에서 결과가 어떻게 달라지는지, 그리고 왜 권장되지 않는지 설명한다.

10. 확인 문제

문제 1. HAL_UART_RxCpltCallback이 ISR이 아니라고 하는 이유는?

벡터 테이블에 등록되어 하드웨어가 직접 호출하는 함수는 USART2_IRQHandler뿐이다. 콜백은 그 안에서 HAL_UART_IRQHandler가 원인을 판별한 뒤 일반 함수 호출로 부르는 함수이다. 다만 ISR 문맥에서 실행되므로 ISR과 같은 제약(짧게, 블로킹 금지)을 따라야 한다.

문제 2. 콜백에서 재무장을 빼면 두 번째 바이트와 세 번째 바이트에서 각각 어떤 레지스터 변화가 생기는가?

두 번째 바이트: RXNE = 1이 되지만 RXNEIE = 0이므로 인터럽트가 없고 DR에 그대로 남는다. 세 번째 바이트: RXNE = 1인 상태에서 수신이 끝나 ORE = 1이 되고 세 번째 바이트는 버려진다. EIE도 0이므로 ORE 역시 인터럽트를 만들지 못한다.

문제 3. 115200 bps 8N1에서 ISR이 DR을 읽기까지 허용되는 최대 지연은 대략 얼마인가?

RXNE가 선 뒤 다음 바이트 수신이 끝나기 전까지, 즉 연속 수신 시 한 프레임 시간인 약 86.8 µs이다. 64 MHz에서 약 5 500 사이클에 해당한다.

문제 4. main 루프에서 uint8_t c = rx_data; 다음에 rx_ready = 0;을 두는 순서가 반대라면 어떤 문제가 생길 수 있는가?

플래그를 먼저 지운 뒤 값을 읽기 전에 인터럽트가 들어와 새 바이트를 쓰고 rx_ready = 1을 세우면, main은 새 값을 읽고도 플래그가 다시 서 있어 같은 값을 한 번 더 처리할 수 있다. 값 복사 후 플래그 해제 순서가 경쟁을 줄인다. 그래도 그 사이에 두 바이트가 오면 하나는 사라지므로 근본 해결은 버퍼이다.
