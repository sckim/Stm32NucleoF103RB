UART 수신 링 버퍼

인터럽트로 들어오는 바이트를 잃지 않고 main 루프로 넘기는 가장 기본적인 자료구조를 다룬다. 예제 04_USART_RingBuffer_c의 코드를 그대로 따라가며 개념, 동작 원리, 실험, 흔한 실수를 순서대로 정리한다.

1. 왜 링 버퍼가 필요한가

PC에서 보낸 글자는 언제 도착할지 모른다. 반면 main 루프는 LCD를 갱신하거나 ADC를 읽는 등 다른 일을 하고 있을 수 있다. 수신 인터럽트가 글자를 받았을 때 main이 바쁘다면 그 글자를 둘 곳이 필요하다.

이전 예제 02_USART_Interrupt_RX는 수신 바이트를 변수 하나에 담았다. main이 그 값을 읽기 전에 다음 글자가 도착하면 앞 글자는 덮어써져 사라진다. 변수 한 칸을 여러 칸의 대기열로 늘린 것이 링 버퍼이다.

생산자 (Producer) = 인터럽트 서비스 루틴수신한 바이트를 버퍼에 넣는다(push). 도착 시각을 정할 수 없고, 짧게 끝내야 한다.
소비자 (Consumer) = main 루프버퍼에서 바이트를 꺼내 처리한다(pop). 자기 속도에 맞춰 꺼낸다.

식당에 비유하면 홀 직원(ISR)이 주문서를 꽂는 주문서 걸이가 링 버퍼이고, 주방(main)은 한가할 때 걸이에서 순서대로 주문서를 뽑아 간다. 먼저 꽂은 주문서를 먼저 뽑으므로 FIFO(First In, First Out)이다.

2. 핵심 아이디어: 배열 하나와 두 개의 인덱스

링 버퍼는 고정 크기 배열 buf[N] 하나와 두 개의 위치 값으로 이루어진다.

이름의미누가 바꾸는가
head다음에 쓸 칸의 번호생산자(ISR)만
tail다음에 읽을 칸의 번호소비자(main)만
  • push는 buf[head]에 쓰고 head를 한 칸 앞으로 옮긴다.
  • pop은 buf[tail]을 읽고 tail을 한 칸 앞으로 옮긴다.
  • 두 인덱스가 배열 끝에 닿으면 0번 칸으로 되돌아간다. 배열의 끝과 처음이 이어진 고리처럼 쓰므로 링(ring) 또는 원형 버퍼(circular buffer)라고 부른다.
  • 데이터를 실제로 옮기지 않고 인덱스만 움직이므로 push와 pop이 모두 몇 줄짜리 상수 시간 연산이다.
상태 판정

비어 있음(empty): head == tail

가득 참(full): ((head + 1) & mask) == tail

저장된 개수: (head − tail) & mask

full 판정에서 head 바로 다음 칸이 tail이면 가득 찬 것으로 본다. 이때 한 칸은 항상 비워 둔다. 이유는 4절에서 설명한다. 그래서 크기 N인 버퍼에는 최대 N−1개가 들어간다.

3. 직접 만져 보기

아래 시뮬레이터는 예제와 같은 규칙(next = (head+1) & mask)으로 동작한다. 보기 쉽도록 기본 크기를 8칸으로 줄였다(예제 코드는 128칸).

  1. push를 여러 번 눌러 head가 도는 모습을 본다. 칸이 가득 차면 다음 push는 버려진다.
  2. pop으로 tail을 움직여 본다. 비어 있으면 아무것도 꺼내지 못한다.
  3. 배열 끝(7번)에서 head나 tail이 0번으로 돌아가는 순간의 계산식을 확인한다.
  4. 자동 재생에서 main 멈춤을 켜 보고 dropped가 늘어나는 것을 확인한다. 7절 실험의 축소판이다.

push 또는 pop을 눌러 계산 과정을 확인한다.

관찰 포인트는 다음과 같다.

  • push 속도 > pop 속도이면 버퍼가 서서히 차오르고 결국 dropped가 생긴다. 평균 처리 속도가 평균 입력 속도보다 느리면 어떤 크기의 버퍼도 언젠가 넘친다.
  • push 속도 < pop 속도이면 버퍼는 대부분 비어 있다. 버퍼의 역할은 평균이 아니라 순간적인 몰림(burst)을 흡수하는 것이다.
  • 가득 찼을 때 head 칸이 비어 있는 것을 확인한다. 이 한 칸이 4절의 ‘한 칸 비우기’이다.

4. 이 구현을 지탱하는 네 가지 규칙

규칙 1. 한 칸을 비워 두어 full과 empty를 구분한다

모든 칸에 데이터를 채우면 head가 한 바퀴 돌아 tail과 같아진다. 그런데 head == tail은 empty의 조건이기도 하다. 같은 값이 ‘텅 빔’과 ‘가득 참’을 동시에 뜻하게 되어 구분할 수 없다. 한 칸을 포기하면 두 상태가 항상 다른 값으로 나타난다.

상태head와 tail의 관계N = 8일 때 예
비어 있음head == tailhead = 3, tail = 3
가득 참 (7개 저장)((head+1) & 7) == tailhead = 2, tail = 3 (2번 칸이 빈 칸)

규칙 2. 크기를 2의 거듭제곱으로 잡고 마스크로 되감는다

인덱스가 끝에서 0으로 돌아가는 처리는 보통 (i + 1) % N으로 쓴다. N이 2의 거듭제곱이면 나머지 연산 대신 AND 한 번으로 같은 결과를 얻는다. mask = N − 1은 이진수로 하위 비트가 모두 1이다.

Nmask (이진)head = 7계산결과
801117 → 8 = 10001000 & 01110000 = 0 (되감김)
801115 → 6 = 01100110 & 01110110 = 6 (그대로)
크기를 2의 거듭제곱이 아니게 잡으면

N = 100이면 mask = 99 = 1100011이다. head가 3일 때 (3+1) & 99 = 0100 & 1100011 = 0이 되어, 100칸 중 4칸만 쓰고 0번으로 돌아가 버린다. 코드 주석의 “반드시 2의 거듭제곱”은 이 때문이다.

규칙 3. head는 ISR만, tail은 main만 쓴다

두 인덱스를 각각 한 쪽만 수정하면 서로 상대방의 값을 읽기만 한다. 이 구조에서는 인터럽트를 잠시 꺼서 보호하지 않아도 안전하다. 이를 lock-free라고 한다. 조건은 생산자 1개, 소비자 1개이다. 소비자가 둘이거나 main과 다른 ISR이 같은 인덱스를 건드리면 이 보장이 깨진다.

이유를 따져 보자. 이 보드는 CPU 코어가 하나이다. 인터럽트는 main의 어느 명령 사이에든 끼어들 수 있지만, ISR은 끝까지 실행된 뒤 main으로 돌아간다. 따라서 main이 pop 도중에 끊기더라도 ISR이 바꾸는 것은 buf[head]와 head뿐이다. main이 읽는 칸(buf[tail])과 main이 쓰는 값(tail)은 건드리지 않는다. main은 head를 ‘이전 값’ 또는 ‘새 값’ 중 하나로 읽는데, 어느 쪽이든 이미 완성된 데이터까지만 가리킨다(규칙 4).

규칙 4. 데이터를 먼저 쓰고 그 다음에 head를 옮긴다

r->buf[r->head] = b;   // ① 먼저 데이터를 쓴다
r->head = next;        // ② 그 다음에 head를 갱신한다 (소비자에게 "읽어도 됨"을 알리는 신호)

순서를 바꾸어 head를 먼저 옮기면, 그 순간 소비자가 아직 쓰이지 않은 칸을 읽을 수 있다. 소비자에게 head의 갱신은 ‘새 데이터가 준비되었다’는 신호이므로, 신호는 항상 내용을 다 쓴 뒤에 보낸다. 같은 이유로 pop에서는 데이터를 읽은 뒤에 tail을 옮긴다.

head와 tail 변수에는 volatile을 붙인다. 컴파일러가 값을 레지스터에 복사해 두고 메모리를 다시 읽지 않으면, 다른 문맥(ISR)이 바꾼 값을 main이 영영 보지 못할 수 있기 때문이다.

5. 하드웨어에서 링 버퍼까지: 바이트 하나의 여정

Nucleo-F103RB에서는 ST-Link가 만든 가상 COM 포트가 USART2(PA2 = TX, PA3 = RX)에 연결되어 있다. 키보드로 글자 하나를 치면 다음 순서로 처리된다.

  1. 1
    PC가 8N1 프레임을 보낸다 (115200 bps)시작 비트 1 + 데이터 8 + 정지 비트 1 = 10비트. 한 바이트에 약 87 µs가 걸린다.
  2. 2
    USART2가 한 바이트를 모아 DR에 넣고 SR.RXNE를 1로 세운다CR1.RXNEIE가 켜져 있으면 인터럽트 요청이 NVIC로 간다.
  3. 3
    USART2_IRQHandler 실행진짜 ISRstm32f1xx_it.c에 있고, 안에서 HAL_UART_IRQHandler(&huart2)만 호출한다.
  4. 4
    HAL이 DR을 읽어 rx_byte에 저장하고 콜백을 부른다1바이트 수신이 끝나면 HAL은 RXNE 인터럽트를 스스로 끈다.
  5. 5
    HAL_UART_RxCpltCallback에서 rb_push(&rb, rx_byte)생산자그리고 HAL_UART_Receive_IT를 다시 호출해 다음 바이트 수신을 준비한다(재무장).
  6. 6
    main 루프가 while (rb_pop(&rb, &c))로 꺼내 처리한다소비자엔터면 통계를 출력하고, 그 외에는 에코(되돌려 보내기)한다.
ISR과 콜백의 구분

인터럽트 벡터에 직접 연결된 함수는 USART2_IRQHandler뿐이다. HAL_UART_RxCpltCallback은 HAL이 그 안에서 불러 주는 일반 함수이지만, 호출 시점이 ISR 안이므로 ISR 문맥에서 실행된다. 콜백 안에서도 오래 걸리는 일을 하면 안 되는 이유이다.

시간 감각

115200 bps에서는 초당 최대 11,520바이트가 들어온다. 127바이트는 약 11 ms 분량이다. 입력이 연속으로 쏟아질 때 main이 11 ms 넘게 꺼내지 못하면 이 예제의 버퍼는 넘친다.

6. 코드 읽기

아래 코드는 Core/Src/main.c의 사용자 코드(USER CODE) 영역이다. CubeMX가 만든 초기화 코드는 생략한다.

main.c · 자료구조 정의
#define RB_SIZE 128U   /* 2의 거듭제곱 */
#define RB_MASK (RB_SIZE - 1U)

typedef struct {
  volatile uint32_t head; /* ISR만 수정 */
  volatile uint32_t tail; /* main만 수정 */
  uint8_t buf[RB_SIZE];
} ringbuf_t;

static ringbuf_t rb;
static uint8_t rx_byte;
static volatile uint32_t rx_total, dropped, max_used;
  1. RB_MASK = 127 = 0111 1111. 모든 인덱스 계산에 쓰인다.
  2. head와 tail은 volatile이다. 두 문맥이 공유하는 변수이기 때문이다.
  3. rx_byte는 HAL이 수신한 1바이트를 임시로 받는 칸이다. 링 버퍼가 아니다.
  4. rx_total, dropped, max_used는 학습용 통계이다. 실제 제품에서는 없어도 된다.
main.c · push (생산자, ISR에서 호출)
static int rb_push(ringbuf_t *r, uint8_t b)
{
  uint32_t next = (r->head + 1U) & RB_MASK;
  if (next == r->tail) return 0; /* full */
  r->buf[r->head] = b;
  r->head = next;   /* 쓴 "뒤에" 갱신 */
  return 1;
}
  1. head가 가리킬 다음 칸 next를 마스크로 계산한다.
  2. next == tail이면 가득 찬 것이다. 새 바이트를 버리고 0을 반환한다(가장 오래된 데이터를 보존하는 방식).
  3. 그렇지 않으면 buf[head]에 쓴 뒤 head를 next로 옮긴다.
main.c · pop (소비자, main에서 호출) 과 개수 계산
static int rb_pop(ringbuf_t *r, uint8_t *b)
{
  if (r->head == r->tail) return 0; /* empty */
  *b = r->buf[r->tail];
  r->tail = (r->tail + 1U) & RB_MASK;
  return 1;
}

static uint32_t rb_used(const ringbuf_t *r)
{ return (r->head - r->tail) & RB_MASK; }
  1. head == tail이면 꺼낼 것이 없다. 0을 반환한다.
  2. 값을 먼저 읽고, 그 뒤에 tail을 옮긴다.
  3. 반환값 1/0으로 ‘꺼냈는지’를 알린다. 호출 쪽은 while (rb_pop(...))로 비어 있을 때까지 반복한다.
  4. rb_used는 head가 tail보다 작아져도(한 바퀴 돈 뒤) 부호 없는 정수의 뺄셈과 마스크 덕분에 올바른 개수가 나온다. 예: head = 2, tail = 6, N = 8이면 (2−6) & 7 = 4.
main.c · 수신 콜백 (ISR 문맥)
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
  if (huart->Instance != USART2) return;
  rx_total++;
  if (!rb_push(&rb, rx_byte)) dropped++;
  uint32_t u = rb_used(&rb);
  if (u > max_used) max_used = u;
  HAL_UART_Receive_IT(&huart2, &rx_byte, 1);
}
  1. 여러 UART를 쓸 때를 대비해 USART2의 콜백인지 확인한다.
  2. push가 실패하면(가득 참) dropped를 올린다.
  3. 사용량의 최고 기록 max_used를 갱신한다. 버퍼 크기를 정하는 근거 자료가 된다.
  4. 마지막 줄이 중요하다. HAL_UART_Receive_IT는 1바이트를 받으면 인터럽트를 끈다. 다시 호출해 주지 않으면 첫 글자 이후로 아무것도 받지 못한다.
main.c · main 루프 (소비자)
while (1)
{
  if (B1 눌림) {                /* 실험용 */
    HAL_Delay(2000);            /* main이 2초 멈춤 */
  }
  while (rb_pop(&rb, &c))
  {
    if (c == '\r' || c == '\n')
      /* 통계 [rx, dropped, max_used, head, tail] 출력 */
    else
      HAL_UART_Transmit(&huart2, &c, 1, 10); /* 에코 */
  }
}
  1. B1(PC13) 버튼을 누르면 main이 2초 동안 아무것도 꺼내지 못한다. 7절 실험용이다.
  2. 평소에는 버퍼에 쌓인 바이트를 모두 꺼낸 뒤 루프를 돈다.
  3. 에코와 통계 출력은 main(소비자)에서 한다. ISR 안에서는 전송하지 않는다.
  4. 통계에는 출력 시점의 head, tail도 들어 있다. 시뮬레이터의 숫자와 같은 값이므로 터미널 출력을 3절 그림에 대입해 볼 수 있다. 두 값을 한 번에 복사해 쓰는 것은 같은 시점의 값을 보기 위해서이다.

7. 오버플로 실험

준비

보드를 연결하고 터미널을 115200 8N1로 연다. 글자를 치면 에코되고, 엔터를 치면 [rx=N, dropped=M, max_used=K/127, head=H, tail=T]가 출력되는지 먼저 확인한다. 엔터를 처리하는 시점에 버퍼가 비어 있으면 head와 tail은 같은 값이다.

  1. B1을 누른다. [main stalled 2s]가 출력된 뒤 main이 2초간 멈춘다.
  2. 멈춘 동안 터미널에 줄바꿈이 없는 200자 이상의 긴 문장을 붙여 넣는다. ISR은 계속 동작하지만 꺼내 가는 쪽이 없다.
  3. 2초가 지나 main이 깨어나면 저장된 글자가 한꺼번에 에코된다. 엔터를 쳐서 통계를 확인한다.
항목예상이유
max_used127 / 127버퍼가 용량(N−1)까지 찼다.
head, tailhead = tail엔터까지 모두 꺼냈으므로 비어 있다. 보드를 리셋한 직후 ‘B1 → 200자 붙여 넣기 → 엔터’ 순서라면 저장에 성공한 바이트가 127 + 엔터 1 = 128개이므로 128 & 127 = 0, 즉 head = tail = 0으로 한 바퀴 돌아 처음 위치에 와 있다. 예상 출력: [rx=201, dropped=73, max_used=127/127, head=0, tail=0] (엔터가 \r 한 바이트일 때)
dropped붙여 넣은 길이 − 127200자라면 약 73. 가득 찬 뒤 도착한 바이트는 버려진다.
에코로 보이는 글자붙여 넣은 문장의 앞 127자push 실패 시 새 바이트를 버리므로 앞쪽이 보존된다.

토의 문제는 다음과 같다.

  • RB_SIZE를 256으로 늘리면 위 결과는 어떻게 바뀌는가. 2초 동안 멈추는 상황은 해결되는가.
  • 버퍼를 계속 키우는 것이 근본 해결책이 아닌 이유는 무엇인가. (힌트: 3절의 속도 비교, main에서 HAL_Delay를 쓰는 습관)
  • 가득 찼을 때 ‘새 데이터를 버리는 방식’과 ‘가장 오래된 데이터를 덮어쓰는 방식’은 어떤 응용에서 각각 적합한가.

8. 트러블슈팅 포인트

증상원인확인과 해결
첫 글자만 받고 이후 반응이 없다HAL_UART_Receive_IT 재무장 누락콜백 끝에서 다시 호출했는지 확인한다. 오류 콜백(HAL_UART_ErrorCallback)에서도 재시작해야 오버런 이후 수신이 이어진다.
dropped가 계속 늘어난다main이 너무 오래 막혀 있거나 평균 처리 속도가 입력보다 느리다HAL_Delay, 긴 블로킹 전송을 main 루프에서 줄인다. max_used로 여유를 보고 크기를 정한다.
글자 순서가 뒤섞이거나 엉뚱한 값이 나온다RB_SIZE가 2의 거듭제곱이 아니다크기를 64, 128, 256 등으로 바꾼다. 4절 규칙 2 참조.
데이터가 들어왔는데도 main이 계속 ‘비어 있음’으로 판단한다head나 tail에 volatile이 없다. 최적화 수준을 올리면 나타난다공유 변수에 volatile을 붙인다. 디버그 빌드에서는 멀쩡하다가 릴리스 빌드에서만 문제가 되는 대표 사례이다.
가끔 쓰레기 값이 섞인다head를 먼저 옮기고 데이터를 나중에 썼다쓰기 → 갱신 순서를 지킨다.
가끔 데이터가 사라지거나 중복된다소비자가 둘이거나, main과 다른 ISR이 같은 인덱스를 수정한다인덱스 소유자를 하나로 정한다. 불가피하면 짧은 구간에서 인터럽트를 잠시 막는다(__disable_irq).
ISR이 길어져 수신 오버런(ORE)이 난다콜백 안에서 printf, 블로킹 전송, 긴 계산을 한다ISR은 push만 하고 나온다. 처리는 main에서 한다.
터미널에 아무것도 안 보인다보율, 포트, 형식 불일치115200 8N1, 올바른 COM 포트를 확인한다. 이 예제에서 별도 배선은 필요 없다.

9. 확인 문제

먼저 스스로 답을 정해 본 뒤 펼쳐 확인한다.

문제 1. N = 16, head = 15, tail = 3일 때 rb_push 후의 head와 used는?

next = (15+1) & 15 = 16 & 15 = 0. next ≠ tail이므로 저장에 성공하고 head = 0이 된다.

used = (0 − 3) & 15 = 13. (push 전에는 (15−3) & 15 = 12였다.)

문제 2. N = 8, head = 4, tail = 5일 때 이 버퍼는 가득 찬 상태인가? 몇 개가 들어 있는가?

(4+1) & 7 = 5 = tail이므로 가득 찬 상태이다.

used = (4 − 5) & 7 = 7. 최대 용량 N−1 = 7개가 들어 있다.

문제 3. 한 칸을 비우지 않고 N칸을 모두 쓰려면 어떤 설계 변경이 필요한가?

head == tail만으로는 full과 empty를 구분할 수 없으므로 정보를 하나 더 둔다. 예를 들어 저장 개수 count 변수를 따로 두거나, 인덱스를 0 ~ 2N−1까지 세고 인덱스 값에 마스크를 적용해 배열에 접근하는 방법이 있다.

단, count를 ISR과 main이 모두 수정하면 규칙 3(수정 주체를 하나로)이 깨져 보호 장치가 필요해진다. 이 예제가 한 칸을 포기하는 이유이다.

문제 4. 콜백 마지막의 HAL_UART_Receive_IT(&huart2, &rx_byte, 1)를 지우면 어떤 일이 생기는가?

첫 바이트 수신 후 HAL이 RXNE 인터럽트를 끄고, 다시 켜 주는 코드가 없으므로 이후의 입력은 수신되지 않는다. 링 버퍼 코드가 맞아도 데이터가 들어오지 않는 증상이다.

문제 5. 115200 8N1에서 RB_SIZE = 128인 버퍼가 연속 입력에 대해 견딜 수 있는 main의 최대 정지 시간은 대략 얼마인가?

한 바이트는 10비트이므로 11,520 바이트/초이다. 용량 127바이트 ÷ 11,520 ≈ 0.011초, 즉 약 11 ms이다. 그보다 긴 블로킹이 있으면 연속 입력 시 데이터가 유실된다. 이 계산이 버퍼 크기를 정하는 기본 방법이다.
