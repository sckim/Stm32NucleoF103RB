스택 (LIFO): 자료구조에서 CPU 스택까지

링 버퍼가 ‘먼저 들어온 것을 먼저’ 꺼내는 대기열이라면, 스택은 ‘마지막에 들어온 것을 먼저’ 꺼내는 더미이다. 배열과 인덱스 하나로 만드는 소프트웨어 스택을 먼저 익히고, 같은 원리로 동작하는 Cortex-M3의 하드웨어 스택(MSP)이 함수 호출과 인터럽트에서 어떻게 쓰이는지 이 폴더의 링커 스크립트와 startup 코드로 확인한다.

1. 왜 스택이 필요한가

어떤 일은 가장 최근에 시작한 것부터 끝내야 한다. 함수 A가 B를 부르고 B가 C를 부르면, C가 먼저 끝나고 B로, 다시 A로 돌아와야 한다. 괄호 ( [ ] )도 마지막에 연 괄호가 먼저 닫혀야 올바르다. 터미널에서 백스페이스를 누르면 마지막에 친 글자가 먼저 지워진다. 이런 ‘되돌아가기’ 순서를 기억하는 자료구조가 스택이다.

push = 맨 위에 올린다새 항목을 더미의 꼭대기(top)에 쌓는다. 꼭대기가 한 칸 올라간다.
pop = 맨 위에서 꺼낸다꼭대기 항목을 꺼낸다. 꼭대기가 한 칸 내려간다. 가장 나중에 넣은 것이 나온다.

식당의 접시 더미에 비유하면, 씻은 접시는 맨 위에 올리고 쓸 접시도 맨 위에서 가져간다. 맨 아래 접시는 위의 것을 모두 치워야 꺼낼 수 있다. 나중에 넣은 것이 먼저 나오므로 LIFO(Last In, First Out)이다.

2. 핵심 아이디어: 배열 하나와 인덱스 하나

소프트웨어 스택은 고정 크기 배열 buf[N]과 위치 값 top 하나로 이루어진다. 이 교안의 C 코드에서 top은 다음에 쓸 빈 칸의 번호이며, 동시에 저장된 개수와 같다.

  • push는 buf[top]에 쓰고 top을 1 늘린다.
  • pop은 top을 1 줄이고 buf[top]을 읽는다.
  • peek은 꺼내지 않고 꼭대기 값 buf[top − 1]만 본다.
  • 링 버퍼와 달리 인덱스가 0으로 되돌아가지 않는다. 0번 칸이 ‘바닥’이고 N−1번 칸이 ‘천장’이다.
상태 판정

비어 있음(empty): top == 0

가득 참(full): top == N

저장된 개수: top 그 자체

링 버퍼는 한 칸을 비워 두어 N−1개만 담았지만, 스택은 N칸을 모두 쓴다. 인덱스가 하나뿐이고 되감기가 없어 top 값 0과 N이 서로 다른 값이기 때문이다. 이유는 4절 규칙 1에서 다시 본다.

두 가지 실패: overflow와 underflow

overflow: 가득 찬 스택에 push하면 buf[N], 즉 배열 바깥에 쓴다. 옆에 있는 변수가 조용히 망가진다.
underflow: 빈 스택에서 pop하면 buf[−1]을 읽고 top이 음수(부호 없는 정수라면 매우 큰 수)가 된다. 두 경우 모두 반드시 함수 안에서 검사하고 실패를 반환해야 한다.

괄호 검사 단계 실행

관찰 포인트는 다음과 같다.

  • A, B, C 순서로 넣으면 C, B, A 순서로 나온다. 스택은 순서를 뒤집는 장치이다.
  • 가득 찼을 때 top은 N이고, 이 값은 실제 배열 칸 번호(0 ~ N−1)를 벗어난다. 그래서 push 전에 top == N을 검사한다.
  • 괄호 검사에서 실패는 세 가지뿐이다. 짝 불일치, 닫을 것이 없는데 닫음(underflow), 끝났는데 열린 것이 남음(top ≠ 0). 여기에 크기 제한 때문에 생기는 overflow가 더해진다.

4. 이 구현을 지탱하는 네 가지 규칙

규칙 1. top의 의미를 하나로 정하고 끝까지 지킨다

top이 ‘다음 빈 칸’인지 ‘마지막 데이터가 있는 칸’인지에 따라 코드가 달라진다. 둘을 섞으면 한 칸씩 어긋나는(off-by-one) 버그가 생긴다.

방식top이 가리키는 곳pushpopempty / full
빈 칸 방식 (이 교안의 C 코드)다음에 쓸 빈 칸buf[top++] = vv = buf[--top]top==0 / top==N
꽉 찬 방식 (full stack)마지막으로 쓴 칸buf[++top] = vv = buf[top--]top==−1 / top==N−1

빈 칸 방식은 top이 개수와 같아 부호 없는 정수로 다루기 쉽다. 반면 5절의 Cortex-M 하드웨어 스택은 꽉 찬 방식 + 아래로 자라는(full descending) 규칙을 쓴다. 둘은 원리가 같지만 규칙이 다르다는 점을 기억한다.

규칙 2. push 전에 full, pop 전에 empty를 검사한다

배열 범위를 벗어난 쓰기는 C에서 컴파일 오류도, 실행 중 예외도 일으키지 않는다. 바로 옆 메모리에 있던 다른 변수를 덮어쓸 뿐이다. 검사는 호출하는 쪽이 아니라 push/pop 함수 안에 두어야 빠뜨리지 않는다. 실패는 반환값(1/0)으로 알리고, 필요하면 링 버퍼 예제의 dropped처럼 횟수를 세어 눈에 보이게 만든다.

규칙 3. 크기는 2의 거듭제곱일 필요가 없다

링 버퍼는 인덱스를 되감기 위해 & mask를 썼고, 그래서 크기가 2의 거듭제곱이어야 했다. 스택의 인덱스는 0과 N 사이를 오르내리기만 하고 되감기지 않으므로 N = 10, 50, 100 어느 것이든 된다. 크기는 필요한 최대 깊이(예: 허용할 괄호 중첩 단계)로 정한다.

규칙 4. ISR과 main이 함께 쓰면 반드시 임계 구역으로 보호한다

링 버퍼가 인터럽트를 막지 않아도 안전했던 이유는 head는 ISR만, tail은 main만 썼기 때문이다(링 버퍼 교안 규칙 3). 스택은 push와 pop이 같은 top을 고친다. ISR이 push하고 main이 pop하면 두 문맥이 한 변수를 동시에 수정하게 되어 lock-free가 성립하지 않는다.

s->top-- 한 줄은 CPU에서 ‘읽기 → 빼기 → 쓰기’ 세 단계(LDR, SUBS, STR)로 실행된다. 그 사이에 인터럽트가 끼어들면 다음과 같이 된다.

순서main (pop 중)ISR (push)메모리의 top
1LDR r3 ← top (=3)3
2인터럽트 발생buf[3] = X; top = 44
3SUBS r3 = 3 − 1 = 24
4STR top ← 22 (X와 원래 buf[2]가 사라짐)

해결책은 공유 스택을 다루는 짧은 구간 동안 인터럽트를 막는 것이다. 이때 무조건 __enable_irq()로 다시 켜지 말고 PRIMASK를 저장했다가 복원한다. 호출한 쪽이 이미 인터럽트를 막아 둔 상태였다면 무조건 켜는 코드가 그 보호를 깨 버리기 때문이다. 코드는 6절에 있다.

5. CPU 안의 스택: Cortex-M3의 MSP

C 언어의 지역 변수, 함수 인자, 돌아갈 주소는 모두 CPU가 관리하는 하드웨어 스택에 저장된다. Cortex-M3는 스택 포인터 레지스터 SP(R13)를 가지며, 기본으로 쓰는 것이 MSP(Main Stack Pointer)이다. 이 프로젝트는 RTOS를 쓰지 않으므로 main과 모든 ISR이 MSP 하나를 함께 쓴다.

스택은 어디에 있고 얼마나 큰가

이 폴더의 링커 스크립트 STM32F103RBTX_FLASH.ld는 다음과 같이 정의한다.

/* Highest address of the user mode stack */
_estack = ORIGIN(RAM) + LENGTH(RAM);

_Min_Heap_Size  = 0x200; /* required amount of heap  */
_Min_Stack_Size = 0x400; /* required amount of stack */

MEMORY
{
  RAM   (xrw) : ORIGIN = 0x20000000, LENGTH = 20K
  FLASH (rx)  : ORIGIN = 0x8000000,  LENGTH = 128K
}

RAM은 0x2000_0000부터 20 KB(= 0x5000)이므로 _estack = 0x2000_5000, 즉 RAM의 맨 끝이다. 스택은 여기서 시작해 낮은 주소 쪽으로 자란다. 전역 변수(.data, .bss)와 힙은 RAM 앞쪽부터 위로 자란다.

_Min_Stack_Size는 ‘한계’가 아니라 ‘예약’이다

0x400(1 KB)은 링크할 때 “전역 변수 + 힙 + 1 KB 스택이 RAM에 들어가는가”를 확인하는 데 쓰인다(링커 스크립트의 ._user_heap_stack 구간). 그리고 Core/Src/sysmem.c의 _sbrk가 힙이 이 예약 구간을 침범하지 않게 막는다.

const uint32_t stack_limit = (uint32_t)&_estack - (uint32_t)&_Min_Stack_Size;
const uint8_t *max_heap = (uint8_t *)stack_limit;
...
/* Protect heap from growing into the reserved MSP stack */
if (__sbrk_heap_end + incr > max_heap) { errno = ENOMEM; return (void *)-1; }

즉 힙은 막지만 스택 자신은 막지 않는다. 실행 중 스택이 1 KB를 넘어 자라면 CPU는 아무 경고 없이 그 아래 메모리를 계속 쓴다.

전원이 켜질 때 SP는 어떻게 정해지는가

Core/Startup/startup_stm32f103rbtx.s의 벡터 테이블 첫 두 워드는 다음과 같다.

g_pfnVectors:
  .word _estack          /* 0번 워드: 초기 MSP 값 */
  .word Reset_Handler    /* 1번 워드: 리셋 후 실행할 주소 */

리셋되면 Cortex-M3 하드웨어가 0번 워드를 읽어 MSP에 넣고, 1번 워드로 점프한다. 그래서 Reset_Handler에는 SP를 설정하는 명령이 없다. 코드가 한 줄도 실행되기 전에 스택이 이미 준비되어 있다.

함수 호출과 스택

함수가 다른 함수를 부를 때 돌아갈 주소는 링크 레지스터 LR(R14)에 들어간다. 호출된 함수가 또 다른 함수를 부르려면 LR을 잃지 않도록 스택에 보관한다. 컴파일러가 만드는 전형적인 함수 앞뒤 코드는 다음과 같다.

push {r4, r5, lr}    @ 진입: 쓸 레지스터와 복귀 주소를 쌓는다 (SP -= 12)
sub  sp, sp, #16      @ 지역 변수 공간 확보
     ...
add  sp, sp, #16
pop  {r4, r5, pc}    @ 복귀: 꺼낸 lr 값을 pc에 넣어 바로 돌아간다

함수가 깊이 중첩될수록, 지역 배열이 클수록 스택이 깊어진다. 재귀 함수는 호출할 때마다 이 과정이 반복되므로 깊이를 예측하기 어렵다.

인터럽트가 들어올 때: 하드웨어 자동 저장(stacking)

  1. 1
    main 루프 실행 중Thread 모드SP = MSP. main의 지역 변수가 스택에 있다.
  2. 2
    USART2 수신 인터럽트 발생 → 하드웨어가 8개 레지스터를 스택에 pushR0, R1, R2, R3, R12, LR, PC, xPSR = 8워드 = 32바이트. 소프트웨어 명령 없이 CPU가 자동으로 한다.
  3. 3
    LR에 EXC_RETURN 값(0xFFFFFFF9)을 넣고 USART2_IRQHandler로 점프Handler 모드0xFFFFFFF9는 “복귀할 때 MSP에서 꺼내 Thread 모드로 돌아가라”는 표시이다.
  4. 4
    ISR → HAL_UART_IRQHandler → HAL_UART_RxCpltCallback각 함수의 push와 지역 변수가 같은 MSP 위에 더 쌓인다. 콜백도 ISR 문맥이다.
  5. 5
    ISR이 bx lr로 끝나면 하드웨어가 8개 레지스터를 popEXC_RETURN을 본 CPU가 저장해 둔 PC로 돌아가 main이 끊긴 자리부터 이어서 실행한다.

6. 코드 읽기

계층과 위치

아래 코드는 이 교안을 위해 작성한 예시 코드이며 현재 Core/Src/main.c에는 들어 있지 않다. 계층은 HAL(UART 송수신) + CMSIS 내장 함수(__get_PRIMASK, __disable_irq, __set_PRIMASK, __get_MSP)이다. 직접 넣어 볼 때는 CubeMX 재생성 시 지워지지 않도록 반드시 /* USER CODE BEGIN ... */ ~ /* USER CODE END ... */ 영역 안에 둔다(예: 정의는 PV/0, 함수는 4, 루프 코드는 3).

main.c · 자료구조 정의 (USER CODE BEGIN PV)
#define STK_SIZE 32U  /* 최대 중첩 깊이. 2의 거듭제곱일 필요 없음 */

typedef struct {
  uint8_t  buf[STK_SIZE];
  uint32_t top;   /* 다음에 쓸 빈 칸 = 저장된 개수 */
} stk_t;

static stk_t    stk;
static uint32_t stk_max_depth;
  1. top 하나로 위치와 개수를 함께 나타낸다(4절 규칙 1의 빈 칸 방식).
  2. 이름을 stack_t로 짓지 않는다. newlib의 signal.h에 같은 이름의 형이 있어 충돌할 수 있다.
  3. 이 스택은 main에서만 쓰므로 volatile이 필요 없다. ISR과 공유할 때는 아래 임계 구역 버전을 쓴다.
main.c · push / pop / peek (USER CODE BEGIN 0)
static int stk_push(stk_t *s, uint8_t v)
{
  if (s->top >= STK_SIZE) return 0; /* overflow */
  s->buf[s->top] = v;
  s->top++;
  if (s->top > stk_max_depth) stk_max_depth = s->top;
  return 1;
}

static int stk_pop(stk_t *s, uint8_t *v)
{
  if (s->top == 0U) return 0;        /* underflow */
  s->top--;
  *v = s->buf[s->top];
  return 1;
}

static int stk_peek(const stk_t *s, uint8_t *v)
{
  if (s->top == 0U) return 0;
  *v = s->buf[s->top - 1U];
  return 1;
}
  1. push는 검사 → 쓰기 → top 증가 순서이다. >=로 검사하면 top이 어떤 이유로 N을 넘었을 때도 막힌다.
  2. pop은 검사 → top 감소 → 읽기 순서이다. push의 정확한 역순이다.
  3. peek은 top을 바꾸지 않는다. 괄호 검사, 수식 계산에서 ‘꺼내기 전에 보기’에 쓴다.
  4. stk_max_depth는 링 버퍼의 max_used와 같은 학습용 통계이다. STK_SIZE를 정하는 근거가 된다.
main.c · 응용: 링 버퍼로 받고 스택으로 괄호 검사 (USER CODE BEGIN 3, while 루프 안)
while (rb_pop(&rb, &c))          /* FIFO: 받은 순서대로 */
{
  if (c == '(' || c == '[' || c == '{') {
    if (!stk_push(&stk, c)) err = "overflow";
  }
  else if (c == ')' || c == ']' || c == '}') {
    uint8_t o;
    if (!stk_pop(&stk, &o))   err = "underflow";
    else if (!pair_ok(o, c))   err = "mismatch";
  }
  else if (c == '\r') {
    if (!err && stk.top != 0U) err = "unclosed";
    /* "OK" 또는 err 출력, max_depth 출력 */
    stk.top = 0U; err = NULL;     /* 다음 줄 준비 */
  }
  HAL_UART_Transmit(&huart2, &c, 1, 10);  /* 에코 */
}
  1. 데이터는 링 버퍼 예제의 rb_pop으로 받는다. FIFO로 들어온 순서를 유지한 채, 검사는 LIFO로 한다. 두 자료구조가 각자 잘하는 일을 나눠 맡는다.
  2. pair_ok(o, c)는 (와 ), [와 ], {와 }가 짝인지 비교하는 작은 함수이다.
  3. 엔터에서 스택이 비어 있지 않으면 닫지 않은 괄호가 남은 것이다.
  4. 스택은 main(소비자) 안에서만 쓰이므로 인터럽트 보호가 필요 없다. ISR에서는 push만 하는 링 버퍼, main에서는 스택으로 역할을 나누면 임계 구역이 필요 없는 구조가 된다.
main.c · ISR과 공유해야 할 때: 임계 구역 (USER CODE BEGIN 0)
static int stk_push_safe(stk_t *s, uint8_t v)
{
  uint32_t primask = __get_PRIMASK(); /* 현재 PRIMASK 저장 */
  __disable_irq();                    /* PRIMASK = 1: 설정 가능한 인터럽트 차단 */
  int ok = stk_push(s, v);
  __set_PRIMASK(primask);             /* 원래 상태로 복원 */
  return ok;
}
  1. PRIMASK는 Cortex-M3의 특수 레지스터로, 비트 0이 1이면 NMI와 HardFault를 제외한 모든 예외가 막힌다.
  2. push/pop 모두 같은 방식으로 감싸야 한다. 한쪽만 보호하면 4절 표의 문제가 그대로 남는다.
  3. 막는 구간은 몇 줄로 짧게 유지한다. 길어지면 그동안 들어온 UART 바이트가 오버런(ORE)으로 유실될 수 있다.
  4. 무조건 __enable_irq()를 쓰지 않는 이유는 4절 규칙 4의 마지막 문단을 참조한다.

7. 스택 측정 실험

준비

링 버퍼 예제를 그대로 쓴다. 터미널은 115200 8N1이다. 아래 코드는 학생이 직접 추가하는 실험 코드이며(HAL + CMSIS), 모두 USER CODE 영역 안에 넣는다. 결과 숫자는 컴파일러 최적화 수준에 따라 달라지므로 직접 측정해 기록한다.

실험 A. main과 ISR에서 SP 값 비교

/* USER CODE BEGIN PV */
static volatile uint32_t isr_sp;        /* 콜백에서 기록, main에서 출력 */

/* HAL_UART_RxCpltCallback 안 (ISR 문맥) 첫 줄 */
isr_sp = __get_MSP();                    /* 출력은 하지 않고 기록만 한다 */

/* main 루프, 엔터 처리 부분 (소비자) */
printf("main SP=0x%08lX, isr SP=0x%08lX, diff=%lu\r\n",
       __get_MSP(), isr_sp, __get_MSP() - isr_sp);
  1. main의 SP가 0x2000_5000보다 조금 작은 값인지 확인한다. main 자체와 HAL 초기화가 쓴 만큼 내려가 있다.
  2. diff는 하드웨어 프레임 32바이트 + IRQHandler + HAL_UART_IRQHandler + 콜백이 쌓은 양이다. 32보다 훨씬 큰 값이 나오는 것을 확인한다.
  3. 콜백 안에서 printf를 쓰지 않는 이유를 다시 떠올린다(ISR은 짧게, 출력은 main에서).

실험 B. 스택 칠하기(stack painting)로 최대 사용량 측정

/* USER CODE BEGIN 0 */
extern uint8_t _estack, _Min_Stack_Size;   /* 링커 심볼: 주소가 곧 값 */
#define PAINT 0xA5A5A5A5UL

static void stack_paint(void)
{
  uint32_t *p  = (uint32_t *)((uint32_t)&_estack - (uint32_t)&_Min_Stack_Size);
  uint32_t *sp = (uint32_t *)__get_MSP();
  while (p < sp - 16) *p++ = PAINT;     /* 현재 SP 아래 64바이트는 남긴다 */
}

static uint32_t stack_peak(void)
{
  uint32_t *p = (uint32_t *)((uint32_t)&_estack - (uint32_t)&_Min_Stack_Size);
  while (p < (uint32_t *)&_estack && *p == PAINT) p++;
  return (uint32_t)&_estack - (uint32_t)p; /* 지금까지 쓴 최대 바이트 수 */
}

/* USER CODE BEGIN 2 (초기화 직후) */  stack_paint();
/* 엔터 처리 부분 */  printf("stack peak=%lu / 1024\r\n", stack_peak());
  1. 예약 구간 맨 아래(_estack − 0x400)부터 현재 SP 바로 아래까지만 칠한다. 지금 사용 중인 스택 프레임을 덮지 않기 위해서이다.
  2. 스택이 깊어지면 칠한 무늬가 지워진다. 아래에서부터 무늬가 남아 있는 곳을 세어 ‘최고 수위’를 구한다.
  3. 평소 입력, 긴 문장 붙여 넣기, B1 버튼(HAL_Delay) 후 각각 peak가 어떻게 달라지는지 기록한다.
  4. peak가 1024에 가깝다면 예약 구간을 이미 넘었을 가능성이 있다(이 방법은 예약 구간 안만 본다). _Min_Stack_Size를 늘려 다시 측정한다.

실험 C (선택). 재귀로 스택 넘치게 하기

static volatile uint32_t depth;

static void dive(uint32_t d)
{
  volatile uint8_t pad[64];   /* volatile: 컴파일러가 지우지 못하게 */
  pad[0] = (uint8_t)d;
  depth  = d;
  dive(d + 1U);
  pad[1] = pad[0];             /* 호출 뒤에 할 일을 남겨 꼬리 호출 최적화 방지 */
}
  1. B1을 누르면 dive(0)을 부르도록 하고 디버거로 depth와 SP를 관찰한다.
  2. SP가 _estack − 0x400 아래로 내려가도 CPU는 멈추지 않는다는 것을 확인한다. 그 아래의 .bss(링 버퍼 rb, huart2 핸들 등)가 덮어써지면서 동작이 이상해지고, 더 내려가면 HardFault로 멈출 수 있다.
  3. 실험 후에는 반드시 코드를 지운다.

토의 문제는 다음과 같다.

  • 실험 A의 diff 값이 최적화 수준(-O0, -Os)에 따라 어떻게 달라지는가. 그 이유는 무엇인가.
  • 실험 B에서 측정한 peak를 근거로 _Min_Stack_Size를 정한다면 얼마의 여유를 더 두어야 하는가. (힌트: 측정하지 못한 경로, 중첩 인터럽트)
  • 재귀 대신 6절의 소프트웨어 스택으로 같은 알고리즘을 구현하면 무엇이 좋아지는가. (힌트: 깊이 제한을 코드에서 검사할 수 있다)

8. 트러블슈팅 포인트

증상원인확인과 해결
스택 옆의 전역 변수가 이유 없이 바뀐다소프트웨어 스택 push에서 full 검사 누락 (overflow)push 안에서 top >= N을 검사한다. 4절 규칙 2.
pop한 값이 엉뚱하고 그 뒤로 계속 이상하다empty 검사 누락 (underflow). 부호 없는 top이 0에서 빼져 매우 큰 수가 되었다pop 안에서 top == 0을 검사한다.
한 칸씩 어긋난 값이 나온다top의 의미(빈 칸 / 마지막 칸)를 섞어 썼다4절 규칙 1의 표 중 하나로 통일한다.
가끔 데이터가 사라지거나 중복된다ISR과 main이 같은 스택을 보호 없이 수정한다PRIMASK 저장/복원 임계 구역으로 감싸거나, ISR 쪽은 링 버퍼로 바꾼다. 4절 규칙 4.
코드를 조금 추가했더니 무작위로 멈추거나 HardFault가 난다하드웨어 스택 넘침. 큰 지역 배열, 깊은 호출, printf(서식 처리에 스택을 많이 쓴다)실험 B로 peak를 측정한다. 큰 배열은 static이나 전역으로 옮기고 _Min_Stack_Size를 늘린다.
디버그 빌드에서는 괜찮고 릴리스 빌드에서만 문제가 생긴다 (또는 반대)최적화 수준에 따라 인라인, 레지스터 사용이 달라져 스택 깊이가 변한다배포할 설정으로 peak를 다시 측정한다.
ISR 안에서만 멈춘다ISR에서 큰 지역 변수를 쓰거나, 중첩 인터럽트가 겹쳐 스택이 모자라다ISR의 지역 변수를 줄이고 처리를 main으로 옮긴다. 5절 중첩 인터럽트 박스 참조.
링크 단계에서 will not fit in region RAM 오류가 난다전역 변수 + 힙 예약 + 스택 예약이 20 KB를 넘었다큰 전역 배열을 줄이거나 _Min_Heap_Size, _Min_Stack_Size를 조정한다.

9. 확인 문제

먼저 스스로 답을 정해 본 뒤 펼쳐 확인한다.

문제 1. 빈 스택에 push A, push B, push C, pop, push D, pop, pop을 차례로 하면 꺼낸 순서와 남은 내용은?

꺼낸 순서: C, D, B. 남은 내용: A 하나 (top = 1).

시뮬레이터에서 같은 순서로 눌러 확인해 본다.

문제 2. N = 8, top = 8인 스택에 push하면? 6절 코드는 어떻게 반응하는가?

top == N이므로 가득 찬 상태이다. 검사 없이 쓰면 buf[8], 즉 배열 바깥을 덮어쓴다. 6절의 stk_push는 top >= STK_SIZE에서 0을 반환하고 아무것도 쓰지 않는다.

문제 3. 링 버퍼는 N−1개만 담지만 스택은 N개를 모두 담는다. 왜 차이가 나는가?

링 버퍼는 인덱스가 되감기므로 ‘텅 빔’과 ‘가득 참’이 모두 head == tail로 나타나는 모호함이 생겨 한 칸을 포기했다.

스택은 인덱스가 하나이고 되감기지 않아 빈 상태(top = 0)와 가득 찬 상태(top = N)가 항상 다른 값이다. 그래서 칸을 비워 둘 필요가 없다.

문제 4. 괄호 문자열 ([)]를 검사하면 어느 글자에서 무슨 오류가 나는가?

( push, [ push, 세 번째 글자 )에서 pop하면 [가 나온다. [와 )는 짝이 아니므로 mismatch이다. 괄호의 개수는 맞지만 순서가 틀린 경우를 스택이 잡아낸다.

문제 5. ISR이 push하고 main이 pop하는 스택에서 인터럽트 보호가 필요한 이유를, 링 버퍼가 보호 없이 안전했던 이유와 비교해 설명하라.

링 버퍼는 head는 ISR만, tail은 main만 수정했다. 각 변수의 수정 주체가 하나이므로 읽기-수정-쓰기가 끊겨도 상대가 그 변수를 바꾸지 않는다.

스택은 push와 pop이 모두 top을 수정한다. main의 top--(LDR-SUBS-STR) 도중에 ISR이 top을 바꾸면 main이 오래된 값으로 덮어써 데이터가 사라진다(4절 표). 따라서 PRIMASK를 이용한 임계 구역이 필요하다.

문제 6. main이 최대 400바이트, ISR1이 최대 80바이트, ISR1을 선점할 수 있는 ISR2가 최대 48바이트의 스택을 쓴다. 필요한 스택은 대략 얼마인가? 이 프로젝트의 예약값으로 충분한가?

400 + (32 + 80) + (32 + 48) = 592바이트. 각 선점 단계마다 하드웨어 프레임 32바이트를 더한다.

예약값 _Min_Stack_Size = 0x400 = 1024바이트이므로 계산상 충분하다. 다만 측정하지 못한 경로를 고려해 실험 B로 실제 peak를 확인하고 여유를 둔다.

문제 7. 리셋 직후 첫 명령이 실행되기 전 MSP의 값은? 그 값은 어디에서 오는가?

0x2000_5000이다. 벡터 테이블 0번 워드에 _estack(= ORIGIN(RAM) + LENGTH(RAM) = 0x2000_0000 + 20 KB)이 들어 있고, 하드웨어가 리셋 시 이 값을 MSP에 넣는다. Reset_Handler에는 SP를 설정하는 코드가 없다.
