PCF8574: 바이트 하나로 핀 여덟 개를 바꾼다

PCF8574는 I2C로 받은 1바이트를 핀 P7~P0에 그대로 내보내는 8비트 입출력 확장 IC이다. MCU는 SCL, SDA 두 선만 쓰고도 출력 핀 8개를 얻는다. 이 예제설명은 쓰기·읽기 프레임, PCF8574의 준양방향 핀 구조, LED를 액티브 Low로 다는 이유를 차례로 보고, I2C1을 HAL 폴링 방식으로 쓰는 02_PCF8574_Output 예제를 해석한다.

1. 문제: MCU 핀이 모자랄 때

LED 8개를 MCU 핀에 직접 달면 GPIO 8개가 든다. Nucleo의 Arduino 헤더는 핀 수가 정해져 있고, 그중 일부는 UART, SPI, 아날로그 입력 같은 다른 용도와 겹친다. 버튼, 릴레이, 표시 장치를 더 붙이려면 금방 핀이 바닥난다.

I2C 입출력 확장 IC는 이 문제를 2선 직렬 버스로 푼다. MCU는 SCL, SDA 두 핀으로 PCF8574에 바이트를 보내고, PCF8574는 그 바이트의 비트 8개를 P7~P0 핀 8개에 하나씩 내보낸다. 같은 버스에 주소가 다른 PCF8574를 8개까지 달 수 있으므로 두 핀으로 최대 64개 핀을 늘릴 수 있다. 다른 I2C 장치(센서, EEPROM, RTC)도 같은 두 선을 함께 쓴다.

그림 1. 이 예제의 구성. MCU 핀 2개가 확장 IC의 핀 8개가 된다. LED는 VCC 쪽에서 전류를 받아 Px로 흘려 넣는 방향으로 단다(이유는 2절).

대가도 있다. GPIO 레지스터 한 번 쓰기(수십 ns)면 끝날 일을 I2C로는 주소 바이트 + 데이터 바이트 + START/STOP을 보내야 한다. 100 kHz에서 약 20비트 시간, 즉 0.2 ms 정도 걸린다(HAL 처리 시간 제외 추정치). LED나 LCD처럼 사람이 보는 장치에는 충분히 빠르지만, 수 µs 단위로 정밀하게 토글해야 하는 신호에는 맞지 않는다.

  • PCF8574 주소 0100 A2A1A0와 HAL 인자 0x27 << 1 = 0x4E의 관계를 설명할 수 있다.
  • 쓰기 프레임(START, 0x4E, ACK, 데이터, ACK, STOP)과 읽기 프레임(START, 0x4F, ACK, 핀 상태, NACK, STOP)을 읽을 수 있다.
  • 준양방향 핀에서 0은 강한 Low, 1은 약한 풀업이라는 점과, 그래서 LED를 액티브 Low로 단다는 점을 설명할 수 있다.
  • 읽기 값이 출력 래치가 아니라 실제 핀 전압이라는 점을 실험으로 확인한다.
  • I2C1 레지스터(CR1, SR1, SR2, DR, CCR, TRISE)와 HAL 1바이트 송수신 순서를 연결한다.
이 예제의 위치

04_I2C_Communication 그룹의 두 번째 예제이다. 앞 예제 01_I2C_Scan으로 버스에 응답하는 주소를 확인한 다음, 응용 없이 "바이트 하나 = 핀 8개"만 본다. 다음 예제 03_PCF8574_LCD는 같은 PCF8574, 같은 핀(PB8/PB9), 같은 주소로 문자 LCD를 구동한다. printf를 USART2로 보내는 방법은 02_USART/01_USART_printf에서 가져왔다. MCU 핀으로 LED를 직접 켜는 방식과 비교하려면 01_GPIO/04_BlinkReg를 본다.

핀 주의

이 예제는 I2C1을 리맵해서 SCL = PB8(Arduino D15), SDA = PB9(Arduino D14)를 쓴다(AFIO_MAPR.I2C1_REMAP = 1). 근거는 stm32f1xx_hal_msp.c의 HAL_I2C_MspInit()에 있는 __HAL_AFIO_REMAP_I2C1_ENABLE()이다. .ioc는 03_PCF8574_LCD의 것을 복사해 이름만 바꿨으므로 두 예제의 회로가 같다. 그룹의 03 이후 예제는 기본 핀 PB6/PB7을 쓴다.

회로 연결도

브레드보드에 꾸밀 실제 배선이다. 그림 1의 블록 구성을 핀 번호 단위로 풀었다. 그림의 3.3V 기호는 모두 Nucleo의 3V3 핀(CN6) 한 넷이고, GND 기호도 모두 같은 GND이다.

2. PCF8574 동작: 주소, 프레임, 준양방향 핀

주소

PCF8574의 7비트 주소는 상위 4비트가 0100으로 고정이고, 하위 3비트는 칩의 A2, A1, A0 핀을 어디에 연결했는지로 정한다. 이 예제는 세 핀을 모두 VCC에 연결해 0100 111 = 0x27이다. PCF8574A는 상위 4비트가 0111이라 0x38~0x3F를 쓴다. 같은 버스에 두 종류를 섞으면 16개까지 달 수 있다.

HAL 함수는 주소 인자를 주소 바이트 형태로 받는다. 내부 매크로 I2C_7BIT_ADD_WRITE(addr)는 addr & ~0x01, I2C_7BIT_ADD_READ(addr)는 addr | 0x01이다. 최하위 비트만 바꾸고 시프트는 하지 않는다. 그래서 코드는 #define PCF_ADDR (0x27 << 1)로 0x4E를 만들어 넘긴다.

쓰기 주소 바이트 = 0x4E & ~1 = 0x4E (0100 1110) 읽기 주소 바이트 = 0x4E | 1 = 0x4F (0100 1111)

쓰기 프레임: 데이터 바이트 = 핀 상태

PCF8574는 내부 레지스터 주소가 없다. 주소 바이트 다음에 오는 데이터 바이트가 곧바로 출력 포트가 된다. 비트 7이 P7, 비트 0이 P0이다. 포트 값은 데이터 바이트의 ACK가 끝나는 시점에 바뀐다.

그림 2. 1바이트 쓰기와 1바이트 읽기. 읽기의 마지막 NACK는 오류가 아니라 마스터가 "더 받지 않겠다"고 알리는 정상 절차이다.

한 번의 START~STOP 안에서 데이터 바이트를 여러 개 보내면 바이트마다 포트가 갱신된다. 다음 예제 03_PCF8574_LCD는 이 성질로 바이트 2개, 4개를 이어 보내 LCD의 E 핀을 1 → 0으로 흔든다. 이 예제는 1바이트만 보낸다.

속도: PCF8574 데이터시트의 최대 SCL 클럭은 100 kHz이다. 이 예제는 표준 모드 100 kHz(ClockSpeed = 100000)를 쓴다. 1비트는 10 µs, ACK를 포함한 1바이트는 9비트 = 90 µs이다.

준양방향(quasi-bidirectional) 핀

PCF8574의 핀에는 "입력/출력 방향 레지스터"가 없다. 대신 각 핀이 다음 두 상태 중 하나이다.

쓴 비트핀 구동핀 전압할 수 있는 일
0강한 Low: 내부 트랜지스터가 핀을 GND로 당긴다. 전류를 흡수(sink)한다LowLED, 릴레이 드라이버 등을 Low에서 켜는 출력
1약한 풀업: 약 100 µA 정도의 작은 전류원이 핀을 High 쪽으로 끈다외부가 가만히 있으면 High, 외부가 Low로 누르면 LowHigh 출력(전류를 거의 못 냄), 또는 입력(버튼 등)

정확한 sink 전류 한계와 풀업 전류 범위는 제조사 데이터시트(PCF8574, TI 또는 NXP)의 전기적 특성 표를 확인한다. 이 예제설명이 쓰는 사실은 "0은 강하다, 1은 약하다" 하나이다. 전원 투입 직후 포트는 모두 1(High)이다. 그래서 코드가 처음에 0xFF를 쓰는 것은 전원 직후 상태와 같다.

그래서 LED는 액티브 Low

그림 3. PCF8574는 전류를 "내보내기"보다 "흡수"를 잘한다. 그래서 LED 전류는 VCC에서 받아 Px로 흘려 넣는다. 결과적으로 0을 쓰면 켜지고 1을 쓰면 꺼진다.

LED 전류는 대략 (VCC − VF) / R이다. 예를 들어 VF를 2 V로 가정하면 3.3 V, 330 Ω에서 약 3.9 mA, 1 kΩ에서 약 1.3 mA이다(LED 색과 종류에 따라 VF가 다르므로 가정값이다). LED 8개를 모두 켜는 0x00에서는 이 전류의 8배가 칩으로 들어가므로, 칩 전체 허용 전류도 데이터시트에서 확인한다.

읽기 = 실제 핀 전압

읽기 프레임의 데이터 바이트는 출력 래치(마지막으로 쓴 값)가 아니라 핀의 실제 전압 레벨이다. 이것이 준양방향 핀의 입력 원리이다.

  • 0을 써 둔 핀은 칩이 강하게 Low로 잡고 있으므로 항상 0으로 읽힌다.
  • 1을 써 둔 핀은 약한 풀업만 걸려 있다. 외부에서 버튼이나 점퍼로 GND에 연결하면 핀이 Low가 되고 0으로 읽힌다. 외부가 가만히 있으면 1로 읽힌다.
  • 따라서 핀을 입력으로 쓰려면 먼저 1을 써 둔다. 0을 써 둔 핀은 입력으로 쓸 수 없다.
읽은 값 R = 쓴 값 W AND NOT(외부에서 Low로 누른 핀)

코드는 매번 쓰고 나서 바로 읽어 W와 R을 비교한다. 정상이면 W == R이다. 다르다면 1을 쓴 핀 중 어떤 것이 외부에서 Low로 눌려 있다는 뜻이다. PCF8574에는 입력 변화를 알리는 오픈 드레인 출력 INT 핀도 있지만 이 예제는 쓰지 않는다(폴링으로 읽는다).

3. 직접 만져 보기

시뮬레이터는 main.c의 한 루프(pcf_write(w) → pcf_read(&r) → print_state(w, r))를 그대로 흉내 낸다. 코드의 HAL 인자는 0x4E로 고정이고, 바꿀 수 있는 것은 칩의 주소 핀과 외부 회로이다.

  1. P7~P0 아래의 비트 버튼을 눌러 바이트를 만든다. 0인 비트의 LED가 켜지는 것을 본다.
  2. 쓰기 프레임 바이트 열과 파형에서 데이터 바이트 ACK 뒤에 핀이 바뀌는(▼) 지점을 찾는다.
  3. 1을 써 둔 핀의 외부 Low를 체크한다. LED가 켜지고 R이 W와 달라지며, UART 줄 끝에 <- R differs가 붙는다. 그런데 UART의 LED= 표시는 그 핀을 -(꺼짐)로 보여 준다. 왜 그런지 6절에서 확인한다.
  4. 주소 핀 A0의 체크를 풀어 칩 주소를 0x26으로 바꾼다. NACK가 나고 핀이 이전 값에 머문다.

SCL·SDA는 이상화한 모양이다. 초록 칸은 ACK(SDA Low), 주황 칸은 NACK(SDA High). ▼는 데이터 바이트의 ACK가 끝나 P7~P0이 바뀌는 지점이다. 쓰기 주소가 NACK이면 HAL이 STOP을 내고 HAL_ERROR를 돌려주므로 데이터 바이트와 읽기 프레임은 나가지 않는다.

시뮬레이터 모델: 비트 버튼, 외부 Low, 주소 핀을 바꿀 때마다 루프 한 번(pcf_write → pcf_read → print_state)을 실행한다. 재생 간격은 보기 좋게 0.6초로 늘렸다(실제 STEP_MS = 300 ms). LED는 핀 레벨이 Low일 때 켜진다. 버스 시간은 프레임당 (바이트 수 × 9 + 2) × 10 µs로 어림했고 HAL 처리 시간은 빠져 있다.

근거는 framework-stm32cubef1의 stm32f1xx_hal_i2c.c이다. 아래 흐름에서 보라색 번호는 하드웨어 플래그를 기다리는 단계, 파란색은 소프트웨어가 레지스터를 쓰는 단계이다.

pcf_write() = HAL_I2C_Master_Transmit(&hi2c1, 0x4E, &value, 1, 10)

  1. 1
    BUSY 대기SR2.BUSY가 0이 될 때까지 최대 25 ms(I2C_TIMEOUT_BUSY_FLAG). 넘으면 HAL_BUSY
  2. 2
    CR1.POS = 0, CR1.START = 1상태를 BUSY_TX로 바꾸고 START를 요청한다
  3. 3
    SB 대기 → DR = 0x4EEV5. 주소 바이트(쓰기)를 보낸다
  4. 4
    ADDR 또는 AFADDR(EV6)이면 SR1·SR2를 읽어 지운다. AF가 먼저 서면 STOP을 내고 AF를 지운 뒤 HAL_ERROR, ErrorCode = HAL_I2C_ERROR_AF(0x04)
  5. 5
    TxE 대기 → DR = value데이터 1바이트를 쓴다
  6. 6
    BTF 대기 → CR1.STOP = 1데이터 바이트와 그 ACK까지 끝났다. 이 시점에 PCF8574 핀은 이미 바뀌었다. STOP을 내고 HAL_OK

pcf_read() = HAL_I2C_Master_Receive(&hi2c1, 0x4E, &value, 1, 10)

  1. 1
    BUSY 대기, CR1.POS = 0송신과 같다
  2. 2
    CR1.ACK = 1, CR1.START = 1I2C_MasterRequestRead(). SB를 기다려 DR = 0x4E | 1 = 0x4F
  3. 3
    ADDR 대기AF면 송신과 같이 HAL_ERROR
  4. 4
    1바이트 전용 순서: CR1.ACK = 0 → ADDR 지움 → CR1.STOP = 1받을 바이트가 하나뿐이므로 그 바이트 뒤에 NACK와 STOP이 나가도록 ADDR을 지우기 전에 ACK를 끈다. HAL은 이 구간을 __disable_irq() ~ __enable_irq()로 감싸 인터럽트가 끼어들지 못하게 한다(소스 주석은 이를 EV6_3 순서라 부른다)
  5. 5
    RxNE 대기 → value = DRPCF8574가 보낸 핀 레벨 바이트를 읽고 HAL_OK
왜 1바이트 읽기가 특별한가

STM32F1 I2C는 바이트를 받는 동안 이미 다음 ACK/NACK를 정해 두어야 한다. ADDR을 지우는 순간 슬레이브가 데이터 바이트를 보내기 시작하므로, 그 전에 ACK = 0을 만들어 두지 않으면 마스터가 ACK를 내고 PCF8574는 다음 바이트를 보내려 한다. HAL은 받을 바이트 수가 1, 2, 3 이상인 경우를 각각 다르게 처리한다. 이 예제는 가장 단순한 1바이트 경우만 쓴다.

HAL_I2C_IsDeviceReady(&hi2c1, 0x4E, 3, 10)

START와 주소 바이트만 보내고 데이터는 보내지 않는다. ADDR이 서면 STOP을 내고 HAL_OK, AF가 서면 AF를 지우고 STOP을 낸 뒤 다시 시도한다. 시도 횟수(Trials)가 3이므로 세 번 모두 NACK이면 HAL_ERROR이다. 이 예제는 시작할 때 한 번만 부르고, 실패해도 멈추지 않고 루프로 들어간다.

#define STEP_MS    300

static const uint8_t patterns[] = {
  0xFF, 0x00,
  0xFE, 0xFD, 0xFB, 0xF7,

  0xAA, 0x55
};
  1. HAL 인자는 7비트 주소를 1비트 왼쪽으로 민 값이다.
  2. 액티브 Low이므로 0인 비트의 LED가 켜진다. 0xFE는 P0만 켜고, 0x7F는 P7만 켠다. 0xFE → 0x7F는 "켜진 LED 하나가 P0에서 P7로 이동"이다.
  3. 0xAA = 1010 1010은 P0, P2, P4, P6이 켜지고, 0x55는 그 반대이다.

{

}

static HAL_StatusTypeDef pcf_read(uint8_t *value)
{

}
  1. 둘 다 같은 PCF_ADDR(0x4E)를 넘긴다. R/W 비트는 HAL이 붙인다(쓰기 0x4E, 읽기 0x4F).
  2. 크기 1, 타임아웃 10 ms. 정상 전송은 0.2 ms 정도라 넉넉하다.
  3. 03_PCF8574_LCD의 라이브러리와 달리 반환값을 돌려준다. 호출한 쪽이 NACK를 알 수 있다.
main.c — 출력 형식 (USER CODE 0)
static void print_state(uint8_t w, uint8_t r)
{
  char bits[9], led[9];
  for (int i = 0; i < 8; i++) {
    uint8_t b = (w >> (7 - i)) & 1u;
    bits[i] = b ? '1' : '0';
    led[i]  = b ? '-' : '*';
  }
  bits[8] = led[8] = '\0';
  printf("W=0x%02X R=0x%02X  P7..P0=%s  LED=%s%s\n",
         w, r, bits, led, (w == r) ? "" :
         "  <- R differs (pin pulled low externally?)");
}
  1. i = 0이 비트 7(P7)이므로 문자열 왼쪽이 P7, 오른쪽이 P0이다.
  2. P7..P0=와 LED=는 모두 쓴 값 w로 만든다. 읽은 값 r은 16진수와 비교에만 쓴다.
  3. 그래서 외부에서 Low로 누른 핀은 실제로 LED가 켜져도 LED=에는 -로 나온다. 대신 줄 끝의 <- R differs가 차이를 알려 준다(시뮬레이터 ③ 단계).

  1. 시작 확인은 실패해도 멈추지 않는다. 배선을 고치는 동안 루프의 write NACK 줄이 계속 상황을 알려 준다.
  2. 쓰기가 실패하면 읽기는 하지 않는다. 쓰기는 성공했는데 읽기가 실패하는 경우는 드물다.
  3. err는 HAL_I2C_GetError()이다. 주소 NACK이면 0x00000004(HAL_I2C_ERROR_AF).
  4. 한 바퀴(12개)가 끝나면 ----를 찍는다. LD2(PA5)는 패턴마다 토글되어 프로그램이 살아 있음을 보여 준다.

ISR과 HAL 콜백

I2C는 블로킹 폴링으로만 쓰므로 I2C 인터럽트(ISR)와 I2C 콜백(HAL_I2C_MasterTxCpltCallback 등)은 없다. 이 프로젝트에서 실제로 켜진 인터럽트는 둘이다.

ISR: SysTick_Handlerstm32f1xx_it.c · 1 ms마다

HAL_IncTick()으로 틱을 올린다. HAL_Delay(300)과 HAL I2C 함수의 타임아웃(BUSY 25 ms, 인자 10 ms)이 모두 이 값을 본다.

ISR: EXTI15_10_IRQHandlerstm32f1xx_it.c · B1(PC13) 상승 에지

CubeMX 보드 기본값으로 켜져 있다. HAL_GPIO_EXTI_IRQHandler(B1_Pin)이 EXTI_PR.PR13을 지우고 콜백을 부른다.

HAL 콜백: HAL_GPIO_EXTI_Callback재정의 안 함 → weak 빈 함수

B1을 누르면 ISR까지는 들어가지만 아무 일도 하지 않는다. 버튼으로 패턴을 바꾸려면 USER CODE 4에 콜백을 정의하고 플래그만 세운 뒤, I2C 전송은 메인 루프에서 한다.

7. 실험

실험 A. 기본 출력 확인

시리얼 터미널(115200 bps)을 열고 리셋한다. 기대 결과: 02_PCF8574_Output: PCF8574 @ 0x4E (7bit 0x27), ACK: PCF8574 found가 나오고, 300 ms마다 W=0xFF R=0xFF P7..P0=11111111 LED=--------부터 W=0x55 R=0x55 … LED=*-*-*-*-까지 12줄 뒤 ----가 반복된다. 실제 LED는 LED= 표시와 같은 위치가 켜진다(P7이 왼쪽). 모든 줄에서 W와 R이 같다.

실험 B. 주소 핀 하나를 바꾼다

전원을 끄고 A0를 GND로 옮긴 뒤 다시 켠다. 칩 주소는 0100 110 = 0x26이 된다. 기대 결과: NACK: no response. … 뒤에 write NACK/timeout (err=0x00000004)가 300 ms마다 나온다. LED는 전원 직후 상태(0xFF, 모두 꺼짐)에서 움직이지 않는다. PCF_ADDR를 (0x26 << 1)로 고치면 다시 동작한다. 시뮬레이터 ①에서 먼저 확인할 수 있다.

실험 C. 1을 쓴 핀을 외부에서 누른다

P0를 점퍼선(또는 버튼)으로 GND에 연결한 채 루프를 지켜본다. 1을 쓴 핀은 대부분의 시간 동안 약한 풀업 전류만 흐르므로 GND로 누르는 입력으로 쓸 수 있다(정확한 전류, 1을 쓰는 순간의 동작은 데이터시트를 확인한다). 기대 결과: P0의 LED가 계속 켜져 있다. W의 비트 0이 1인 줄(0xFF, 0xFD, … , 0x55)은 R의 비트 0이 0이 되어 R = W − 1이 되고, 줄 끝에 <- R differs (pin pulled low externally?)가 붙는다. 예: W=0xFF R=0xFE … LED=-------- <- R differs. 비트 0이 원래 0인 줄(0x00, 0xFE, 0xAA)은 W = R이다. LED= 표시가 실제 LED와 다르다는 점(코드가 w로 만든다)도 확인한다.

주의

외부에서 핀을 High(VCC)로 직접 연결하지 않는다. 그 핀에 0을 쓰는 순간 칩의 강한 Low와 VCC가 정면으로 맞서 큰 전류가 흐른다. 입력은 "GND로 누르는" 방향으로만 만든다.

실험 D. 핀을 입력으로 쓴다

루프를 고쳐 처음에 pcf_write(0xF0)을 한 번만 쓰고, 그 뒤로는 pcf_read(&r)만 반복해 값이 바뀔 때 출력한다(USER CODE 3 안에서 고친다). P7~P4에는 GND로 누르는 버튼을, P3~P0에는 LED를 단다. 기대 결과: 버튼을 누르지 않으면 R=0xF0, P4 버튼을 누르면 R=0xE0, P7을 누르면 R=0x70이다. 하위 니블은 0을 써 두었으므로 LED 4개가 켜지고 R의 하위 4비트는 항상 0이다. 한 칩에서 상위 4개는 입력, 하위 4개는 출력으로 섞어 쓴 셈이다.

실험 E. LED를 거꾸로 단다

LED 하나를 Px → LED 애노드, 캐소드 → 저항 → GND로 바꿔 단다. 기대 결과: 이 LED는 비트 1일 때 켜져야 하지만 약한 풀업 전류뿐이라 매우 어둡거나 보이지 않는다. 비트 0일 때는 꺼진다. 같은 위치의 액티브 Low LED와 밝기를 비교하고, 2절의 "0은 강하다, 1은 약하다"를 직접 확인한다. Proteus에서는 시뮬레이션 모델에 따라 결과가 실제와 다를 수 있으므로 실제 보드로 확인한다.

9. 확인 문제

문제 1. A2 = 1, A1 = 0, A0 = 1인 PCF8574의 7비트 주소와 HAL 인자는?

0100 101 = 0x25. HAL 인자는 0x25 << 1 = 0x4A이고, 읽기 주소 바이트는 0x4B이다.

문제 2. P3와 P5의 LED만 켜려면 어떤 바이트를 써야 하는가?

액티브 Low이므로 비트 3과 5만 0이다. 1101 0111 = 0xD7.

문제 3. W = 0x0F를 쓰고, P0와 P6을 외부에서 GND로 눌렀다. 읽은 값 R과 UART 줄의 LED= 표시는?

P6은 이미 0을 썼으므로 변화가 없고, P0는 1을 썼으므로 0이 된다. R = 0x0E. LED=는 W로 만들므로 ****----이고 줄 끝에 <- R differs가 붙는다. 실제로는 P0 LED도 켜져 있다.

문제 4. 1바이트 읽기에서 마스터가 마지막에 ACK가 아니라 NACK를 내는 이유와, 이를 위해 HAL이 건드리는 비트는?

NACK는 "이 바이트가 마지막"이라는 표시이다. ACK를 내면 슬레이브는 다음 바이트를 보내려 한다. HAL은 ADDR을 지우기 전에 CR1.ACK = 0을 만들고, ADDR을 지운 뒤 CR1.STOP = 1을 쓴다.

문제 5. PCF8574 핀을 입력으로 쓰기 전에 왜 1을 써야 하는가?

0을 쓴 핀은 칩이 강하게 Low로 잡고 있어 외부 신호와 관계없이 항상 0으로 읽힌다. 1을 쓴 핀은 약한 풀업만 걸려 있어 외부가 Low로 누르면 0, 가만두면 1로 읽힌다.

문제 6. PCF_ADDR를 실수로 0x27로 정의하면 버스에는 어떤 주소 바이트가 나가고, UART에는 무엇이 찍히는가?

HAL이 최하위 비트만 지워 0x26을 보낸다. 슬레이브는 7비트 0x13으로 읽어 응답하지 않는다. NACK: no response … 뒤 write NACK/timeout (err=0x00000004)가 반복된다.

문제 7. 이 예제 루프 한 번의 I2C 버스 시간은 대략 얼마인가?

쓰기 프레임 = 주소 + 데이터 2바이트 × 9비트 + START/STOP ≈ 20비트 = 0.2 ms, 읽기도 같다. 합 약 0.4 ms(HAL 처리 시간 제외)이다. HAL_Delay(300)에 비하면 무시할 만하다.

정리

  • PCF8574는 레지스터 없는 8비트 포트이다. 쓰기 프레임의 데이터 바이트가 곧 P7~P0이고, 데이터 ACK 직후 바뀐다.
  • 주소는 0100 A2A1A0. HAL 인자는 7비트 주소 << 1(0x4E)이고 R/W는 HAL이 붙인다.
  • 준양방향 핀: 0은 강한 Low, 1은 약 100 µA의 약한 풀업. 그래서 LED는 액티브 Low로 단다.
  • 읽기 값은 실제 핀 레벨이다. 1을 써 둔 핀은 입력으로 쓸 수 있다.
  • HAL 폴링 함수는 START → SB → ADDR → TxE/BTF → STOP(쓰기), ACK = 0 → ADDR → STOP → RxNE(1바이트 읽기)를 대신 처리한다.
다음 예제로

03_PCF8574_LCD는 같은 바이트의 비트에 이름을 붙인다: P0 = RS, P1 = RW, P2 = E, P3 = 백라이트, P4~P7 = LCD D4~D7. E 비트만 1 → 0으로 바뀌는 바이트 두 개를 이어 보내면 LCD가 니블 하나를 읽는다. 이 예제설명의 "바이트 하나 = 핀 8개"가 그대로 LCD 구동 원리가 된다.
