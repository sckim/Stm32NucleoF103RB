PCF8574: 선 두 개로 문자 LCD를 움직인다

16x2 문자 LCD(HD44780)는 4비트 모드에서도 핀이 6개 이상 필요하다. I2C 확장 IC PCF8574를 붙이면 SCL과 SDA 두 선으로 줄어든다. 대신 글자 하나를 보내려면 I2C 바이트 4개가 필요하다. 이 교안은 I2C 프레임, PCF8574의 핀 배치, HD44780의 4비트 전송을 차례로 연결하고, I2C1을 HAL 폴링 방식으로 쓰는 03_PCF8574_LCD 예제를 해석한다.

1. 문제: LCD 하나에 핀이 너무 많이 든다

HD44780 계열 문자 LCD는 병렬 인터페이스이다. 8비트 모드는 데이터 8개 + RS + E (+ RW) 핀을, 4비트 모드도 D4~D7 + RS + E = 최소 6핀을 쓴다. 백라이트까지 제어하면 7핀이다. Nucleo의 Arduino 헤더에서 이만큼을 LCD에 내주면 다른 장치를 붙일 핀이 부족하다.

LCD 백팩 모듈은 이 문제를 I2C 입출력 확장 IC로 푼다. MCU는 I2C로 1바이트를 보내고, PCF8574는 그 바이트를 8개 출력 핀 P0~P7에 그대로 내보낸다. 이 8개 핀이 LCD의 RS, RW, E, 백라이트, D4~D7에 연결되어 있다. MCU 쪽은 SCL, SDA 두 선이면 된다. 다른 I2C 장치와 같은 버스를 공유할 수도 있다.

  • I2C 프레임(START, 7비트 주소 + R/W, ACK, 데이터, STOP)을 읽을 수 있다.
  • HAL 주소 인자가 7비트 주소를 왼쪽으로 1비트 민 값(0x27 << 1 = 0x4E)임을 설명할 수 있다.
  • PCF8574 바이트 하나가 LCD 핀 8개의 상태임을 이해하고, 글자 하나가 I2C 바이트 4개가 되는 이유를 설명할 수 있다.
  • I2C1 레지스터(CR1, CR2, CCR, TRISE, SR1, SR2)가 100 kHz 마스터 송신을 어떻게 만드는지 안다.
이 예제의 위치

04_I2C_Communication 그룹의 세 번째 예제이다. 앞 예제 02_PCF8574_Output과 같은 PCF8574, 같은 핀(PB8/PB9), 같은 주소(0x4E)를 쓴다. printf를 USART2로 보내는 방법은 02_USART/01_USART_printf에서 그대로 가져왔다. 시작할 때 돌리는 주소 스캐너는 다음 예제 01_I2C_Scan에서 독립 예제로 다듬어진다. 레지스터가 있는 센서를 읽는 방법(HAL_I2C_Mem_Read)은 04_I2C_MPU6050_c에서 다룬다. PCF8574는 내부 레지스터가 없는 가장 단순한 I2C 장치라서 출발점으로 알맞다.

02_PCF8574_Output에서 이어지는 점

02_PCF8574_Output은 "바이트 하나 쓰기 = 핀 P7~P0 상태"만 확인했다. 이 예제는 같은 바이트의 비트에 LCD 신호 이름을 붙인다: P0 = RS, P1 = RW, P2 = E, P3 = 백라이트, P4~P7 = D4~D7. E 비트만 1 → 0으로 바뀌는 바이트 두 개를 이어 보내면 LCD가 D7~D4 니블 하나를 읽는다. 8비트 명령·문자 하나는 니블 2개, 즉 I2C 데이터 4바이트이다. 01에서 LED가 데이터 ACK 직후 바뀌던 것처럼, 여기서는 E 핀이 바이트마다 바뀐다.

핀 주의

이 예제는 I2C1을 리맵해서 SCL = PB8(Arduino D15), SDA = PB9(Arduino D14)를 쓴다(AFIO_MAPR.I2C1_REMAP = 1). 그룹의 다른 예제는 기본 핀 PB6/PB7을 쓰므로 배선이 다르다. 근거는 stm32f1xx_hal_msp.c의 HAL_I2C_MspInit()과 PCF8574.ioc이다.

회로 연결도

실제로 꽂는 선은 네 가닥(VCC, GND, SCL, SDA)뿐이다. 나머지 연결은 LCD 뒤에 납땜된 백팩 모듈 안에 이미 되어 있다. 아래 그림은 그 내부까지 회로도 기호로 펼친 것이다.

2. I2C 프레임: 주소 바이트, ACK, 데이터

I2C 버스의 두 선은 오픈 드레인이다. 어떤 장치든 선을 Low로 끌어내릴 수만 있고, High는 풀업 저항이 만든다. 그래서 여러 장치가 같은 선을 써도 충돌하지 않는다. 풀업이 없으면 선이 High로 올라가지 못해 통신이 되지 않는다. 대부분의 LCD 백팩에는 풀업 저항이 이미 달려 있다.

  • START: SCL이 High인 동안 SDA가 High → Low. 버스 사용 시작.
  • STOP: SCL이 High인 동안 SDA가 Low → High. 버스 반납.
  • 데이터 비트: SDA는 SCL이 Low일 때만 바뀌고, SCL이 High일 때 읽힌다. MSB부터 보낸다.
  • ACK: 바이트 8비트 뒤 9번째 클럭에서 받는 쪽이 SDA를 Low로 끌면 ACK, 놓아 두어 High이면 NACK이다.

그림 1. 마스터 쓰기 프레임. 주소 7비트와 R/W 비트가 합쳐 한 바이트가 된다. 이 바이트를 통째로 HAL에 넘기기 때문에 HAL 인자는 7비트 주소의 2배이다.

주소: 7비트와 "8비트 표기"

데이터시트가 말하는 주소는 7비트이다. PCF8574는 상위 4비트가 0100으로 고정이고 하위 3비트는 A2, A1, A0 핀으로 정한다. PCF8574A는 상위 4비트가 0111이다. LCD 백팩은 보통 A2~A0이 풀업되어 있어 모두 1이다.

칩7비트 주소 범위A2~A0 = 111일 때HAL 인자 (<<1)
PCF85740x20 ~ 0x270x270x4E (이 예제)
PCF8574A0x38 ~ 0x3F0x3F0x7E

HAL 함수(HAL_I2C_Master_Transmit, HAL_I2C_IsDeviceReady 등)는 주소 인자를 주소 바이트 그대로 받는다. HAL 내부 매크로 I2C_7BIT_ADD_WRITE(addr)는 addr & ~0x01, 즉 최하위 비트(R/W)만 0으로 만들어 DR에 쓴다. 시프트는 해 주지 않는다. 그래서 0x27을 그대로 넘기면 버스에는 0x26이 나가고, 슬레이브는 이를 7비트 주소 0x13으로 읽는다. 아무도 응답하지 않는다(NACK).

HAL 인자 = 7비트 주소 << 1 = 0x27 << 1 = 0x4E 버스 주소 바이트 = 0x4E | R/W(0) = 0x4E

속도

이 예제는 표준 모드 100 kHz(ClockSpeed = 100000)를 쓴다. PCF8574/PCF8574A 데이터시트의 최대 SCL 클럭도 100 kHz이므로 더 올리면 안 된다. 1비트는 10 µs, ACK를 포함한 1바이트는 9비트 = 90 µs이다.

3. PCF8574와 HD44780: 바이트 하나 = 핀 8개

PCF8574는 내부 레지스터 주소가 없다. 주소 바이트 다음에 오는 데이터 바이트가 곧바로 출력 포트 P7~P0이 된다. 데이터 바이트의 ACK가 끝나는 시점에 포트 값이 바뀐다. 한 번의 START~STOP 안에서 바이트를 여러 개 보내면 바이트마다 포트가 갱신된다. 이 성질 덕분에 바이트 4개를 한 번에 보내 E 핀을 High → Low로 흔들 수 있다.

출력은 준양방향(quasi-bidirectional)이다. 0을 쓰면 강하게 Low로 끌고, 1을 쓰면 약한 풀업으로 High를 낸다. 전원 투입 직후 포트는 모두 1(High)이다. LCD를 구동하는 출력 용도에는 이 정도로 충분하다.

글자 하나 = I2C 바이트 4개

LCD는 4비트 모드이므로 8비트 값을 상위 니블, 하위 니블 두 번에 나눠 받는다. 니블마다 E를 1로 올렸다가 0으로 내려야 한다. 그래서 니블 2개 × E 상태 2개 = 바이트 4개가 된다. 문자 'S'(0x53)를 예로 든다.

명령은 RS = 0이므로 0x0C(E=1)와 0x08(E=0)을 OR한다. 이 4바이트가 HAL_I2C_Master_Transmit() 한 번으로 나간다. 프레임 하나는 START + 주소 9비트 + 데이터 4 × 9비트 + STOP으로, 100 kHz에서 SCL 45주기, 약 0.45 ms이다(HAL 처리 시간 제외 추정치). 바이트 사이 간격은 90 µs이므로 E의 High 구간이 LCD가 요구하는 최소 펄스 폭(수백 ns)보다 훨씬 길다. 별도 지연이 필요 없다.

2줄 모드에서 DDRAM은 1행이 0x00~0x27(40칸), 2행이 0x40~0x67(40칸)이다. 16x2 LCD는 각 행의 앞 16칸(0x00~0x0F, 0x40~0x4F)만 보여 준다. 나머지 24칸은 메모리에는 있지만 화면에 나오지 않는다.

이 예제에서 실제로 생기는 일

1행 문자열 "STM32 with C Code"는 17자이다. 17번째 글자 'e'는 DDRAM 0x10에 들어가므로 화면에는 STM32 with C Cod까지만 보인다. 시뮬레이터에서 직접 확인한다. 16자 이하로 줄이거나 화면 이동 명령(0x18)을 쓰면 해결된다.

초기화 순서: 데이터시트, 라이브러리, 그리고 lcd_init_4bit()

전원 직후 HD44780은 8비트 모드이다. 이때는 E 하강 에지 한 번이 곧 명령 하나이다(백팩에 연결되지 않은 D3~D0도 함께 읽힌다). 4비트 인터페이스로 바꾸는 데이터시트 절차(HD44780 Figure 24)는 니블 하나씩 보내는 것이다: 40 ms 이상 대기 → 0x3 → 4.1 ms 이상 → 0x3 → 100 µs 이상 → 0x3 → 0x2(4비트 전환). 그 뒤부터 명령 하나는 니블 2개이다: 0x28, 0x08, 0x01, 0x06, 0x0C.

사용한 라이브러리의 lcd_init()은 0x30, 0x30, 0x30, 0x20을 모두 lcd_send_cmd()로 보낸다. 이 함수는 항상 니블 두 개(상위, 하위)를 보내므로 E 하강 에지가 명령마다 두 번 나간다. 결과를 니블 단위로 따라가면 다음과 같다.

라이브러리 호출E↓마다 나가는 니블LCD 상태LCD가 실행하는 것
lcd_send_cmd(0x30) × 33, 0, 3, 0, 3, 08비트니블마다 명령 하나(총 6개). 0x3?는 8비트 Function set, 0x0?의 효과는 D3~D0 레벨에 달려 있어 여기서 정하지 않는다
lcd_send_cmd(0x20)2 | 08비트 → 4비트2에서 4비트로 바뀐다. 남은 0은 4비트 모드의 상위 니블로 대기한다
lcd_send_cmd(0x28)2, 84비트, 한 니블 밀림(0,2) = 0x02 Return home. 8은 다음 상위 니블로 대기
lcd_send_cmd(0x08)0, 8밀림(8,0) = 0x80 DDRAM 주소 0
lcd_send_cmd(0x01)0, 1밀림(8,0) = 0x80

결국 0x28(2줄)과 0x0C(표시 ON)는 한 번도 실행되지 않는다. HD44780은 내부 리셋 직후 표시 OFF 상태이므로 화면이 꺼진 채로 남는다. 이후 lcd_clear(), lcd_gotoxy(), lcd_puts()도 계속 한 니블씩 어긋난 짝으로 해석되고, 이 예제의 호출 순서에서는 그 짝이 0x0C~0x0F 명령이 되는 경우가 없다. Proteus의 LM016L 모델에서 실제로 화면에 아무것도 나오지 않았다. 실제 LCD 모듈에서 같은 증상이 나는지는 이 교안에서 확인하지 않았다(D3~D0 처리, 전원 투입 순서에 따라 다를 수 있다).

수정: main.c의 lcd_init_4bit()

main.c는 라이브러리 lcd_init() 대신 USER CODE 0 영역의 lcd_init_4bit()를 부른다. 초기화 니블 3, 3, 3, 2는 lcd_write_nibble()로 니블 하나씩(I2C 바이트 2개: E = 1, E = 0) 보내고, 4비트 모드가 된 뒤에만 라이브러리 lcd_send_cmd()로 0x28, 0x08, 0x01, 0x06, 0x0C를 보낸다. 니블 짝이 처음부터 맞으므로 이후 라이브러리 함수(lcd_clear, lcd_gotoxy, lcd_puts)를 그대로 쓸 수 있다. 이 수정으로 Proteus LM016L에 글자가 나타났다. 4절 시뮬레이터에서 두 초기화를 바꿔 가며 비교할 수 있다.

4. 직접 만져 보기

세 부분으로 되어 있다. ① 주소 설정이 ACK를 받는지, ② 한 번의 전송이 버스에서 어떤 파형이 되는지, ③ main.c의 호출 순서대로 LCD 화면과 DDRAM이 어떻게 바뀌는지를 본다. 세 부분은 연결되어 있다. ①에서 주소를 틀리게 하면 ③의 전송이 NACK로 끝나고 화면이 바뀌지 않는다.

  1. 기본값(PCF8574, A2~A0 = 111, HAL 인자 0x4E)에서 ACK가 나오는지 확인한다.
  2. HAL 인자를 0x27 (시프트 누락)로 바꾸고 버스에 나가는 주소 바이트가 0x26이 되는 것을 본다.
  3. HAL 인자를 0x4E로 되돌리고 main.c 끝까지를 누른다. 1행 끝의 e가 화면 밖 DDRAM 0x10에 들어가는 것을 본다.
  4. 처음부터 → 다음 전송 1개를 여러 번 눌러 바이트 4개와 E 하강 에지를 하나씩 본다.
  5. 문자를 직접 입력해 4바이트로 나뉘는 모습을 확인한다.
  6. ③의 초기화 함수를 lcd_init() — 라이브러리 원본으로 바꾸고 main.c 끝까지를 누른다. 로그에서 니블 짝이 어긋나 화면이 꺼진 채로 남는 것을 본다(3절 끝).

6. HAL이 대신 해 주는 일

초기화

  1. 1
    HAL_I2C_Init(&hi2c1) → HAL_I2C_MspInit()GPIOB 클럭, PB8/PB9를 AF 오픈 드레인으로, __HAL_AFIO_REMAP_I2C1_ENABLE()(AFIO_MAPR.I2C1_REMAP = 1), I2C1 클럭 허용
  2. 2
    소프트웨어 리셋PE = 0으로 끈 뒤 CR1.SWRST를 1 → 0. 이전 상태를 지운다
  3. 3
    타이밍HAL_RCC_GetPCLK1Freq()로 32 MHz를 얻어 CR2.FREQ = 32, TRISE = 33, CCR = 160을 계산해 쓴다
  4. 4
    CR1, OAR1, OAR2, PEENGC/NOSTRETCH 설정, 자기 주소 설정, 마지막에 __HAL_I2C_ENABLE()(PE = 1)

HAL_I2C_Master_Transmit(hi2c, 0x4E, data_t, 4, 100)

  1. 1
    BUSY 대기SR2.BUSY가 0이 될 때까지 최대 25 ms(I2C_TIMEOUT_BUSY_FLAG). 넘으면 HAL_BUSY
  2. 2
    START → SB → 주소CR1.POS = 0, CR1.START = 1. SB(EV5)를 기다려 DR = 0x4E & ~1
  3. 3
    ADDR 또는 AFADDR(EV6)이면 SR1·SR2를 읽어 지운다. AF가 먼저 오면 STOP을 내고 HAL_ERROR(ErrorCode = AF)
  4. 4
    바이트마다 TxE → DR → BTFTxE를 기다려 DR에 쓰고, BTF가 설 때까지 기다린다. 4번 반복
  5. 5
    STOPCR1.STOP = 1, 상태를 READY로 되돌리고 HAL_OK

HAL_I2C_IsDeviceReady(hi2c, addr, 1, 10)

START와 주소 바이트만 보내고 데이터는 보내지 않는다. ADDR이 서면 STOP을 내고 HAL_OK, AF가 서면 AF를 지우고 STOP을 낸 뒤 다음 시도로 간다. 시도 횟수(Trials)가 1이므로 실패하면 바로 HAL_ERROR를 돌려준다. 장치가 없는 주소는 9번째 클럭에서 바로 NACK가 나오므로 타임아웃 10 ms까지 기다리지 않는다.

반환값을 보지 않는 코드

lcd_send_cmd(), lcd_send_data()는 HAL_I2C_Master_Transmit()의 반환값을 버린다. 주소가 틀렸거나 LCD가 빠져 있어도 프로그램은 아무 일 없다는 듯 계속 진행한다. 화면이 비어 있으면 스캐너 출력과 hi2c1.ErrorCode(HAL_I2C_ERROR_AF = NACK)를 먼저 본다.

static void lcd_write_nibble(I2C_LCD_HandleTypeDef *lcd,
                             uint8_t nibble)
{
  uint8_t d = (uint8_t)(nibble << 4);
  uint8_t buf[2] = {
    (uint8_t)(d | 0x0C),  // E=1, RS=0, 백라이트=1
    (uint8_t)(d | 0x08)   // E=0 -> 하강 에지에서 D7~D4
  };
  HAL_I2C_Master_Transmit(lcd->hi2c, lcd->address,
                          buf, 2, 100);
}

static void lcd_init_4bit(I2C_LCD_HandleTypeDef *lcd)
{
  HAL_Delay(50);
  lcd_write_nibble(lcd, 0x3);  HAL_Delay(5);
  lcd_write_nibble(lcd, 0x3);  HAL_Delay(1);
  lcd_write_nibble(lcd, 0x3);  HAL_Delay(1);
  lcd_write_nibble(lcd, 0x2);  HAL_Delay(1);  // 4비트

  lcd_send_cmd(lcd, 0x28);  // 4비트, 2줄, 5x8
  lcd_send_cmd(lcd, 0x08);  // 표시 OFF
  lcd_send_cmd(lcd, 0x01);  // 화면 지우기
  lcd_send_cmd(lcd, 0x06);  // Entry mode
  lcd_send_cmd(lcd, 0x0C);  // 표시 ON
}  // (명령 사이 HAL_Delay 생략)
  1. lcd_write_nibble()은 니블 하나 = I2C 데이터 바이트 2개이다. 니블 3이면 0x3C, 0x38, 니블 2이면 0x2C, 0x28이다. E 하강 에지가 정확히 한 번 나간다.
  2. 8비트 모드에서는 이 E 하강 에지 하나가 명령 하나이다. 3, 3, 3으로 어떤 상태에서든 8비트 모드로 맞춘 뒤 2로 4비트 모드에 들어간다.
  3. 그 뒤에는 라이브러리 lcd_send_cmd()(니블 2개)를 그대로 쓴다. 짝이 처음부터 맞으므로 0x28과 0x0C가 제대로 실행된다.
  4. 사용자 코드이므로 CubeMX 재생성에도 지워지지 않도록 /* USER CODE BEGIN 0 */ 안에 있다. 라이브러리 파일(.pio/libdeps)은 고치지 않았다.
.pio/libdeps/…/I2C-LCD-STM32/i2c_lcd.c — 4바이트 만들기 (외부 라이브러리)
void lcd_send_data(I2C_LCD_HandleTypeDef *lcd, char data)
{
  char upper_nibble, lower_nibble;
  uint8_t data_t[4];
  upper_nibble = (data & 0xF0);
  lower_nibble = ((data << 4) & 0xF0);
  data_t[0] = upper_nibble | 0x0D;  // en=1, rs=1
  data_t[1] = upper_nibble | 0x09;  // en=0, rs=1
  data_t[2] = lower_nibble | 0x0D;  // en=1, rs=1
  data_t[3] = lower_nibble | 0x09;  // en=0, rs=1
  HAL_I2C_Master_Transmit(lcd->hi2c, lcd->address,
                          data_t, 4, 100);
}
  1. 상위·하위 니블을 P7~P4 자리에 놓는다.
  2. 0x0D = BL | E | RS, 0x09 = BL | RS. 백라이트 비트가 항상 1이라 "백라이트 자동 ON"이 된다.
  3. lcd_send_cmd()는 같은 구조에 0x0C/0x08(RS = 0)을 쓴다.
  4. 반환값을 검사하지 않고, LCD의 busy 플래그도 읽지 않는다(RW = 0 고정). I2C 전송이 느리다는 점과 HAL_Delay에 기대어 타이밍을 맞춘다.
i2c_lcd.c — lcd_clear()
void lcd_clear(I2C_LCD_HandleTypeDef *lcd)
{
  lcd_send_cmd(lcd, 0x80);   // DDRAM 0x00
  for (int i = 0; i < 80; i++)
    lcd_send_data(lcd, ' ');
}
  1. Clear 명령(0x01) 대신 공백 80개를 쓴다. 2줄 모드 DDRAM 80칸(0x00~0x27, 0x40~0x67)을 모두 덮는다.
  2. 전송 81번 × 약 0.45 ms ≈ 37 ms(버스 시간만 추정). 0x01 한 번(1.52 ms 실행)보다 훨씬 느리다. 대신 실행 시간이 긴 명령 뒤에 지연을 넣을 필요가 없다.

ISR과 HAL 콜백

I2C는 블로킹 폴링으로만 쓰므로 I2C 인터럽트와 I2C 콜백은 없다. HAL_I2C_MasterTxCpltCallback() 같은 콜백은 _IT/_DMA 함수를 쓸 때만 호출된다(05_I2C_MPU6050_DMA_c). 이 프로젝트에서 실제로 켜진 인터럽트는 둘이다.

ISR: SysTick_Handlerstm32f1xx_it.c · 1 ms마다

HAL_IncTick()으로 uwTick을 올린다. HAL_Delay()와 HAL I2C 함수의 타임아웃(25 ms BUSY 대기, Timeout 100 ms 등)이 모두 이 값을 본다. 인터럽트가 막히면 I2C 함수가 영원히 기다릴 수 있다.

ISR: EXTI15_10_IRQHandlerstm32f1xx_it.c · B1(PC13) 상승 에지

CubeMX 보드 기본값으로 켜져 있다. HAL_GPIO_EXTI_IRQHandler(B1_Pin)이 EXTI_PR.PR13을 지우고 콜백을 부른다.

HAL 콜백: HAL_GPIO_EXTI_Callback재정의 안 함 → weak 빈 함수

이 예제는 콜백을 만들지 않았다. B1을 누르면 ISR까지는 들어가지만 아무 일도 하지 않는다. 버튼으로 LCD 내용을 바꾸고 싶다면 USER CODE 4 영역에 이 콜백을 정의한다(ISR 안에서 I2C 블로킹 전송은 피하고, 플래그만 세운다).

8. 실험

실험 A. 스캐너로 주소 확인

시리얼 터미널(115200 bps)을 연 채로 리셋한다. 기대 결과: I2C Scan Start → Found: 0x4E (7bit: 0x27) → I2C Scan Done. 백팩의 A0 점퍼를 GND로 납땜(또는 단락)하면 0x4C (7bit: 0x26)으로 바뀐다. 0x7E (7bit: 0x3F)가 나오면 PCF8574A 모듈이므로 lcd1.address = 0x7E로 고친다.

실험 B. 시프트를 빠뜨린다

lcd1.address = 0x27;로 바꾸고 lcd_puts() 뒤에 printf("err=0x%lX\n", hi2c1.ErrorCode);를 넣는다. 기대 결과: LCD에 아무것도 나오지 않고(백라이트 상태는 이전 그대로), err=0x4(HAL_I2C_ERROR_AF)가 출력된다. 로직 분석기로 보면 주소 바이트가 0x26이고 9번째 클럭에서 SDA가 High(NACK)이다.

실험 C. 17번째 글자

1행을 그대로 두고 lcd_gotoxy() 없이 lcd_send_cmd(&lcd1, 0x18);(화면 왼쪽 이동)을 1초 간격으로 반복한다. 기대 결과: 두 행이 함께 한 칸씩 왼쪽으로 흐르고, 숨어 있던 e가 나타난다. 원래 의도대로 고치려면 문자열을 16자 이하(예: "STM32 w/ C Code")로 줄인다.

실험 D. 버스 시간 측정

lcd_clear() 앞뒤에서 HAL_GetTick()을 읽어 차이를 출력한다. 기대 결과: 버스 시간만 약 37 ms(81 전송 × 45 SCL 주기)이고, HAL 처리 시간이 더해져 그보다 약간 길다. 로직 분석기로 SCL 주기가 10 µs 근처인지도 본다. 측정값을 이 교안의 추정치와 비교해 HAL 오버헤드가 얼마인지 기록한다.

실험 E. 초기화 니블: 라이브러리 lcd_init()과 lcd_init_4bit() 비교

로직 분석기를 SDA/SCL에 연결하고 I2C 디코더를 켠 채 전원을 새로 넣는다. 초기화 구간의 데이터 바이트를 표로 옮겨 E(P2)의 하강 에지마다 D7~D4(P7~P4) 값을 적는다. 먼저 현재 코드(lcd_init_4bit)로 찍고, 다음에 USER CODE 2의 호출을 lcd_init(&lcd1);로 잠시 바꿔 다시 찍는다.

실험 F. 백라이트 끄기

라이브러리를 고치지 않고 uint8_t b = 0x00; HAL_I2C_Master_Transmit(&hi2c1, 0x4E, &b, 1, 100);을 보낸다. 기대 결과: P3 = 0이 되어 백라이트가 꺼진다. 다만 다음 lcd_send_* 호출이 BL = 1을 다시 쓰므로 곧 다시 켜진다. 바이트 하나가 곧 핀 8개라는 점을 확인하는 실험이다.

10. 확인 문제

문제 1. 7비트 주소 0x3F인 PCF8574A에 쓰려면 HAL 인자는 얼마인가? 0x3F를 그대로 넘기면 버스에 어떤 주소 바이트가 나가는가?

HAL 인자는 0x3F << 1 = 0x7E이다. 0x3F를 그대로 넘기면 HAL이 최하위 비트만 지워 0x3E를 보낸다. 슬레이브는 이를 7비트 0x1F로 읽으므로 NACK가 난다.

문제 2. 문자 'A'(0x41)를 lcd_send_data()로 보낼 때 data_t[0..3]은?

상위 니블 0x40, 하위 니블 0x10. 0x4D, 0x49, 0x1D, 0x19이다. 0x0D = BL|E|RS, 0x09 = BL|RS.

문제 3. PCLK1이 32 MHz이고 100 kHz 표준 모드일 때 I2C1_CR2.FREQ, CCR, TRISE 값은?

FREQ = 32, CCR = 32 MHz / (2 × 100 kHz) = 160, TRISE = 1000 ns / 31.25 ns + 1 = 33이다.

문제 4. lcd_puts()로 15자 문자열을 보내는 데 I2C 버스 시간은 대략 얼마인가?

글자마다 전송 1번 = 주소 1 + 데이터 4 = 5바이트 = 45 SCL 주기 = 약 0.45 ms. 15자이면 약 6.8 ms이다(HAL 처리 시간 제외).

문제 5. ADDR 플래그는 어떻게 지워지는가? HAL에서는 어느 매크로가 이 일을 하는가?

SR1을 읽은 다음 SR2를 읽으면 지워진다(RM0008 EV6). HAL은 __HAL_I2C_CLEAR_ADDRFLAG()로 SR1, SR2를 차례로 읽는다.

문제 6. B1 버튼을 누르면 무엇이 실행되는가? 왜 화면은 바뀌지 않는가?

EXTI15_10_IRQHandler(ISR) → HAL_GPIO_EXTI_IRQHandler(B1_Pin) → HAL_GPIO_EXTI_Callback이 실행된다. 콜백을 재정의하지 않아 weak 빈 함수가 불리므로 아무 동작도 없다.

정리

  • I2C는 오픈 드레인 2선 버스이다. 주소 바이트 = 7비트 주소 + R/W이고, HAL 인자는 이 바이트(7비트 << 1)이다.
  • PCF8574는 레지스터 없는 8비트 포트이다. 데이터 바이트가 곧 P7~P0 핀 상태이다.
  • 4비트 LCD는 니블마다 E를 1 → 0으로 흔든다. 그래서 글자 하나 = I2C 바이트 4개 = 전송 한 번(약 0.45 ms)이다.
  • 초기화 니블 3, 3, 3, 2는 니블 하나씩 보내야 한다. 라이브러리 lcd_init()처럼 두 니블씩 보내면 4비트 전환 뒤 짝이 어긋나 표시가 켜지지 않는다. 이 예제는 lcd_init_4bit()로 고쳤다.
  • I2C1은 PCLK1 32 MHz에서 FREQ = 32, CCR = 160, TRISE = 33으로 100 kHz가 된다. 이 예제는 리맵 핀 PB8/PB9를 쓴다.
  • HAL 폴링 함수는 SB → ADDR → TxE/BTF → STOP 순서를 대신 처리한다. NACK는 SR1.AF와 HAL_ERROR로 드러난다.
