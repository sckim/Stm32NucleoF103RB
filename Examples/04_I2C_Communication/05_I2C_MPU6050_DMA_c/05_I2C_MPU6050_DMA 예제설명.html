DMA로 읽는 MPU6050: 버스가 도는 동안 CPU는 다른 일을 한다

04_I2C_MPU6050_c는 HAL_I2C_Mem_Read()로 14바이트를 읽는 약 1.6 ms 동안 CPU를 붙잡았다. 이 예제설명은 같은 읽기를 HAL_I2C_Mem_Read_DMA()로 바꾼다. 데이터 바이트는 DMA1 채널7이 I2C1->DR에서 메모리로 옮기고, CPU는 완료 콜백에서 결과만 받는다. 다만 HAL F1의 이 함수는 주소 단계를 여전히 폴링으로 처리한다. 어디까지가 CPU 일이고 어디부터 DMA 일인지 레지스터 수준에서 나눠 본다.

1. 03에서 무엇이 바뀌는가

I2C는 느리다. 100 kHz에서 한 바이트는 ACK 비트를 포함해 9클럭, 즉 90 µs이다. 64 MHz Cortex-M3는 그동안 명령을 수천 개 실행할 수 있다. 블로킹 API는 그 시간을 플래그 폴링으로 버린다. 이 예제는 그 시간을 DMA에 넘기고, 결과가 실제로 CPU를 비웠는지를 main loops during DMA 숫자로 보여 준다.

DMA 수신 자체는 이미 봤다. 02_USART/04_USART_DMA_IdleLine_c는 UART 수신 바이트를, 03_ADC/04_ADC_DMA_TimTrigger는 ADC 결과를 DMA로 옮겼다. 이 예제는 같은 원리를 I2C에 적용한다. 차이는 I2C가 마스터가 시작해야 바이트가 오는 버스라는 점이다. 그래서 DMA를 켜기 전에 START, 주소, 레지스터 번호를 누군가 보내야 하고, 마지막 바이트에서 NACK과 STOP을 정확히 내야 한다.

회로 연결도

2. I2C 레지스터 읽기 프레임

I2C는 SCL(클럭)과 SDA(데이터) 두 선을 쓴다. 두 선 모두 오픈 드레인 + 풀업이다. 누구든 선을 Low로 당길 수 있고, 아무도 당기지 않으면 풀업이 High로 올린다. 그래서 STM32 핀 모드는 GPIO_MODE_AF_OD(PB6, PB7)이다.

  • START (S): SCL이 High인 동안 SDA가 High → Low로 떨어진다. 마스터만 만든다.
  • 바이트: SDA는 SCL이 Low일 때 바뀌고 High일 때 읽힌다. MSB부터 8비트, 9번째 클럭은 받는 쪽이 SDA를 Low로 당기면 ACK, 놓아 두면 NACK이다.
  • RESTART (Sr): STOP 없이 다시 START를 낸다. 버스를 놓지 않고 방향(쓰기 → 읽기)을 바꾼다.
  • STOP (P): SCL이 High인 동안 SDA가 Low → High로 오른다.

이 예제가 한 번에 보내는 프레임

“0x3B번 레지스터부터 14바이트를 읽어라”는 쓰기 한 번(레지스터 번호 지정) + 읽기 한 번으로 이루어진다. 파랑은 STM32(마스터)가 SDA를 구동하는 칸, 보라는 MPU6050(슬레이브)이 구동하는 칸이다.

S0xD0 (0x68|W)A0x3BASr0xD1 (0x68|R)A D0AD1A…D12AD13NP
HAL 주소 인자 = 7비트 주소 << 1

MPU6050의 7비트 주소는 AD0 = GND일 때 0x68이다. 버스에 실리는 첫 바이트는 주소 << 1 | R/W이므로 쓰기는 0xD0, 읽기는 0xD1이다.

HAL은 DevAddress에 이미 1비트 왼쪽으로 민 값을 기대한다. 그래서 코드는 #define MPU_ADDR (0x68 << 1)이다. 0x68을 그대로 넘기면 HAL은 0x68 >> 1 = 0x34번 장치를 부르게 되고 응답이 없다.

3. MPU6050 레지스터

MPU6050은 내부 레지스터 번호(8비트)로 접근하는 장치이다. 읽기를 계속하면 레지스터 번호가 자동으로 1씩 늘어나므로(burst read), 0x3B부터 14바이트를 읽으면 가속도·온도·자이로가 같은 샘플 시점의 값으로 한 번에 온다. 근거는 InvenSense MPU-6000/MPU-6050 Register Map and Descriptions(Rev 4.2)이다.

mg = raw × 1000 / 16384 (예: raw = 16384 → 1000 mg = 1 g)

0.1 °/s = raw × 10 / 131 (예: raw = 131 → 10 → 1.0 °/s)

4. 직접 만져 보기

아래 시뮬레이터는 HAL_I2C_Mem_Read_DMA() 한 번을 단계별로 실행한다. 단계마다 버스에 무엇이 실리는지, I2C1·DMA 레지스터 비트가 어떻게 바뀌는지, 누가(CPU, DMA, ISR) 일하는지를 보여 준다.

  1. 한 단계를 눌러 주소 단계 5칸 동안은 CPU(파랑)가 일하고, return HAL_OK 뒤로는 DMA(청록)가 dma_buf를 채우는 것을 본다. main loops는 반환 뒤부터만 늘어난다.
  2. 마지막 데이터 바이트에서 마스터가 ACK 대신 NACK을 내는 것을 확인한다(CR2.LAST의 효과). STOP은 TC 인터럽트 단계에서 생긴다.
  3. 오류 주입을 센서 없음으로 바꾼다. 주소 바이트에서 NACK이 나고 함수가 HAL_ERROR로 반환된다. ErrorCallback은 불리지 않는다.
  4. 데이터 중 버스 오류와 응답 멈춤을 비교한다. 앞의 것은 ER ISR → ErrorCallback 경로, 뒤의 것은 main의 20 ms 타임아웃 경로로 복구된다.
  5. SCL을 400 kHz로 바꾸고 아래 CPU 점유 막대를 본다. 기울기 슬라이더를 움직이면 다음 전송의 바이트와 UART 출력이 바뀐다.

5. 레지스터 분석

I2C1 레지스터 (기준 주소 0x4000 5400, RM0008 26장)

레지스터비트이 예제에서의 값·역할
CR1 (0x00)PE(0), START(8), STOP(9), ACK(10), POS(11), SWRST(15)PE = 1로 켠다. START를 쓰면 하드웨어가 START/RESTART를 내고 비트를 지운다. ACK = 1이면 받은 바이트마다 ACK. STOP은 DMA TC 처리에서 HAL이 쓴다. SWRST는 HAL_I2C_Init()이 재초기화 때 쓴다.
CR2 (0x04)FREQ[5:0], ITERREN(8), ITEVTEN(9), ITBUFEN(10), DMAEN(11), LAST(12)FREQ = 32(PCLK1 = 32 MHz). 데이터 단계 직전에 LAST = 1, ITERREN = 1, DMAEN = 1. ITEVTEN과 ITBUFEN은 이 경로에서 켜지지 않는다. RM0008은 DMA 수신 때 ITBUFEN을 켜지 말라고 한다.
OAR1 (0x08)ADD[9:0], ADDMODE(15), bit14자기 주소. 마스터로만 쓰므로 0. bit14는 RM0008이 소프트웨어로 1을 유지하라고 한 비트이며, HAL은 I2C_ADDRESSINGMODE_7BIT(0x4000)로 이 비트를 세운다.
DR (0x10)DR[7:0]송신 바이트를 쓰고 수신 바이트를 읽는 곳. 주소 단계에서는 CPU가 쓰고, 데이터 단계에서는 DMA가 읽는다(CPAR7 = 0x4000 5410).
SR1 (0x14)SB(0), ADDR(1), BTF(2), RxNE(6), TxE(7), BERR(8), ARLO(9), AF(10), OVR(11)SB: START 완료(SR1 읽기 + DR 쓰기로 지워짐). ADDR: 주소 ACK 받음(SR1 읽기 + SR2 읽기로 지워짐). TxE/BTF: 송신 진행. RxNE: 수신 바이트 도착 → DMA 요청. AF: NACK 받음. BERR/ARLO/OVR: 오류(ITERREN이면 ER 인터럽트).
SR2 (0x18)MSL(0), BUSY(1), TRA(2)BUSY: 버스에서 START를 본 뒤 STOP 전까지 1. HAL은 시작 전에 이 비트가 0이 되기를 최대 25 ms 기다린다. MSL: 마스터 모드. TRA: 1이면 송신, 0이면 수신.
CCR (0x1C)CCR[11:0], DUTY(14), F/S(15)표준 모드(F/S = 0): T_high = T_low = CCR × T_PCLK1. CCR = 32 MHz / (2 × 100 kHz) = 160(0xA0).
TRISE (0x20)TRISE[5:0]표준 모드 최대 상승 시간 1000 ns를 PCLK1 주기로 센 값 + 1 = 32 + 1 = 33.
400 kHz로 바꾸면

HAL은 F/S = 1, DUTY = 0(T_low/T_high = 2)을 쓰고 CCR = (32 000 000 − 1) / (3 × 400 000) + 1 = 27로 계산한다. 이론 SCL = 32 MHz / (3 × 27) ≈ 395 kHz이다. TRISE = 32 × 300 / 1000 + 1 = 10(Fast mode 최대 상승 시간 300 ns). MPU6050은 400 kHz Fast mode를 지원한다.

DMA1 채널7 (I2C1_RX)

F103에서 I2C1 요청은 DMA1에 고정 연결되어 있다. I2C1_TX → 채널6, I2C1_RX → 채널7(RM0008 13.3.7, DMA1 요청 표). 이 예제는 읽기만 하므로 채널7만 실제로 움직인다.

LAST 비트가 하는 일과 하지 않는 일

I2C 마스터 수신기는 마지막 바이트에 NACK을 내야 한다. 그래야 슬레이브가 SDA를 놓고 마스터가 STOP을 낼 수 있다. CPU가 바이트를 읽는 방식에서는 소프트웨어가 마지막 바이트 직전에 ACK = 0을 써야 하는데, DMA 방식에서는 그 시점을 CPU가 모른다.

CR2.LAST = 1은 “다음 DMA EOT가 마지막 전송이다”라는 뜻이다. I2C는 DMA가 마지막 바이트를 가져가는 시점에 맞춰 자동으로 NACK을 낸다. 그러나 STOP은 자동이 아니다. DMA1 채널7 TC 인터럽트에서 HAL(I2C_DMAXferCplt)이 CR1.STOP = 1을 쓴다. 이 순서 때문에 TC 인터럽트가 늦게 처리되면 STOP도 늦어진다.

6. HAL이 대신 해 주는 일

HAL_I2C_DeInitPE = 0 → HAL_I2C_MspDeInit: I2C1 클럭 끔, PB6/PB7 초기화, DMA 채널 6/7 DeInit, I2C1 EV/ER IRQ 끔
정리: 이 예제의 ‘논블로킹’은 절반이다

100 kHz에서 전송 1회 약 1.56 ms 중 약 0.29 ms(주소 단계)는 여전히 CPU가 HAL_I2C_Mem_Read_DMA() 안에서 기다린다. 나머지 약 1.27 ms(데이터 14바이트 + STOP)가 CPU에서 풀려난다. 읽는 바이트가 많을수록 이득이 커진다. 1바이트만 읽는다면 DMA로 얻는 것이 거의 없다.

7. ISR과 콜백

정상 흐름에서 CPU가 깨어나는 인터럽트는 하나, DMA1 채널7 TC뿐이다. 진짜 ISR과 HAL 콜백을 구분해 둔다.

  1. 1
    I2C1이 14번째 바이트를 받고 DMA가 가져간다HWSR1.RxNE → DMA 요청 → DMA가 DR을 읽어 dma_buf[13]에 쓴다. CNDTR7 = 0이 되어 DMA1_ISR.TCIF7이 선다. LAST = 1이었으므로 이 바이트에 I2C가 NACK을 낸다.
  2. 2
    DMA1_Channel7_IRQHandler() — 진짜 ISRISRstm32f1xx_it.c. 벡터 테이블에서 바로 불리며 HAL_DMA_IRQHandler(&hdma_i2c1_rx)만 호출한다. NVIC 우선순위 1.
  3. 3
    HAL_DMA_IRQHandler() → I2C_DMAXferCplt()ISR 문맥DMA1_IFCR로 TCIF7을 지우고 채널 인터럽트를 끈 뒤(일반 모드), I2C 쪽 완료 처리로 넘어간다. 여기서 CR1.STOP = 1, CR2.LAST = 0, CR2.DMAEN = 0.
  4. 4
    HAL_I2C_MemRxCpltCallback() — HAL 콜백main.c사용자가 정의한 함수이다. ISR이 아니지만 ISR 문맥에서 실행된다. dma_buf를 data로 복사하고 rx_done = 1만 한다. 변환과 UART 출력은 main이 한다.
ISR (stm32f1xx_it.c)NVIC 우선순위이 예제에서이어지는 HAL 콜백
DMA1_Channel7_IRQHandler1사용 (TC: 완료, TE: DMA 오류)MemRxCpltCallback / ErrorCallback
I2C1_ER_IRQHandler0사용 (데이터 단계의 BERR, ARLO, OVR)ErrorCallback
I2C1_EV_IRQHandler0호출되지 않음. ITEVTEN이 켜지지 않는다. _IT 계열 API용–

왜 재초기화를 콜백에서 하지 않는가

HAL_I2C_ErrorCallback()은 ISR 문맥이다. 여기서 HAL_I2C_DeInit()/HAL_I2C_Init()을 부르면 아직 끝나지 않은 HAL 오류 처리(같은 핸들의 상태 변경, DMA 중단 콜백)와 겹칠 수 있고, ISR이 길어진다. 콜백은 rx_error = 1만 하고 main이 다음 루프에서 재초기화한다. rx_done, rx_error는 ISR과 main이 공유하므로 volatile이다.

특히 BERR이 나면 HAL_I2C_ER_IRQHandler가 CR1.SWRST = 1을 남겨 두므로(6절) I2C1은 재초기화 전까지 멈춰 있다. main의 HAL_I2C_DeInit() + MX_I2C1_Init()이 이 비트를 다시 0으로 돌린다.

8. 코드 읽기

계층은 HAL + DMA이다. 사용자 코드는 모두 /* USER CODE BEGIN ... */ 영역 안에 있다. 오른쪽은 각 줄이 다루는 레지스터·비트이다.

  4. dma_buf는 전역(static)이어야 한다. DMA는 함수가 끝난 뒤에도 그 주소에 쓴다

9. 실험

배선: MPU6050(GY-521) VCC = 3.3 V, GND, SCL = PB6(Arduino D10), SDA = PB7, AD0 = GND. GY-521 모듈에는 풀업 저항이 있다. 터미널은 115200 8N1이다.

실험 A. 기본 출력과 loops 값

WHO_AM_I=0x68, starting DMA reads
acc[mg]     12    -20   1003 | gyroZ[0.1dps]     -3 | main loops during DMA = ...
acc[mg]     11    -18   1001 | gyroZ[0.1dps]     -2 | main loops during DMA = ...

보드를 평평하게 두면 az가 약 1000 mg, ax와 ay는 0 근처이다(오프셋은 칩마다 다르다). 한 축을 아래로 세우면 그 축이 ±1000 mg이 된다. main loops during DMA는 0이 아닌 일정한 값이어야 한다. 이 값을 데이터 단계 시간(약 1.27 ms)으로 나누면 main 루프 1바퀴의 대략적인 시간이 나온다. 시뮬레이터의 가정값과 비교한다.

실험 B. 블로킹 구간을 핀으로 잰다

HAL_I2C_Mem_Read_DMA() 호출 직전에 HAL_GPIO_WritePin(LD2_GPIO_Port, LD2_Pin, GPIO_PIN_SET), 직후에 RESET을 넣는다. PA5(D13)와 SCL(PB6)을 AD2 오실로스코프로 함께 본다. 펄스 폭은 약 0.3 ms로, 버스의 처음 3바이트(+Sr, 4번째 주소 바이트) 구간과 겹쳐야 한다. 같은 자리를 블로킹 HAL_I2C_Mem_Read()로 바꾸면 펄스가 약 1.6 ms로 늘고 loops는 0 근처가 된다.

실험 C. 센서를 뽑았다 꽂는다

동작 중에 SDA 선을 뺀다. 매 100 ms마다 다음 줄이 나와야 한다.

I2C start failed (st=1, err=0x04) -> re-init

st=1은 HAL_ERROR, err=0x04는 HAL_I2C_ERROR_AF(주소 NACK)이다. 선을 다시 꽂으면 다음 주기부터 정상 출력으로 돌아온다. 모듈 전원(VCC)을 빼면 모듈의 풀업도 함께 꺼져 버스가 Low로 끌릴 수 있다. 이때는 err=0x20(TIMEOUT)이 나올 수 있다. 두 경우를 비교한다.

실험 D. 400 kHz로 올린다

CubeMX에서 I2C1을 Fast Mode 400 kHz로 바꾸거나 hi2c1.Init.ClockSpeed = 400000으로 바꾼다(MX_I2C1_Init은 CubeMX 영역이므로 .ioc에서 바꾸는 것이 원칙이다). 전송 시간이 약 1/4로 줄어 loops도 약 1/4이 되어야 한다. 실험 B의 펄스도 약 0.07 ms로 줄어든다.

실험 E. 로직 분석기로 프레임을 본다

AD2 Logic의 I2C 디코더로 SCL = PB6, SDA = PB7을 캡처한다. S, 0xD0 A, 0x3B A, Sr, 0xD1 A, 14바이트(마지막 N), P가 2절의 그림과 같은지 확인한다. 마지막 바이트의 NACK과 STOP 사이 간격이 TC 인터럽트 처리 시간이다. SCL 실제 주파수도 여기서 잰다.

11. 확인 문제

먼저 스스로 답을 정해 본 뒤 펼쳐 확인한다.

문제 1. AD0를 3.3 V에 연결하면 7비트 주소와 HAL에 넘길 주소는 각각 얼마인가?

7비트 주소는 0x69, HAL 인자는 0x69 << 1 = 0xD2이다. 버스에서 쓰기 바이트는 0xD2, 읽기 바이트는 0xD3이다.

문제 2. 100 kHz에서 이 예제의 전송 1회 중 CPU가 폴링으로 기다리는 시간과 DMA가 맡는 시간은 각각 대략 얼마인가?

주소 단계: S + 3바이트 × 9클럭 + Sr ≈ 29클럭 ≈ 0.29 ms(CPU). 데이터 단계: 14 × 9 = 126클럭 = 1.26 ms(DMA). 합계와 STOP을 더하면 약 1.6 ms이다.

문제 3. 센서를 뽑았을 때 HAL_I2C_ErrorCallback()이 불리지 않는 이유는?

NACK은 주소 바이트(0xD0)에서 생긴다. 이 단계는 HAL_I2C_Mem_Read_DMA() 안에서 폴링으로 처리되므로, HAL이 SR1.AF를 직접 보고 STOP을 낸 뒤 HAL_ERROR를 반환한다. 이때 ITERREN은 아직 켜지지 않았고 ER 인터럽트도 없다. 그래서 반환값을 검사해야 이 오류를 알 수 있다.

문제 4. CR2.LAST를 켜지 않고 DMA로 14바이트를 받으면 어떤 일이 생길 수 있는가?

마스터가 14번째 바이트에도 ACK을 낸다. 슬레이브는 읽기가 계속된다고 보고 다음 바이트의 첫 비트를 SDA에 내놓는다. 그 비트가 0이면 슬레이브가 SDA를 Low로 잡고 있어 마스터가 STOP(SDA 상승)을 만들 수 없고, 버스가 BUSY에 걸릴 수 있다. LAST는 마지막 바이트에 NACK을 자동으로 내 이 문제를 막는다.

문제 5. 이 예제의 진짜 ISR 중 실제로 호출되는 것과, 이어지는 HAL 콜백을 말하라.

정상 흐름: DMA1_Channel7_IRQHandler → HAL_DMA_IRQHandler → I2C_DMAXferCplt → HAL_I2C_MemRxCpltCallback. 데이터 단계 오류: I2C1_ER_IRQHandler → HAL_I2C_ER_IRQHandler → HAL_I2C_ErrorCallback. 그 밖에 SysTick_Handler가 1 ms 틱을 센다. I2C1_EV_IRQHandler와 DMA1_Channel6_IRQHandler는 이 흐름에서 불리지 않는다.

문제 6. 콜백에서 dma_buf를 data로 복사하는 이유는? 지금 코드에서 복사를 빼도 당장 문제가 없는 이유는?

main이 값을 변환하는 동안 다음 DMA 전송이 시작되면 dma_buf가 덮어써져 앞뒤 샘플이 섞일 수 있다. 사본을 두면 그 위험이 없다. 지금 코드는 busy = 0이 되고 출력까지 끝난 뒤에야 다음 전송을 시작하므로 겹치지 않는다. 그러나 출력과 전송을 겹치도록 고치는 순간 문제가 되므로 복사해 두는 편이 안전하다.

문제 7. data[4] = 0x40, data[5] = 0x00, data[12] = 0xFF, data[13] = 0x7D이면 출력되는 az와 gyroZ 값은?

az = 0x4000 = 16384 → 16384 × 1000 / 16384 = 1000 mg. gz = 0xFF7D = −131 → −131 × 10 / 131 = −10, 즉 −1.0 °/s이다.

문제 8. main loops during DMA는 정확히 어느 구간에 돈 루프 수인가? 주소 단계 시간이 포함되는가?

loops = 0은 HAL_I2C_Mem_Read_DMA() 호출 직전에 되지만, 함수 안에서 폴링하는 동안에는 main 루프가 돌지 않는다. 따라서 함수가 반환된 뒤부터 main이 rx_done을 보기 직전까지, 즉 데이터 단계 + TC 인터럽트 처리 시간 동안의 루프 수이다. 주소 단계는 포함되지 않는다.

문제 9. 100 kHz에서 CCR과 TRISE 값을 PCLK1 = 32 MHz로부터 계산하라.

표준 모드에서 T_high = T_low = CCR × T_PCLK1이므로 CCR = 32 MHz / (2 × 100 kHz) = 160. TRISE = 1000 ns / 31.25 ns + 1 = 32 + 1 = 33이다.
