I2C EEPROM: 페이지 경계와 ACK 폴링

AT24C32/64는 전원이 꺼져도 값을 지키는 I2C EEPROM이다. 읽기는 센서 레지스터처럼 쉽지만, 쓰기에는 규칙이 세 개 있다. 메모리 주소가 16비트이고, 한 번에 한 페이지(32바이트) 안에서만 쓸 수 있으며, 쓴 뒤 수 ms 동안 칩이 응답하지 않는다. 이 교안은 07_I2C_EEPROM_AT24C_c 예제가 이 세 규칙을 HAL_I2C_Mem_Write, 페이지 분할, HAL_I2C_IsDeviceReady 반복(ACK 폴링)으로 처리하는 방법을 해석한다.

1. 문제: 전원이 꺼져도 남아야 하는 값

보정값, 설정, 누적 카운터처럼 리셋 뒤에도 남아야 하는 값이 있다. MCU의 SRAM은 전원이 꺼지면 지워진다. 내부 플래시는 페이지(F103RB는 1 KB) 단위로 지워야 해서 몇 바이트만 바꾸기 번거롭다. 외장 I2C EEPROM은 바이트 단위로 고쳐 쓸 수 있는 비휘발성 메모리이다.

앞 예제들과의 관계는 다음과 같다.

  • 01_I2C_Scan에서 버스에 응답하는 주소를 찾았다. 이 예제는 같은 원리(주소에 ACK가 오는가)를 쓰기 완료 검출에 다시 쓴다.
  • 04_I2C_MPU6050_c는 HAL_I2C_Mem_Read에 8비트 레지스터 주소를 썼다. AT24C32/64는 메모리 주소가 16비트라 I2C_MEMADD_SIZE_16BIT를 쓴다.
  • 다음 예제 08_I2C_DS3231_RTC_c는 같은 ZS-042 모듈에 올라간 RTC를 읽는다. 이 모듈의 EEPROM이 이 예제의 대상이 될 수 있다.
  • 10_Flash_CRC/01_Flash_Write_c는 내부 플래시를 쓴다. "쓰기 전에 지운다", "쓰는 동안 기다린다"는 비슷한 제약을 비교해 볼 수 있다.
이 교안의 목표
  • 장치 주소 바이트(1010 A2 A1 A0 R/W)와 HAL 주소 인자(0x50 << 1 = 0xA0)를 연결한다.
  • 페이지 쓰기의 되감김(roll-over)을 이해하고, ee_write()가 40바이트를 4 + 32 + 4바이트로 나누는 이유를 계산한다.
  • 쓰기 사이클(tWR) 동안 칩이 NACK하는 성질을 이용한 ACK 폴링을 이해한다.
  • HAL이 I2C1의 CR1.START, SR1.SB/ADDR/TXE/BTF/AF 플래그를 어떤 순서로 다루는지 따라간다.

회로 연결도

예제가 쓰는 연결은 I2C 두 선과 전원 두 선이다. stm32f1xx_hal_msp.c는 PB6(I2C1_SCL)과 PB7(I2C1_SDA)을 오픈 드레인 대체 기능(GPIO_MODE_AF_OD)으로 설정하고 내부 풀업을 켜지 않는다. 그래서 두 선 모두 외부 풀업 저항이 필요하다. 시중 AT24C 모듈에는 풀업이 이미 달린 경우가 많다. 그때는 R1·R2를 따로 달지 않는다.

페이지 쓰기의 되감김

칩은 페이지 쓰기 중 받은 바이트를 내부 페이지 버퍼에 모은다. 이때 주소의 하위 5비트만 1씩 증가한다(페이지 32 = 25). 하위 5비트가 31에서 다음으로 넘어가면 0으로 돌아가고 상위 비트는 그대로이다. 즉 다음 페이지로 넘어가지 않고 같은 페이지의 처음을 덮어쓴다. 32바이트보다 많이 보내면 먼저 보낸 바이트가 나중 바이트로 덮인다.

그림 1. 페이지 경계를 넘는 한 번의 쓰기. 버스 오류도 NACK도 없다. HAL은 HAL_OK를 돌려준다. 잘못 쓴 것은 다시 읽어 봐야 드러난다.

쓰기 사이클 tWR

STOP 이후 칩은 페이지 버퍼를 EEPROM 셀에 프로그래밍한다. 이 시간이 tWR이다. AT24C32C/AT24C64C 데이터시트의 최댓값은 5 ms이다. 제조사·세대·전원 전압에 따라 값이 다를 수 있으니 실제 칩의 데이터시트를 확인한다. 이 동안 칩은 장치 주소에 NACK한다. 읽기도 쓰기도 받지 않는다.

방법 1. 고정 지연HAL_Delay(5)

단순하다. 하지만 항상 최악의 시간을 기다린다. tWR가 더 긴 칩에서는 부족할 수도 있다. HAL_Delay(5)는 최소 대기를 보장하려고 1틱을 더하므로 실제로는 5~6 ms이다.

방법 2. ACK 폴링 (이 예제)HAL_I2C_IsDeviceReady 반복

주소만 보내서 ACK가 오는지 확인하고 반복한다. 끝나는 즉시 진행한다. 20 ms 상한을 두어 칩이 사라져도 무한 대기에 빠지지 않는다.

3. 40바이트를 페이지 단위로 나누기

예제는 TEST_ADDR = 0x011C부터 TEST_LEN = 40바이트를 쓴다. 일부러 경계 0x0120과 0x0140을 걸치게 잡았다. ee_write()는 매번 "이 페이지에 남은 칸"을 계산한다.

세 번 쓰므로 tWR도 세 번 기다린다. 분할하지 않고 40바이트를 한 번에 보내면 어떻게 되는가? 모두 페이지 0x0100~0x011F에 들어간다. 바이트 i는 0x0100 + ((0x1C + i) % 32)에 떨어진다. 40 > 32이므로 처음 8바이트는 나중 8바이트에 덮여 사라진다. 결과적으로 페이지 전체(32바이트)에 wr[8]~wr[39]가 남고 0x0120~0x0143은 바뀌지 않는다. 다시 읽으면 FAIL이다. 아래 시뮬레이터에서 직접 확인한다.

읽기는 경계와 무관하다

연속 읽기는 주소 전체(AT24C32는 12비트)가 1씩 증가하므로 페이지 경계를 자유롭게 넘는다. 그래서 예제는 읽기를 HAL_I2C_Mem_Read 한 번(40바이트)으로 처리한다. 메모리의 맨 끝 주소를 넘으면 0번지로 돌아간다.

4. 직접 만져 보기

시뮬레이터 1은 EEPROM의 0x0100~0x017F(4페이지)를 보여 준다. 쓰기 방식을 고르고 실행하면 칩이 받은 바이트가 어디에 떨어지는지, 다시 읽은 값이 맞는지, ACK 폴링을 몇 번 했는지 계산한다.

  1. 기본값(0x011C, 40 B, 페이지 분할)으로 쓰기 실행을 누른다. 트랜잭션 3개, PASS를 확인한다.
  2. 방식을 분할 없이 한 번에로 바꾸고 다시 실행한다. 주황 칸(범위 밖 덮어쓰기)과 점선 칸(기대값과 다름: 안 바뀌었거나 나중 바이트로 덮임)이 생기고 FAIL이 된다.
  3. 시작 주소를 0x0120, 길이 32로 맞추면 분할이 없어도 PASS인 것을 확인한다. 경계에 맞춰 쓰면 페이지 하나에 딱 맞는다.
  4. tWR 슬라이더를 1 ms와 10 ms로 바꿔 폴링 횟수와 총 시간의 변화를 본다. 대기 방식을 HAL_Delay(5), 대기 없음으로도 바꿔 본다.

시뮬레이터 모델: 전송 시간 = (바이트 수 × 9 + 2) / f_SCL. ACK 폴링 1회 ≈ 11 SCL 클럭(START + 주소 9비트 + STOP)으로 가정하고 HAL의 소프트웨어 오버헤드는 무시한다. 실제 값은 칩의 tWR와 HAL 실행 시간에 따라 달라진다. 데이터 패턴은 예제처럼 wr[i] = round × 3 + i이고 실행할 때마다 round가 1 증가한다. "대기 없음"에서는 칩이 바쁠 때 온 Mem_Write가 주소 NACK으로 HAL_ERROR를 받는다.

시뮬레이터 2. 첫 바이트의 SCL/SDA 파형

장치 주소 바이트 하나를 비트 단위로 그린다. ACK 폴링의 핵심은 9번째 클럭에서 SDA를 누가 Low로 당기는가이다.

    ADDR 해제 SR1 → SR2 읽기두 레지스터를 순서대로 읽어 ADDR을 지운다.
  5. 5
    메모리 주소 2바이트 TXE → DR ← MSB, TXE → DR ← LSBI2C_MEMADD_SIZE_16BIT이므로 상위 바이트(0x01)를 먼저, 하위 바이트(0x1C)를 다음에 보낸다.
  6. 6
    데이터 n바이트 TXE → DR바이트마다 TXE를 기다려 DR에 쓴다. 마지막에 BTF를 기다린다.
  7. 7
    STOP CR1.STOPSTOP 생성. EEPROM 내부 쓰기 사이클이 여기서 시작한다. HAL은 이 사실을 모른다. 기다리는 일은 사용자 코드가 해야 한다.

HAL_I2C_Mem_Read

1~5단계는 같다(주소 포인터를 옮기는 "더미 쓰기"). 그다음 CR1.ACK = 1로 두고 STOP 없이 다시 START(RESTART)를 건다. 주소 0xA1을 보내 ADDR을 받고, RXNE마다 DR을 읽는다. 끝에서 두세 바이트 전에 CR1.ACK를 내리고 STOP을 예약해 마지막 바이트에 NACK을 보낸다.

HAL_I2C_IsDeviceReady(&hi2c1, 0xA0, Trials, Timeout)

START → 주소 0xA0 → ADDR 또는 AF를 기다린다. ADDR이면 STOP, ADDR 해제, HAL_OK. AF면 STOP, AF 지움, BUSY 해제를 기다리고 다음 시도로 넘어간다. Trials번 모두 NACK이면 HAL_ERROR이다. 시도 사이에 지연은 없다. 데이터는 한 바이트도 보내지 않으므로 칩 내용은 바뀌지 않는다.

ISR과 콜백

이 예제는 블로킹 API만 쓴다. I2C 이벤트/오류 인터럽트(I2C1_EV_IRQHandler, I2C1_ER_IRQHandler)도, HAL 콜백(HAL_I2C_MemTxCpltCallback 등)도 없다. 동작하는 인터럽트는 SysTick 하나이다. SysTick_Handler(ISR)가 HAL_IncTick()을 불러 1 ms 틱을 올리고, HAL 함수는 이 틱(HAL_GetTick)으로 타임아웃을 잰다. 논블로킹 I2C는 05_I2C_MPU6050_DMA_c에서 다룬다.

  1. EE_ADDR = 0xA0. ZS-042 모듈이면 (0x57 << 1)로 바꾼다.
  2. EE_PAGE는 칩마다 다르다. AT24C256이면 64로 바꾼다.

main.c — USER CODE 0: ACK 폴링
static uint32_t ee_wait_ready(void)
{
    uint32_t t0 = HAL_GetTick(), polls = 0;
    while ((HAL_GetTick() - t0) < 20)
    {
        polls++;
        if (HAL_I2C_IsDeviceReady(&hi2c1, EE_ADDR, 1, 5) == HAL_OK)
            return polls;   /* ACK 오면 내부 쓰기 종료 */
    }
    return 0;              /* 20 ms 안에 응답 없음 → 실패 */
}
  1. Trials = 1로 한 번만 시도하고 반복은 바깥 while이 한다. 그래서 몇 번 시도했는지 셀 수 있다.
  2. 상한 20 ms는 tWR 최댓값(5 ms)보다 넉넉하다. 칩이 빠지거나 배선이 끊기면 0을 돌려 오류로 처리한다.
  3. t0를 빼서 비교하므로 HAL_GetTick()이 넘쳐 0으로 돌아가도 올바르다.
main.c — USER CODE 0: 페이지 분할 쓰기
static int ee_write(uint16_t addr, const uint8_t *data,
                    uint16_t len, uint32_t *polls_total)
{
    while (len)
    {
        uint16_t room = (uint16_t)(EE_PAGE - (addr % EE_PAGE));
        uint16_t n = len < room ? len : room;
        if (HAL_I2C_Mem_Write(&hi2c1, EE_ADDR, addr,
                I2C_MEMADD_SIZE_16BIT, (uint8_t *)data, n, 100) != HAL_OK)
            return 0;
        uint32_t p = ee_wait_ready();   /* tWR 대기 */
        if (!p) return 0;
        *polls_total += p;
        addr = (uint16_t)(addr + n); data += n; len = (uint16_t)(len - n);
    }
    return 1;
}
  1. room은 현재 페이지에 남은 칸 수이다. 3절 표처럼 4, 32, 32가 나온다.
  2. 쓰기 하나마다 바로 ACK 폴링을 한다. 다음 Mem_Write가 NACK을 받지 않게 하는 순서이다.
  3. Mem_Write 실패와 폴링 시간 초과를 모두 0으로 돌려준다. 호출부는 PASS/FAIL로만 구분한다.
  4. (uint8_t *)data 캐스트는 HAL 원형이 const가 아니어서 필요하다. HAL은 쓰기 버퍼를 바꾸지 않는다.

수명 주의

이 루프는 2초마다 같은 40바이트를 다시 쓴다. 하루 43,200회이다. AT24C32C/64C 데이터시트의 쓰기 내구성은 셀당 1,000,000회이므로 계속 켜 두면 약 23일 만에 보증 횟수를 넘는다. 소스 머리 주석도 "자주 바뀌는 값은 같은 주소에 반복 쓰지 말 것"이라고 했다. 실습이 끝나면 보드를 끄거나, 실험 E처럼 라운드 수를 제한한다.

8. 실험

실험 A. 기본 실행과 폴링 횟수

그대로 빌드해 시리얼 터미널(115200)을 연다. 2초마다 #n write 40 B @0x011C … ms, ACK polls=… | read back: PASS가 나와야 한다. 기대 결과: 매 줄 PASS. polls는 세 번 쓰기의 합이라 3 이상이다. 시간은 대략 "전송 약 4.5 ms(100 kHz, 447 클럭) + 실제 tWR × 3" 근처이다. 정확한 값은 칩마다 다르므로 직접 읽은 값을 기록한다.

실험 B. 페이지 분할을 없애기

ee_write() 안의 n을 n = len;으로 바꿔 40바이트를 한 번에 보낸다. 기대 결과: Mem_Write는 HAL_OK인데 read back이 FAIL이다. 시뮬레이터 1의 "분할 없이" 결과와 같은 배치인지, rd를 16진수로 출력해 확인한다.

실험 C. 대기를 빼거나 고정 지연으로

(1) ee_wait_ready() 호출을 빼고 p = 1로 둔다. 기대 결과: 두 번째 Mem_Write가 주소 NACK으로 HAL_ERROR를 받아 FAIL. (2) 대신 HAL_Delay(5)를 넣는다. 기대 결과: 칩의 실제 tWR가 5 ms(HAL_Delay(5)의 최소 대기)보다 짧으면 PASS지만, 시간은 폴링 방식보다 길거나 같다. tWR가 더 긴 칩이면 다음 쓰기가 NACK을 받는다.

실험 D. 주소 실수

EE_ADDR를 시프트 없이 0x50으로 바꾼다. 기대 결과: 버스에는 7비트 주소 0x28이 나가고, 시작 직후 "EEPROM not found"가 출력된 뒤 멈춘다. 02 예제 스캐너로 실제 주소를 다시 확인해 본다.

실험 E. 전원을 꺼도 남는지 확인 (수명 보호 겸)

USER CODE 2 끝에서 쓰기 전에 0x011C부터 40바이트를 먼저 읽어 출력하게 하고, 테스트 루프는 round < 5일 때만 쓰게 바꾼다. 전원을 껐다 켜서 직전 라운드의 패턴(round × 3 + i, 마지막 round = 4이면 12, 13, 14 …)이 그대로 읽히는지 본다. 기대 결과: 리셋 직후 첫 출력이 마지막에 쓴 패턴과 같다.

10. 확인 문제

문제 1. A2·A1·A0 = 101인 AT24C64의 HAL DevAddress는?

7비트 주소는 1010 101 = 0x55이다. HAL 인자는 0x55 << 1 = 0xAA이다. 읽기 때 버스에는 0xAB가 나간다.

문제 2. 0x01F8부터 20바이트를 쓰려면 Mem_Write를 몇 번, 어떻게 나눠 호출해야 하는가? (페이지 32 B)

0x01F8 % 32 = 24이므로 room = 8이다. 0x01F8~0x01FF에 8바이트, 0x0200~0x020B에 12바이트, 모두 2번이다.

문제 3. 분할 없이 0x011C에 40바이트를 한 번에 보냈다. 0x0100에 남는 값은 wr의 몇 번째 원소인가?

바이트 i는 0x0100 + ((28 + i) % 32)에 떨어진다. 0x0100에는 i = 4와 i = 36이 차례로 떨어지고 나중 것이 남는다. 따라서 wr[36]이다.

문제 4. ACK 폴링에 HAL_I2C_IsDeviceReady(…, Trials = 100, …) 한 번을 쓰지 않고 Trials = 1을 바깥 루프로 반복한 이유는?

몇 번 만에 ACK가 왔는지 셀 수 있고, 반복 상한을 시도 횟수가 아니라 시간(20 ms)으로 정할 수 있다. 시도 1회의 시간은 SCL 속도와 HAL 오버헤드에 따라 달라지므로 시간 상한이 더 분명하다.

문제 5. ACK 폴링 중 칩이 NACK을 보냈을 때 STM32 I2C1의 어느 비트가 세트되고, 누가 지우는가?

SR1.AF(bit 10, Acknowledge failure)가 하드웨어로 세트된다. 소프트웨어가 0을 써서 지운다. HAL에서는 __HAL_I2C_CLEAR_FLAG(hi2c, I2C_FLAG_AF)가 이 일을 한다.

문제 6. 읽기(HAL_I2C_Mem_Read)는 왜 페이지로 나누지 않아도 되는가?

연속 읽기에서는 주소 전체가 증가하므로 페이지 경계를 넘어간다. 되감김은 쓰기 때 페이지 버퍼를 쓰는 데서 생기는 제약이다. 메모리 끝을 넘을 때만 0번지로 돌아간다.

정리

  • HAL 주소 인자는 7비트 주소 << 1 이다. AT24C는 0x50 | A2A1A0.
  • AT24C32/64는 16비트 메모리 주소(I2C_MEMADD_SIZE_16BIT), 32바이트 페이지를 쓴다.
  • 페이지 경계를 넘는 쓰기는 오류 없이 같은 페이지 처음으로 되감긴다. 쓰기는 페이지 단위로 나눈다. 읽기는 나누지 않아도 된다.
  • STOP 뒤 tWR 동안 칩은 NACK한다. 주소만 보내는 ACK 폴링으로 끝을 감지하고, 시간 상한을 둔다.
  • NACK은 I2C1 SR1.AF로 나타난다. HAL은 이를 HAL_ERROR로 바꾼다.
  • EEPROM 쓰기 수명은 유한하다. 같은 주소를 주기적으로 반복해 쓰지 않는다.
