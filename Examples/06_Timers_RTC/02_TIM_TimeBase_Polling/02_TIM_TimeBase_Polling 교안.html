UIF 폴링과 틱 누락: 플래그는 횟수를 세지 못한다

타이머는 오버플로가 나면 인터럽트를 허용하지 않아도 상태 플래그(UIF)를 세운다. 이 플래그를 main 루프가 직접 읽는 것이 폴링이다. 이 교안은 01 예제와 같은 1 ms 타임베이스를 인터럽트 없이 폴링으로 처리하고, 루프가 막히면 틱이 누락되는 현상을 SysTick 기준 시계와 비교하여 측정하는 02_TIM_TimeBase_Polling 예제를 해석한다.

  • '먼저 지우고 일한다' 원칙과 폴링의 한계를 측정한다.

3. 폴링이 틱을 놓치는 이유

그림 1. 루프가 1 ms보다 오래 막히면 그 사이에 선 여러 번의 UIF가 한 번으로 합쳐진다.

UIF는 횟수를 세지 못하는 1비트 플래그이다. main 루프가 printf로 막힌 동안 UEV가 여러 번 나도 플래그는 1로 유지될 뿐이므로, 루프로 돌아와 확인하면 한 번으로만 센다.

4. 직접 만져 보기

아래 시뮬레이터는 10초 동안 1 ms 틱을 세고, 매초 한 번 실행되는 printf가 루프를 막을 때 폴링과 인터럽트가 얼마나 다른지 보여 준다.

  1. 방식을 폴링으로 두고 printf 바이트 수를 29로 맞춘다. 전송 시간이 약 2.5 ms이고 매초 1~2 ms씩 lag가 쌓인다.
  2. 바이트 수를 0으로 줄인다. 루프가 1 ms 안에 끝나므로 lag가 0이 된다.
  3. 방식을 인터럽트로 바꾼다. printf가 길어도 lag는 0이다.
  4. 폴링에서 먼저 지우기를 일한 뒤 지우기로 바꾸어 같은 조건에서 lag를 비교한다.

시뮬레이터 모델: 1바이트 = 86.8 µs. 전송 중 UEV는 floor(전송 시간[ms])번 또는 그보다 1번 많이 발생하므로 폴링의 누락은 floor(T)−1 ~ floor(T)틱이다(범위의 중간값을 사용). '일한 뒤 지운다'는 작업 중 선 UIF까지 지워 누락이 floor(T)+1로 늘어난다.

5. 비트 클리어 규칙: rc_w0

SR.UIF는 rc_w0 비트이다. 0을 써야 지워지고, 1을 쓰면 변하지 않는다. 그래서 HAL 매크로는 SR = ~TIM_SR_UIF(UIF 위치만 0, 나머지 1)를 한 번에 쓴다.

읽기-수정-쓰기 금지

TIM3->SR &= ~TIM_SR_UIF는 SR을 읽은 뒤 다시 쓴다. 읽은 직후 다른 플래그(CC1IF 등)가 새로 서면 쓰는 값에서 그 비트가 0이 되어 의도하지 않게 지워진다. 이 예제처럼 UIF만 쓰는 경우 영향은 작지만 습관적으로 SR = ~flag 형태를 쓴다.

6. 레지스터 비교

시간 기준 설정은 01과 같다 (TIM3, PSC=63, ARR=999, ARPE=1 → 1 kHz). 달라지는 것은 시작과 이벤트 처리이다.

레지스터01 (IT)02 (폴링)비고
CR10x00810x0081ARPE=1, CEN=1 (동일)
DIER0x00010x0000UIE만 다르다
SR.UIFHAL이 클리어main이 클리어bit 0, rc_w0

비교용 기준 시계로 HAL_GetTick()을 사용한다. SysTick은 인터럽트로 동작하므로 UIF 폴링과 무관하게 정확히 1 ms마다 증가한다.

7. 코드 읽기

외부 부품은 필요 없다. LD2(PA5) 토글과 USART2 가상 COM(115200 8N1) 출력을 사용한다.

main.c — 시작 전 UIF 정리와 타이머 시작
__HAL_TIM_CLEAR_FLAG(&htim3, TIM_FLAG_UPDATE);
gTickStart = HAL_GetTick();

/*
 * HAL_TIM_Base_Start (인터럽트 없는 버전)
 *   TIM3_CR1.CEN = 1 (카운터 시작) 만 한다.
 *   TIM3_DIER.UIE 는 0 그대로이므로 오버플로 때 UIF 플래그만 서고 TIM3_IRQn 은 발생하지 않는다.
 *   (01_TIM_TimeBase 의 HAL_TIM_Base_Start_IT 는 여기에 DIER.UIE = 1 을 더한다.)
 */
if (HAL_TIM_Base_Start(&htim3) != HAL_OK) {
    Error_Handler();
}
  1. 시작 전에 UIF를 지워 초기화로 남은 플래그가 첫 틱으로 세어지는 것을 막는다.
  2. HAL_TIM_Base_Start는 CEN만 켠다 (UIE 없음).
main.c — 폴링 루프
    if (__HAL_TIM_GET_FLAG(&htim3, TIM_FLAG_UPDATE) != RESET) {
        __HAL_TIM_CLEAR_FLAG(&htim3, TIM_FLAG_UPDATE);   /* TIM3_SR.UIF = 0 */

        gTimerCnt++;
        if (gTimerCnt == 1000) {                         /* 소프트웨어 분주: 1ms x 1000 = 1s */
            gTimerCnt = 0;
            HAL_GPIO_TogglePin(LD2_GPIO_Port, LD2_Pin);  /* GPIOA_ODR.ODR5 반전 */
            gSeconds++;

            /*
             * 경과 시간 출력 + 누락 확인
             *   이 printf 는 약 30자 x 87us(115200bps) = 2.6ms 동안 루프를 붙잡는다.
             *   그동안 UIF 가 2~3번 서지만 1번으로만 보이므로 매초 1~2ms 씩 틱을 놓친다.
             *   SysTick(HAL_GetTick) 은 인터럽트로 세므로 놓치지 않는다 -> 두 값의 차이(lag)가
             *   초마다 커지는 것으로 폴링 방식의 한계를 확인한다.
             */
            uint32_t elapsed = HAL_GetTick() - gTickStart;
            printf("[%lu s] tick=%lu ms lag=%ld ms\n", (unsigned long) gSeconds,
                    (unsigned long) elapsed, (long) (elapsed - gSeconds * 1000U));
        }
    }
}
  1. UIF를 확인하면 작업보다 먼저 지운다. 작업 중 새로 선 UIF를 보존하기 위함이다.
  2. 1000틱마다 LD2를 토글하고 tick과 lag를 출력한다.
  3. lag = SysTick 경과 − 초 × 1000이다.
출력 해석
TIM3 TimeBase start (1ms update, UIF polling, print every 1s)
[1 s] tick=1000 ms lag=0 ms
[2 s] tick=2003 ms lag=3 ms
[3 s] tick=3005 ms lag=5 ms
항목의미
tickHAL_GetTick() 경과 시간. 놓치지 않는 기준 시계이다.
lagtick − 초 × 1000. 폴링으로 놓친 1 ms 틱의 누적이다.

한 줄(약 29바이트)의 전송 시간은 29 × 86.8 µs ≈ 2.5 ms이다. 이 동안 UEV가 2~3번 발생하지만 UIF는 한 번으로 보이므로 매초 1~2 ms씩 lag가 커진다. (값은 예시이며 메시지 길이에 따라 달라진다.)

8. 실험

실험 A. printf 제거

루프 안의 printf를 제거하고 lag가 0으로 유지되는지 확인한다. 루프 한 바퀴가 1 ms보다 짧을 때만 유지된다.

실험 B. 클리어 순서 바꾸기

UIF를 작업 뒤에 지우도록 코드를 바꾸고 lag의 증가 속도를 비교한다. 시뮬레이터의 '일한 뒤 지운다'와 비교한다.

실험 C. 하드웨어 주기 늘리기

PSC=6399, ARR=9999로 바꾸어 UEV 간격을 1초로 만들면 lag가 사라지는가? 그 이유를 설명한다.

실험 D. 인터럽트 방식으로 전환

Start_IT와 콜백으로 바꾸고 같은 출력을 비교한다 (01 예제).

10. 확인 문제

문제 1. printf를 제거하면 lag가 0으로 유지되는가? 그 조건은?

루프 한 바퀴가 1 ms보다 짧으면 매 UIF를 놓치지 않고 확인하므로 유지된다.

문제 2. 틱을 놓치지 않는 방법 세 가지를 쓰시오.

① 인터럽트 방식 ② 하드웨어 주기를 1초로 늘리기(PSC=6399, ARR=9999) ③ UART 송신을 인터럽트·DMA로 바꿔 루프를 막지 않기.

문제 3. UIF 폴링 대신 경과 시간을 구하는 방법은?

CNT 값을 읽어 차이를 계산한다. 03 예제에서 다룬다.

문제 4. SR &= ~UIF 대신 SR = ~UIF를 쓰는 이유는?

읽기-수정-쓰기 사이에 다른 플래그가 서면 그 비트가 0으로 쓰여 지워질 수 있다. rc_w0 비트이므로 0을 쓴 비트만 지워지고 1을 쓴 비트는 유지되는 점을 이용한다.
