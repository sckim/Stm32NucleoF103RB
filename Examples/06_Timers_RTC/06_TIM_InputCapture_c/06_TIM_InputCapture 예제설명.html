입력 캡처: 엣지가 온 순간의 카운터 값으로 주파수를 잰다

04와 05는 타이머가 핀의 파형을 만드는 쪽이었다. 이 예제설명은 반대 방향을 다룬다. 핀으로 들어오는 신호의 상승 에지가 온 순간 TIM2의 카운터 값을 CCR1에 붙잡아 두고(캡처), 연속된 두 값의 차로 주기와 주파수를 계산한다. TIM3이 스스로 만든 PWM(PA6)을 점퍼선으로 PA0에 되먹임해 시험하는 06_TIM_InputCapture_c 예제를 해석한다. 이 예제의 테스트 신호 주파수는 소스와 설정 파일이 서로 다르다(7장의 경고 상자).

1. 문제: 주파수 측정2. 입력 캡처의 원리3. 클럭과 측정 범위4. 직접 만져 보기5. 레지스터 분석6. HAL이 해 주는 일7. 코드 읽기8. 실험9. 트러블슈팅10. 확인 문제

1. 문제: CPU가 엣지를 지켜볼 수 없다

외부 신호의 주파수를 재려면 두 엣지 사이의 시간을 알아야 한다. CPU가 핀을 계속 읽으며 엣지를 기다리면(폴링) 그동안 다른 일을 못 하고, 엣지가 온 시각도 루프 한 바퀴만큼 부정확하다. 입력 캡처는 엣지가 온 순간의 카운터 값을 하드웨어가 대신 기록한다. CPU는 나중에 그 값을 읽기만 하면 된다.

  • 입력 캡처가 04의 출력 비교와 같은 CCR을 반대 방향으로 쓰는 것임을 확인한다("이 시각에 이 일을 하라" ↔ "그 일이 이 시각에 일어났다").
  • 두 캡처값의 차가 주기이고, 16비트 뺄셈이 카운터가 한 번 넘어간 것을 저절로 보정함을 계산한다.
  • 카운터 클럭이 분해능과 최저 측정 주파수를 함께 정하는 맞바꿈을 계산한다.
  • HAL이 CC1 인터럽트를 콜백으로 연결하는 경로(TIM2_IRQHandler → HAL_TIM_IRQHandler → HAL_TIM_IC_CaptureCallback)를 따라간다.
  • 이 예제 코드가 가정하는 것(1카운트 = 1 µs, 신호 주기 < 65.5 ms)이 깨질 때 무슨 일이 생기는지 시뮬레이터로 확인한다.

2. 입력 캡처의 원리

용어하드웨어에서 일어나는 일이 예제에서
캡처입력단을 통과한 유효한 에지가 오는 순간 카운터 CNT 값이 CCR1에 복사된다(래치).TI1(PA0)의 상승 에지마다
캡처 플래그같은 순간 SR.CC1IF가 선다. DIER.CC1IE가 1이면 TIM2 인터럽트가 걸린다.콜백이 호출된다
주기연속된 두 캡처값의 차이다.Δ = now − last
카운터 넘침CNT가 ARR(65535)에서 0으로 돌아간다.16비트 뺄셈이 한 번의 넘침을 자동 보정한다
오버캡처값을 꺼내기 전에 다음 엣지가 오면 이전 값이 덮어써지고 SR.CC1OF가 선다.이 예제는 검사하지 않는다

그림 1. 상승 에지마다 CNT가 CCR1에 래치된다(위의 숫자). 첫 에지(60000) 뒤에 CNT가 넘쳐 0으로 돌아간 다음 두 번째 에지(4464)가 와도, 16비트 부호 없는 뺄셈은 10000을 낸다. 시간 축은 CNT 한 바퀴(65 536카운트)를 400 칸으로 그린 것이다. 값 10000은 100 Hz 신호를 1 MHz로 센 것이고, 숫자는 설명용이다.

주기 [카운트] = (now − last) mod 65536 주파수 f = f_CNT / 주기 예) last = 60000, now = 4464 → (4464 − 60000) mod 65536 = 10000 카운트 → f_CNT = 1 MHz이면 10 ms, 100 Hz

이 계산은 두 엣지 사이에 카운터가 한 번까지 넘칠 때만 맞다. 두 번 이상 넘치면 차이가 주기 모듈로 65536이 되어 참 주기와 달라진다. 구조의 일반 설명은 06_Timers_RTC 개념설명 2장의 "캡처"와 "분해능과 주파수의 맞바꿈"에 있다.

3. 클럭과 측정 범위

TIM2는 APB1에 연결된다. APB1 분주비가 2이므로 타이머 클럭은 ×2가 되어 64 MHz이다(05 예제설명 3장). PSC = 63이면 카운터 클럭이 64 MHz / 64 = 1 MHz이다.

항목값계산
카운터 클럭 f_CNT1 MHz64 MHz / (PSC + 1) = 64 MHz / 64
분해능1 µs1 / f_CNT
한 바퀴 시간65.536 ms(ARR + 1) / f_CNT = 65536 / 1 MHz
잴 수 있는 가장 낮은 주파수약 15.26 Hzf_CNT / 65536 (README의 "약 15.3 Hz")
측정 오차±1 카운트엣지가 카운터 눈금 사이 어디에 오는지 알 수 없다

±1 카운트는 입력 주파수가 높을수록 상대 오차를 키운다. 한 주기가 몇 카운트인가가 곧 분해능이다.

입력 주파수한 주기의 카운트 (1 MHz)±1 카운트의 상대 오차

PSC를 줄이면 f_CNT가 올라가 분해능이 좋아지지만 한 바퀴 시간이 짧아져 최저 측정 주파수가 올라간다. PSC를 키우면 반대이다. 높은 주파수는 분해능 때문에, 낮은 주파수는 넘침 때문에 어렵다. ISR이 초당 몇 번의 엣지까지 따라갈 수 있는지(최대 측정 주파수)는 네 근거 문서에 없다.

이 예제의 테스트 신호와 측정 타이머는 모두 같은 PCLK1 클럭에서 나오므로(TIM3과 TIM2 모두 PSC = 63), 주기가 정수 카운트로 정해져 차이값이 매번 같게 나올 것으로 예상한다(실측 전). 외부 신호라면 클럭이 서로 달라 N과 N+1 사이로 흔들린다.

4. 직접 만져 보기

아래 시뮬레이터는 입력 신호의 상승 에지 여섯 개에서 CCR1에 래치되는 값, 뺄셈, 그리고 이 예제 코드가 그대로 출력할 줄을 계산한다.

  1. 기본값(100 Hz, PSC = 63)에서 Δ가 매번 10000이고 period=10000 us freq=100 Hz가 나오는 것을 확인한다.
  2. 입력 신호를 3 kHz로 바꾸어, 주기가 정수 µs가 아니면 Δ가 333과 334 사이로 흔들리는 것을 본다.
  3. 10 Hz와 15 Hz로 바꾸어 한 주기가 65536카운트를 넘을 때 값이 틀려도 프로그램이 아무 경고 없이 값을 출력하는 것을 본다.
  4. 입력을 100 Hz로 되돌리고 PSC = 0으로 바꾼다. 64 MHz로 세면 한 주기가 640 000카운트라서 넘침이 여러 번 생긴다.
  5. PSC = 7로 바꾸어 코드의 상수 1000000이 f_CNT = 8 MHz에서 맞지 않는 것을 본다.

시뮬레이터 모델: 카운터는 t = 0에서 0으로 시작하고 f_CNT로 센다. CCR1 = ⌊t · f_CNT⌋ mod 65536. 첫 에지는 코드처럼 기준점으로만 쓴다. 출력은 코드와 같이 1000000 / Δ(정수 나눗셈)로 계산한다. ISR 지연, 오버캡처, 입력 필터는 모델에 없다.

위 값은 HAL의 동작에서 유도한 기대값이다. 이 예제는 컴파일만 확인했고 보드에서 실측하지 않았다. 디버거의 Peripheral/SFR 뷰에서 실제 값을 확인한다.

  • HAL_TIM_IC_Start_IT(&htim2, TIM_CHANNEL_1)은 DIER.CC1IE를 켜고, CCER.CC1E를 켜고, CR1.CEN을 켠다(슬레이브 모드가 아닐 때).
  • TIM2_IRQHandler는 HAL_TIM_IRQHandler(&htim2)만 부른다. HAL은 SR과 DIER를 읽어 CC1IF와 CC1IE가 모두 1이면 먼저 CC1IF를 지우고(SR에 0 쓰기), htim->Channel을 HAL_TIM_ACTIVE_CHANNEL_1로 바꾼다. CCMR1.CC1S가 0이 아니면 입력 캡처이므로 HAL_TIM_IC_CaptureCallback()을 부른다.
  • 그러므로 콜백이 불릴 때 CC1IF는 이미 0이다. 콜백은 CCR1만 읽는다(HAL_TIM_ReadCapturedValue가 TIM2->CCR1을 반환). CC1OF는 이 코드가 확인하지도 지우지도 않는다.
  • 온보드 PA0은 아두이노 A0 핀이다. PA6은 D12이다. PA0은 TIM2_CH1이자 WKUP 핀이다.

HAL 소스는 이 폴더에 Drivers가 없어 01_TIM_TimeBase/Drivers의 stm32f1xx_hal_tim.c에서 확인했다.

코드는 100 Hz이고 나머지 세 곳은 1 kHz이다. MX_TIM3_Init은 USER CODE 영역 밖이라 CubeMX에서 다시 Generate하면 .ioc 값(1 kHz)으로 덮어써진다. 이 예제설명은 지금의 main.c를 기준으로 쓴다. 따라서 점퍼를 연결하면 period=10000 us freq=100 Hz가 나올 것으로 예상한다(예상 출력이며 실측하지 않았다). 어느 쪽이 의도인지는 아직 정해지지 않았다. 1 kHz로 맞추면 이 문서의 10000은 1000으로, 100 Hz는 1000 Hz로 읽으면 된다. 이 문서에서 수치에 의존하는 곳은 이 상자, 5장 TIM3 표, 8장 실험 A·B, 4장 시뮬레이터의 첫 예시뿐이다.

  1. PWM을 먼저 시작하고 입력 캡처를 시작한다. 입력 캡처의 첫 에지는 기준점으로만 쓰인다.

  3. 마지막 주기 하나만 출력한다. 평균하지 않는다. 0.5초 동안 새 캡처가 없었으면 no signal on PA0이다.
  4. 주파수는 1000000UL / p이다. 이 상수는 카운터 클럭이 1 MHz라는 가정이다(PSC = 63일 때만 맞다).
main.c — 캡처 콜백 (ISR 문맥)
void HAL_TIM_IC_CaptureCallback(TIM_HandleTypeDef *htim)
{
  if (htim->Instance == TIM2 && htim->Channel == HAL_TIM_ACTIVE_CHANNEL_1)
  {
    uint16_t now = (uint16_t)HAL_TIM_ReadCapturedValue(htim, TIM_CHANNEL_1);
    if (first_edge)
    {
      first_edge = 0;
    }
    else
    {
      period_ticks = (uint16_t)(now - last_capture);
      have_sample = 1;
    }
    last_capture = now;
  }
}
  1. ISR(TIM2_IRQHandler)이 아니라 HAL이 ISR 안에서 부르는 콜백이다. 짧게 끝낸다.
  2. CCR1을 읽어 now에 담는다. 이 값이 엣지 순간의 CNT이다.
  3. 첫 에지는 비교할 이전 값이 없어 기준점으로만 저장한다.
  4. now - last_capture를 uint16_t로 잘라 모듈로 65536 뺄셈을 한다. 이것이 1장에서 말한 넘침 보정이다.

그림 2. 데이터 흐름. 보라색 상자는 하드웨어, 파란색 상자는 소프트웨어이다. 점퍼선 앞까지는 TIM3이 신호를 만들고, 점퍼선 뒤부터는 TIM2가 그 신호를 잰다. CPU는 콜백과 main 루프에서만 일한다.

PSC를 바꾸면 이 코드는 틀린다

README는 "입력 주파수에 맞춰 PSC를 조정"하라고 하지만, 소스의 계산식 1000000UL / p와 period_ticks 주석의 "[us]"는 카운터 클럭이 1 MHz일 때만 맞다. PSC를 바꾸면 f = f_CNT / p로 고쳐야 한다. 4장 시뮬레이터에서 PSC = 7을 넣어 확인한다.

8. 실험

실험 A. 기본 출력 확인

PA6과 PA0을 점퍼선으로 잇고 터미널(115200 8N1)을 연다. 지금의 main.c로는 0.5초마다 period=10000 us freq=100 Hz가 나올 것으로 예상한다. 두 타이머가 같은 클럭에서 나오므로 값이 매번 같은지 본다. 다르게 나오면 알려진 오차의 범위(±1카운트)와 비교한다.

실험 B. 테스트 신호를 1 kHz로 맞추기

htim3.Init.Period를 999로, sConfigOC.Pulse를 500으로 바꾼다(.ioc·주석의 값). period=1000 us freq=1000 Hz가 나와야 한다. 100 Hz일 때보다 ±1 카운트의 상대 오차가 10배 커진다(3장 표).

실험 C. 점퍼 빼기

점퍼를 빼면 no signal on PA0가 나올 것으로 예상하지만 확정할 수 없다. PA0은 풀업·풀다운이 없는 입력이라 떠 있는 핀이 잡음 엣지를 캡처할 수 있다. 확실히 보려면 PA0을 저항(예: 10 kΩ)으로 GND에 연결한다.

실험 D. 느린 신호 (넘침)

TIM3의 Prescaler를 639로 바꾸면(10 µs 눈금, 9999 → 10 Hz) 신호 주기가 100 000 µs이다. 이것은 TIM2의 65 536 µs 한 바퀴를 넘는다. 시뮬레이터로 예측한 출력은 period=34464 us freq=29 Hz이다. 프로그램은 경고 없이 틀린 값을 낸다.

실험 E. PSC를 바꾸어 분해능 높이기

TIM2의 Prescaler를 7로 바꾸면 f_CNT = 8 MHz이다. 100 Hz 신호의 한 주기는 80 000카운트라서 한 바퀴를 넘는다. 1 kHz 신호(실험 B)에서는 8 000카운트로 분해능이 8배 좋아진다. 어느 경우든 출력식은 8000000UL / p로 고쳐야 맞다.

실험 F. 하강 에지로 바꾸기

sConfigIC.ICPolarity를 TIM_INPUTCHANNELPOLARITY_FALLING으로 바꾼다. 듀티가 같은 한 주기이므로 주기 값은 변하지 않는다. 두 에지를 함께 보면 펄스 폭도 잴 수 있다(07, 10 예제).

10. 확인 문제

문제 1. 이전 캡처값이 60000이고 이번 캡처값이 4464이다. 주기(카운트)는? 1 MHz이면 몇 Hz인가?

(4464 − 60000) mod 65536 = 10000카운트이다. 1 MHz이면 10 ms, 100 Hz이다. 카운터가 한 번 넘친 것이 16비트 뺄셈으로 저절로 보정된다.

문제 2. 이 예제가 잴 수 있는 가장 낮은 주파수는? 더 낮은 신호를 재려면?

1 MHz / 65536 ≈ 15.26 Hz이다. PSC를 키워 f_CNT를 낮추면 한 바퀴가 길어져 더 낮은 주파수를 잴 수 있다(대신 분해능이 거칠어진다). 또는 03 예제처럼 갱신 인터럽트로 넘침 횟수를 세어 32비트로 확장한다.

문제 3. 입력이 10 kHz일 때 ±1 카운트의 상대 오차는? 분해능을 8배 높이려면 PSC는? 이때 최저 측정 주파수는?

한 주기가 100카운트이므로 ±1 카운트는 1 %이다. PSC = 7이면 f_CNT = 8 MHz로 한 주기가 800카운트가 되어 0.125 %이다. 최저 측정 주파수는 8 MHz / 65536 ≈ 122 Hz로 올라간다. 코드의 1000000UL은 8000000UL로 고쳐야 한다.

문제 4. 입력 신호가 10 Hz이고 PSC = 63이다. 프로그램은 무엇을 출력하는가? 왜 경고가 없는가?

한 주기는 100 000카운트이고 이것은 65 536을 한 번 넘는다. 뺄셈 결과는 100 000 mod 65536 = 34464이므로 period=34464 us freq=29 Hz가 출력된다. 프로그램은 넘침 횟수를 세지 않고 오버캡처 플래그도 보지 않으므로, 차이값이 참인지 알 방법이 없다.

문제 5. ICPolarity를 FALLING으로 바꾸면 측정한 주기가 달라지는가?

달라지지 않는다. 하강 에지 사이의 간격도 한 주기이다. 펄스 폭을 재려면 상승과 하강 두 에지를 모두 캡처해야 한다(07, 10 예제).

문제 6. main 루프가 __disable_irq()로 변수를 복사하는 이유는?

콜백이 period_ticks와 have_sample을 차례로 갱신하는데, main이 둘 사이에서 읽으면 새 주기에 옛 플래그가 짝지어질 수 있다. 인터럽트를 잠깐 막아 두 값을 한꺼번에 복사한다.
