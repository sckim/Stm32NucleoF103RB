DMA 메모리 복사: CPU 없이 1 KB를 옮기는 채널 하나

DMA(Direct Memory Access)는 CPU 대신 버스 마스터가 되어 데이터를 옮기는 하드웨어이다. 이 교안은 가장 단순한 형태인 메모리 → 메모리 복사로 DMA 채널의 구성 요소를 익힌다. 256워드(1 KB) 배열을 CPU 반복문과 DMA로 각각 복사하고, 복사하는 동안 CPU가 다른 일을 할 수 있는지를 free_loops로 확인한다. 이 예제의 핵심은 DMA가 CPU 반복문보다 빠르다는 것이 아니라, 전송 중에 CPU가 자유롭다는 것이다.

1. DMA가 필요한 이유

CPU가 메모리를 복사하면 명령어 하나하나가 일을 한다. 워드 하나를 옮기려면 읽기(LDR), 쓰기(STR), 인덱스 증가, 비교, 분기가 필요하다. 그동안 CPU는 다른 일을 할 수 없다. DMA는 “어디에서 어디로, 몇 개를, 어떤 폭으로”만 알려 주면 CPU 없이 버스를 직접 구동해 옮기고, 끝나면 인터럽트로 알려 준다.

이 저장소에서의 위치

DMA는 이 저장소에서 이미 몇 번 나왔다. 02_USART/04_USART_DMA_IdleLine_c는 UART 수신 바이트를, 03_ADC/04_ADC_DMA_TimTrigger는 ADC 결과를, 04_I2C_Communication/05_I2C_MPU6050_DMA_c는 I2C 수신 바이트를 DMA로 옮겼다. 그 예제들은 주변장치가 ‘요청’을 보내 DMA를 움직인다. 이 예제는 요청 없이 소프트웨어가 채널을 켜면 바로 시작하는 메모리 → 메모리 모드이므로, 주변장치 없이 DMA 채널 자체만 관찰하기 좋다.

2. 채널의 구성 요소

STM32F103RB의 DMA1에는 채널이 7개 있다(RM0008 13장). 한 채널은 아래 네 가지를 정하면 일할 수 있다.

구성 요소레지스터이 예제의 값
어디에서DMA1_CPAR1src 배열의 시작 주소
어디로DMA1_CMAR1dst_dma 배열의 시작 주소
몇 번DMA1_CNDTR1256 (전송 횟수이며 바이트 수가 아님)
어떻게DMA1_CCR1MEM2MEM=1, PINC=MINC=1, PSIZE=MSIZE=32비트, PL=High, CIRC=0
  • 데이터 폭(PSIZE/MSIZE): 한 번의 전송에서 옮기는 크기이다. 32비트면 한 번에 4바이트이다. 같은 1 KB를 8비트로 옮기면 CNDTR은 1024가 된다.
  • 주소 증가(PINC/MINC): 전송마다 주소를 데이터 폭만큼 늘릴지 정한다. 배열 복사는 양쪽 다 켠다. 끄면 같은 주소만 계속 읽거나 쓴다.
  • 우선순위(PL): 여러 채널이 동시에 요청할 때의 순서이다. 같은 우선순위면 채널 번호가 낮은 쪽이 먼저이다. 이 예제는 채널이 하나라 영향이 없다.
메모리 → 메모리에서 ‘주변장치 주소’의 뜻

이름이 헷갈린다. 메모리 → 메모리 모드에서도 레지스터 이름은 그대로라서 CPAR가 소스, CMAR가 목적지가 된다. 이 프로젝트가 쓰는 HAL(DMA_SetConfig)도 방향이 MEMORY_TO_PERIPH가 아니면 CPAR = SrcAddress, CMAR = DstAddress로 쓴다. 그리고 DMA_MEMORY_TO_MEMORY는 CCR.MEM2MEM 비트만 켜는 값이므로 CCR.DIR은 0 그대로이다. 그래서 PINC는 소스 주소(CPAR) 증가이고 MINC는 목적지 주소(CMAR) 증가이다.

메모리 → 메모리 모드의 규칙 (RM0008 13.3)
  • MEM2MEM=1이면 주변장치 요청을 기다리지 않고, EN을 쓰는 순간 전송이 시작되어 CNDTR이 0이 되면 멈춘다.
  • 원형(CIRC) 모드와 같이 쓸 수 없다. 02 예제처럼 계속 반복하려면 주변장치(타이머 등) 요청 방식이어야 한다.
  • 어느 채널로도 할 수 있다. 주변장치 요청이 필요 없으므로 채널 1이어도 된다.

3. 직접 만져 보기

아래 시뮬레이터는 32바이트를 옮기는 DMA 채널 하나를 한 번 전송씩 실행한다. CPAR, CMAR, CNDTR이 전송마다 어떻게 바뀌는지, 설정을 바꾸면 결과가 어떻게 틀어지는지 본다.

  1. 기본값(32비트, PINC 켬, MINC 켬)에서 한 전송을 여러 번 눌러 파랑(읽은 곳)과 청록(쓴 곳)이 4바이트씩 앞으로 가는 것과 CNDTR이 8에서 0으로 줄어드는 것을 본다. 0이 되면 TCIF1이 서고 EN이 내려간다.
  2. 데이터 폭을 8비트로 바꾼다. 같은 32바이트인데 CNDTR이 32가 된다. CNDTR은 바이트 수가 아니라 전송 횟수이다.
  3. PINC를 끄고 끝까지 실행한다. 소스에서 같은 첫 워드만 계속 읽어 목적지 전체가 src[0]의 반복으로 채워지고 검증이 FAIL이 된다.
  4. MINC를 끄고 끝까지 실행한다. 목적지 첫 워드만 계속 덮어써져 마지막 값만 남는다.

4. 레지스터 분석

DMA1 채널1 (기준 주소 DMA1 = 0x4002 0000, RM0008 13.4)

레지스터비트이 예제에서의 값·역할
DMA1_ISR (0x00)GIF1(0), TCIF1(1), HTIF1(2), TEIF1(3)채널1 상태 플래그. 전송이 끝나면 TCIF1 = 1. HAL이 DMA1_IFCR(0x04)에 1을 써서 지운다
DMA1_CCR1 (0x08)EN(0), TCIE(1), HTIE(2), TEIE(3), DIR(4), CIRC(5), PINC(6), MINC(7), PSIZE(9:8), MSIZE(11:10), PL(13:12), MEM2MEM(14)아래 표 참조
DMA1_CNDTR1 (0x0C)NDT[15:0]남은 전송 횟수. 256에서 시작해 한 번 전송할 때마다 1씩 감소한다. 최대 65535
DMA1_CPAR1 (0x10)PA[31:0]소스 주소(src)
DMA1_CMAR1 (0x14)MA[31:0]목적지 주소(dst_dma)

CCR1 값은 HAL이 단계별로 조립한다. 비트에서 직접 계산해 두면 디버거로 레지스터를 읽을 때 맞는지 검산할 수 있다.

시점켜진 비트CCR1
HAL_DMA_Init() 직후MEM2MEM(0x4000) + PL=High(0x2000) + MSIZE=32(0x0800) + PSIZE=32(0x0200) + MINC(0x80) + PINC(0x40)0x6AC0
HAL_DMA_Start_IT() 직후위에 TEIE(0x08) + TCIE(0x02) + EN(0x01). 반 완료 콜백이 없으므로 HTIE는 꺼 둔다0x6ACB
전송이 끝난 뒤하드웨어가 EN을 내리고 HAL이 TCIE/TEIE를 끈다0x6AC0
NVIC

HAL_NVIC_SetPriority(DMA1_Channel1_IRQn, 1, 0)과 HAL_NVIC_EnableIRQ가 NVIC->ISER[0]의 해당 비트(인터럽트 번호 11)를 켠다. 위 코드는 MX_DMA_Init() 안에 있다.

DMA 클럭

DMA1은 AHB 장치라 RCC_AHBENR.DMA1EN(bit 0)을 켜야 레지스터를 쓸 수 있다. __HAL_RCC_DMA1_CLK_ENABLE()이 이 일을 한다. 클럭을 켜기 전에 HAL_DMA_Init()을 부르면 설정이 반영되지 않는다.

5. HAL이 대신 해 주는 일

아래는 이 프로젝트가 빌드하는 STM32CubeF1 HAL(PlatformIO framework-stm32cubef1)의 stm32f1xx_hal_dma.c를 읽고 정리한 것이다.

HAL 함수하는 일 (레지스터)
MX_DMA_InitCubeMX가 만든 함수. RCC_AHBENR.DMA1EN 켜기 → hdma_memtomem_dma1_channel1 필드 채우기 → HAL_DMA_Init → NVIC 설정
HAL_DMA_Init핸들 값으로 CCR1을 한 번에 조립해 쓴다(위 표의 0x6AC0). 채널 번호로 DmaBaseAddress와 ChannelIndex를 정한다
HAL_DMA_RegisterCallback핸들의 XferCpltCallback 함수 포인터에 dma_done_cb를 넣는다. 레지스터는 건드리지 않는다. 채널이 READY 상태가 아니면(전송 중이면) HAL_ERROR를 반환하고 등록하지 않는다
HAL_DMA_Start_IT상태가 READY인지 확인 → CCR1.EN = 0 → DMA_SetConfig: IFCR로 플래그 지움, CNDTR1 = 256, CPAR1 = src, CMAR1 = dst_dma → TCIE/TEIE 켬(HT 콜백이 NULL이면 HTIE는 끔) → CCR1.EN = 1. 이 순간 전송이 시작된다
HAL_DMA_IRQHandlerDMA1_ISR의 플래그와 CCR1의 인터럽트 허용 비트를 함께 확인. TC이면 일반 모드에서 TCIE/TEIE를 끄고 상태를 READY로 바꾼 뒤 IFCR로 플래그를 지우고 XferCpltCallback()을 부른다
고정 이름 콜백이 아니라 등록형 콜백인 이유

UART의 HAL_UART_RxCpltCallback()처럼 weak 함수를 덮어쓰는 방식은 주변장치 드라이버가 정의해 둔 이름이다. 순수 DMA 핸들(DMA_HandleTypeDef)에는 그런 weak 함수가 없다. 주변장치 드라이버(UART, ADC 등)는 자기 콜백을 핸들의 함수 포인터에 내부에서 채워 넣어 쓴다. 우리가 DMA를 직접 쓰면 HAL_DMA_RegisterCallback()으로 포인터를 직접 채워야 한다.

6. ISR과 콜백

정상 흐름에서 CPU가 깨어나는 인터럽트는 DMA1 채널1의 TC 하나뿐이다. 진짜 ISR과 등록한 콜백을 구분해 둔다.

  1. 1
    DMA가 마지막 워드를 쓴다HWCNDTR1 = 0이 되어 DMA1_ISR.TCIF1이 선다. CCR1.EN은 하드웨어가 내린다. CCR1.TCIE = 1이므로 인터럽트 요청이 NVIC로 간다.
  2. 2
    DMA1_Channel1_IRQHandler() — 진짜 ISRISRstm32f1xx_it.c. 벡터 테이블에서 바로 불리며 HAL_DMA_IRQHandler(&hdma_memtomem_dma1_channel1)만 호출한다. NVIC 우선순위 1.
  3. 3
    HAL_DMA_IRQHandler()ISR 문맥TCIF1과 TCIE를 확인하고, 일반 모드이므로 TCIE/TEIE를 끄고 상태를 READY로 바꾼 뒤 플래그를 지운다. 그다음 등록된 함수 포인터를 부른다.
  4. 4
    dma_done_cb() — 등록한 콜백main.c사용자가 만든 함수이다. ISR이 아니지만 ISR 문맥에서 실행된다. dma_done = 1만 한다. 판정과 출력은 main이 한다.

콜백에서 왜 플래그만 세우는가

dma_done은 ISR 문맥(콜백)이 쓰고 main이 읽으므로 volatile이어야 한다. 빼면 컴파일러가 while (!dma_done)을 무한 루프로 최적화해 버릴 수 있다. 콜백이 UART 출력처럼 긴 일을 하면 다른 인터럽트의 지연이 커지므로, 콜백은 짧게 끝내고 나머지는 main에서 한다.

7. 코드 읽기

계층은 HAL + DMA이다. 사용자 코드는 모두 /* USER CODE BEGIN ... */ 영역 안에 있다. 오른쪽은 각 줄이 다루는 레지스터·비트이다.

Core/Src/main.c — USER CODE BEGIN PD / PV
#define N_WORDS 256

static uint32_t src[N_WORDS];
static uint32_t dst_cpu[N_WORDS];
static uint32_t dst_dma[N_WORDS];
static volatile uint8_t dma_done;
  1. 256워드 × 4바이트 = 1 KB
  2. DMA의 소스·목적지는 함수가 끝나도 유효해야 하므로 지역 변수가 아니라 전역(static)이다
  3. CNDTR1 = 256, 전송 폭은 워드(32비트)
  4. 콜백(ISR 문맥)과 main이 공유하는 플래그라 volatile
Core/Src/main.c — USER CODE BEGIN 0 (콜백과 측정)
static void dma_done_cb(DMA_HandleTypeDef *hdma)
{ (void)hdma; dma_done = 1; }

/* (1) CPU 복사 */
volatile uint32_t *d = dst_cpu;
t0 = DWT->CYCCNT;
for (i = 0; i < N_WORDS; i++) d[i] = src[i];
cpu_cycles = DWT->CYCCNT - t0;

/* (2) DMA 복사 */
dma_done = 0;
t0 = DWT->CYCCNT;
HAL_DMA_Start_IT(&hdma_memtomem_dma1_channel1,
    (uint32_t)src, (uint32_t)dst_dma, N_WORDS);
while (!dma_done) free_loops++;
dma_cycles = DWT->CYCCNT - t0;
  1. 이 함수는 ISR 문맥에서 불리는 등록형 콜백이다. 플래그만 세운다
  2. volatile 포인터로 쓰면 컴파일러가 반복문을 memcpy로 바꾸거나 지우지 못한다
  3. DWT->CYCCNT: 코어 사이클 카운터. 64 MHz에서 1 사이클은 15.6 ns
  4. 이 줄이 CCR1.EN = 1을 쓰며 전송을 시작한다. 반환까지 걸리는 시간은 짧다
  5. free_loops는 DMA가 일하는 동안 CPU가 반복문을 돈 횟수이다. CPU가 풀려난 증거이다
  6. 이 루프가 SRAM을 읽고 쓰는 동안은 DMA와 버스를 두고 경합한다. 측정된 DMA 시간이 길어질 수 있는 이유이다
Core/Src/main.c — USER CODE BEGIN 2
CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
DWT->CYCCNT = 0;
DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;

HAL_DMA_RegisterCallback(&hdma_memtomem_dma1_channel1,
    HAL_DMA_XFER_CPLT_CB_ID, dma_done_cb);

for (i = 0; i < N_WORDS; i++)
    src[i] = 0xA5000000u | i;
run_test();
  1. DWT 사용 허가: DEMCR.TRCENA(bit 24) = 1
  2. 카운터 시작: DWT_CTRL.CYCCNTENA(bit 0) = 1
  3. TC 콜백 등록. 함수 포인터만 바꾸고 레지스터는 건드리지 않는다
  4. 소스 값 = 상위 바이트 0xA5 + 인덱스. 복사가 어긋나면 값만 봐도 어느 칸인지 알 수 있다
Core/Src/main.c — 검증과 출력
int ok = (memcmp(src, dst_dma, sizeof src) == 0);
snprintf(msg, sizeof msg,
  "CPU=%lu cyc  DMA=%lu cyc  (CPU free loops=%lu)  verify=%s\r\n",
  cpu_cycles, dma_cycles, free_loops, ok ? "OK" : "FAIL");
  1. Cortex-M3에는 데이터 캐시가 없으므로 TC 직후 memcmp로 바로 비교해도 된다. 캐시가 있는 코어(Cortex-M7 등)에서는 캐시를 비우고 무효화하는 작업이 추가로 필요하다
  2. 출력은 115200 8N1로 ST-Link 가상 COM 포트에 나간다

8. 실험

준비: Nucleo-F103RB를 USB로 연결하고 터미널을 115200 8N1로 연다. 별도 배선은 없다. 부팅 시 한 번 측정하고, B1(PC13)을 누를 때마다 다시 측정한다. 아래 출력의 ...은 보드에서 읽을 값이다. 값은 여기에 적지 않았으니 직접 재서 채운다.

실험 A. 기본 출력과 free_loops

CPU=... cyc  DMA=... cyc  (CPU free loops=...)  verify=OK

verify=OK가 먼저 확인할 것이다. free_loops가 0이 아니면 DMA가 도는 동안 CPU가 반복문을 돈 것이다. 출력값으로 워드당 사이클을 어림해 시뮬레이터 슬라이더(3절)에 넣어 본다. CPU 사이클 ÷ 256 = CPU 복사의 워드당 사이클, DMA 사이클 ÷ 256 = (오버헤드를 포함한) DMA의 워드당 사이클이다.

실험 B. 크기를 바꿔 손익분기점 찾기

N_WORDS를 16, 64, 256, 1024로 바꿔(배열 선언도 같이 커진다) 각각 측정한다. DMA에는 크기와 상관없는 고정 비용(채널 설정, 인터럽트 진입과 복귀)이 있으므로, 작은 N에서는 CPU 복사가 더 짧을 수 있다. 어느 N에서 뒤집히는지 표로 만들고 3절 모델의 손익분기 N과 비교한다.

실험 C. 주소 증가를 끈다

CubeMX에서 DMA1 채널1의 Peripheral Increment Address를 끄고(PINC = 0) 재생성한다. verify=FAIL이 나와야 한다. dst_dma를 시리얼로 출력하게 고치면 전체가 src[0] 값 하나로 채워진 것을 볼 수 있다. 이어서 Memory Increment를 끄면(MINC = 0) 목적지의 첫 워드만 마지막 소스 값으로 덮어써지고 나머지는 0으로 남는다. 3절 시뮬레이터가 보여 준 결과와 같은지 확인한다.

실험 D. 데이터 폭을 8비트로

Data Width를 Byte로 바꾸고 HAL_DMA_Start_IT()의 마지막 인자를 N_WORDS * 4로 바꾼다. 그대로 두면 256바이트(= 64워드)만 옮겨 verify=FAIL이 난다. CNDTR은 바이트 수가 아니라 전송 횟수임을 확인하는 실험이다. 전송 횟수가 4배가 되므로 DMA 시간도 달라지는지 본다.

실험 E. 전송 중 다른 일을 시킨다

DMA 대기 루프를 while (!dma_done) { HAL_GPIO_TogglePin(LD2_GPIO_Port, LD2_Pin); }로 바꾼다. LD2(PA5, D13)를 AD2 오실로스코프로 보면 DMA가 도는 동안 핀이 토글되는 것이 보인다. CPU 복사 구간(for 루프)에서는 같은 핀을 건드릴 수 없다. 이 차이가 DMA의 목적이다.

9. 트러블슈팅

증상원인조치
verify=FAILPINC/MINC가 꺼짐, 전송 폭과 개수가 맞지 않음(실험 C, D), 완료 전에 비교함DMA1_CCR1을 디버거로 읽어 0x6ACB와 비교. CNDTR이 전송 횟수임을 확인
프로그램이 while (!dma_done)에서 멈춤콜백 등록을 안 함, NVIC에서 DMA1_Channel1_IRQn이 꺼짐, 컴파일러가 dma_done을 레지스터에 캐시(volatile 누락)등록 줄과 MX_DMA_Init 순서 확인. dma_done 선언 확인
Error_Handler()로 빠짐HAL_DMA_Start_IT()가 HAL_BUSY 반환: 이전 전송이 아직 끝나지 않았거나, 핸들이 READY가 아님콜백이 불린 뒤(상태 READY) 다음 전송을 시작하는지 확인
시간 값이 말이 안 됨DWT 카운터가 꺼져 있음(0만 출력), 32비트 오버플로(약 67초)DEMCR.TRCENA와 CYCCNTENA 설정 확인. 측정은 짧게
HardFault소스·목적지가 존재하지 않는 주소 또는 지역 변수(스택)에 놓임. 전송 폭에 맞지 않게 정렬되지 않은 주소전역 배열 사용. 32비트 전송이면 4바이트 정렬 확인
DMA 시간이 CPU 시간보다 길다N이 작아 고정 오버헤드가 큼. 대기 루프가 같은 SRAM 버스를 써서 DMA가 느려짐실험 B로 N을 키워 본다. 이 예제의 목적은 속도가 아니라 CPU 해방임을 기억한다

10. 확인 문제

먼저 스스로 답을 정해 본 뒤 펼쳐 확인한다.

문제 1. 1 KB를 32비트 폭으로 옮길 때 CNDTR은 얼마인가? 8비트 폭이면?

32비트면 1024 ÷ 4 = 256, 8비트면 1024이다. CNDTR은 바이트 수가 아니라 전송 횟수이다.

문제 2. 메모리 → 메모리 모드에서 소스와 목적지 주소는 어느 레지스터에 쓰는가?

소스는 CPAR, 목적지는 CMAR이다. 레지스터 이름은 주변장치/메모리이지만 이 모드에서는 ‘읽는 쪽’과 ‘쓰는 쪽’으로 쓰인다. HAL은 DMA_MEMORY_TO_MEMORY일 때 CCR.DIR을 0으로 두고 CPAR = Src, CMAR = Dst로 쓴다.

문제 3. 메모리 → 메모리 모드를 원형 모드와 함께 쓸 수 없는 이유를 설명하라.

이 모드는 주변장치의 요청 없이 EN을 쓰는 순간 시작해 CNDTR이 0이 될 때까지 최고 속도로 돈다. 원형 모드로 두면 0이 되자마자 다시 채워져 멈추지 않고 버스를 계속 점유한다. RM0008도 두 모드를 동시에 쓰지 말라고 한다. 주기적으로 반복하려면 타이머 같은 요청원이 필요하다(02 예제).

문제 4. PINC = 0, MINC = 1로 256워드를 복사하면 dst_dma에 무엇이 들어가는가?

소스 주소가 늘지 않으므로 src[0](= 0xA5000000)만 256번 읽는다. dst_dma 전체가 0xA5000000으로 채워진다. memcmp가 어긋나므로 verify=FAIL이다.

문제 5. dma_done에서 volatile을 빼면 어떤 일이 생길 수 있는가?

컴파일러는 while (!dma_done) 루프 안에서 값이 바뀌지 않는다고 보고 한 번만 읽어 무한 루프로 만들 수 있다. 값은 ISR 문맥(콜백)에서 바뀌므로 컴파일러가 알 수 없다. volatile이 매번 메모리에서 읽게 한다.

문제 6. 이 예제에서 HAL_DMA_Start_IT() 직후 DMA1_CCR1의 값은? (비트 계산으로 구하라)

0x4000(MEM2MEM) + 0x2000(PL=High) + 0x0800(MSIZE=32) + 0x0200(PSIZE=32) + 0x0080(MINC) + 0x0040(PINC) + 0x0008(TEIE) + 0x0002(TCIE) + 0x0001(EN) = 0x6ACB이다. HTIE(0x04)는 반 완료 콜백을 등록하지 않았으므로 꺼져 있다.

문제 7. DMA 복사가 CPU 복사보다 느리게 나올 수 있는 이유를 두 가지 들라.

(1) 고정 오버헤드: 채널 설정과 인터럽트 진입·복귀가 N과 무관하게 든다. 작은 N에서는 이것이 복사 자체보다 크다. (2) 버스 경합: 소스와 목적지가 모두 SRAM이라 DMA가 읽고 쓰는 동안 CPU(대기 루프)도 SRAM을 쓰면 버스 매트릭스가 둘을 번갈아 중재한다. 그래서 이 예제의 평가 기준은 시간이 아니라 free_loops이다.

문제 8. 콜백 dma_done_cb는 ISR인가? 어느 문맥에서 실행되는가?

진짜 ISR은 stm32f1xx_it.c의 DMA1_Channel1_IRQHandler이다. dma_done_cb는 HAL_DMA_IRQHandler가 함수 포인터로 부르는 사용자 함수이며, ISR 안에서 호출되므로 ISR 문맥에서 실행된다. 그래서 짧게 끝내야 하고 공유 변수는 volatile이어야 한다.
