원형 DMA와 핑퐁 버퍼: 타이머가 박자를 맞추고 DMA가 포트를 구동한다

01 예제의 DMA는 한 번 옮기면 끝났다. 이 교안은 DMA가 타이머의 박자에 맞춰 끝없이 반복하는 구성을 다룬다. TIM2가 10 kHz로 DMA 요청을 내면 DMA1 채널2가 64샘플 버퍼의 값을 GPIOC->ODR에 하나씩 쓴다. CPU는 파형을 만들지 않고, 반쯤 보냈을 때(HT)와 끝까지 보냈을 때(TC)의 인터럽트에서 이미 보낸 쪽 절반만 새 패턴으로 채운다. 이것이 핑퐁(더블 버퍼) 구조이다.

왜 HAL_TIM_Base_Start_DMA()를 쓰지 않는가

HAL에는 HAL_TIM_Base_Start_DMA(htim, pData, Length)가 있다. 그러나 이 함수는 목적지를 TIMx->ARR로 고정하고, DMA 핸들의 XferCpltCallback/XferHalfCpltCallback을 타이머 드라이버 내부 함수로 덮어쓴다. 타이머 주기(ARR)를 DMA로 바꾸는 용도이지 GPIO를 구동하는 용도가 아니다. 그래서 이 예제는 같은 일을 직접 한다: HAL_DMA_Start_IT()로 목적지를 &GPIOC->ODR로 지정하고, __HAL_TIM_ENABLE_DMA()로 DIER.UDE를 켜고, HAL_TIM_Base_Start()로 카운터를 시작한다.

2. 타이밍 계산

이 예제의 모든 숫자는 TIM2 클럭 하나에서 나온다.

  1. TIM2 클럭 = 64 MHz. SYSCLK = HCLK = 64 MHz, APB1 분주비 2이므로 PCLK1 = 32 MHz이다. 그러나 APB 분주비가 1이 아니면 타이머 클럭은 PCLK의 2배가 된다(RM0008 RCC). 그래서 TIM2는 64 MHz로 동작한다.
  2. 업데이트 주파수 = 64 MHz ÷ (PSC+1 = 64) ÷ (ARR+1 = 100) = 10 kHz. 샘플 간격 100 µs.
  3. 한 반(32샘플) = 32 × 100 µs = 3.2 ms. 한 바퀴(64샘플) = 6.4 ms.
  4. HT, TC 발생률 = 한 바퀴에 각각 1번 → 1 ÷ 6.4 ms ≈ 156.25 /s씩. 인터럽트는 3.2 ms 간격으로 HT, TC가 번갈아 온다.
  5. 패턴 반복 주파수 = 1 ÷ 6.4 ms ≈ 156 Hz. (램프·삼각파는 버퍼 한 바퀴가 곧 한 주기이다.)
채우기 마감 시간 (deadline)

HT 콜백이 앞 절반을 채우기 시작하면, DMA가 뒤 절반 32샘플을 다 보내고 앞 절반으로 돌아올 때까지의 3.2 ms 안에 채우기를 끝내야 한다. fill_half()는 32번 도는 간단한 반복문이라 이 시간에 비해 훨씬 짧을 것으로 예상되지만, 실제 소요 시간은 핀을 토글해 직접 재야 한다(9절 실험 D). 샘플 주기를 줄이거나 채우는 계산이 무거워지면 마감이 줄어든다.

3. 핑퐁 원리

버퍼 하나를 DMA가 읽는 동안 CPU가 같은 버퍼를 고치면 읽는 도중에 값이 바뀐다. 이를 막으려고 버퍼를 둘로 나눠 한쪽을 DMA가 읽는 동안 다른 쪽을 CPU가 채운다. 방향이 번갈아 바뀌므로 핑퐁이라 부른다. 이 예제는 64샘플 하나를 반으로 쪼갠 구조이다.

구간DMA가 읽는 곳CPU가 채우는 곳신호
① 샘플 0~31 전송 중앞 절반 buf[0..31](직전에 뒤 절반을 채움)–
② 31번째 전송 직후뒤 절반 buf[32..63]로 이동앞 절반 buf[0..31] ← half_cbHTIF2 (CNDTR = 32)
③ 샘플 32~63 전송 중뒤 절반(앞 절반은 이미 채움)–
④ 63번째 전송 직후CNDTR이 64로 재장전, 앞 절반으로 복귀뒤 절반 buf[32..63] ← full_cbTCIF2 (CNDTR = 0 → 64)
  • HT 콜백은 앞 절반(fill_half(&buf[0], 0)), TC 콜백은 뒤 절반(fill_half(&buf[N/2], N/2))을 채운다. 헷갈리기 쉬운 부분이다. 신호가 ‘지금 보내고 있는 쪽’이 아니라 ‘방금 다 보낸 쪽’을 알려 주기 때문이다.
  • 채우기가 반 주기(3.2 ms)보다 오래 걸리면 다음 콜백이 밀려 쌓이다가, 어느 순간 DMA가 아직 새 값이 쓰이지 않은 칸을 그대로 내보낸다. 이전 패턴이 섞인 파형이 나온다. 4절 시뮬레이터에서 ‘채우기 시간’ 슬라이더로 확인한다.
  • 패턴을 바꾸는 순간(main이 pattern을 바꿈)에도 한 바퀴 동안은 앞뒤 절반의 패턴이 다르다. 콜백이 다음 차례의 절반부터 새 패턴으로 채우기 때문이다.

4. 직접 만져 보기

64칸 링 버퍼를 DMA 포인터가 한 칸씩 돌며 값을 ODR에 쓴다. 칸의 색은 그 칸을 채운 패턴(보라 = 나이트라이더, 주황 = 이진 램프, 청록 = 삼각파)이다.

  1. 반 버퍼를 눌러 포인터가 32칸 움직이면 CNDTR이 32가 되고 HT가 오는 것을 본다. 방금 보낸 앞 절반이 새로 채워진다(칸이 다시 칠해진다).
  2. 한 바퀴까지 가면 CNDTR이 0에서 64로 되돌아가고 TC가 온다. 이번에는 뒤 절반이 채워진다.
  3. 패턴 바꾸기를 누르고 계속 진행한다. 새 패턴은 비워진 절반부터 반영되므로 한 바퀴 동안 두 색이 섞여 있다.
  4. 채우기 시간을 32틱(3.2 ms)보다 크게(예: 45) 올리고 한 바퀴를 여러 번 누른다. 점선 칸은 아직 채우기를 기다리는 칸이다. 콜백 하나가 반 주기보다 오래 걸리면 다음 콜백이 밀려 대기가 쌓이고, 몇 바퀴 뒤부터 DMA가 아직 못 채운 칸을 읽어 빨간 칸(오래된 값을 내보낸 칸)이 생긴다. 오른쪽 위 카운트와 ODR 파형이 어긋난다.

GPIOC->ODR 전체를 쓰는 것의 함정 두 가지

(1) 상위 8비트도 쓴다. 반워드 전송이라 PC8~PC15 비트도 0으로 쓰인다. 그 핀이 출력으로 쓰이고 있다면 이 값으로 끌려간다.

(2) 입력 풀업/풀다운 핀의 방향이 바뀐다. 입력 풀업/풀다운 모드에서는 해당 ODR 비트가 풀업(1)/풀다운(0)을 고른다(RM0008 GPIO 포트 비트 설정 표). PC8~PC15를 풀업 입력으로 쓰고 있다면 0이 쓰이는 순간 풀다운으로 바뀐다. 이 예제의 PC13(B1)은 리셋 상태(부동 입력)라 영향이 없다. 필요한 비트만 건드리려면 BSRR를 목적지로 쓴다(9절 실험 E).

반워드 쓰기가 APB 레지스터에 통하는 이유

GPIO 레지스터는 32비트인데 DMA는 16비트로 쓴다. RM0008 3.1에 따르면 APB 레지스터에 16비트·8비트 접근을 하면 브리지가 그 데이터를 32비트 값으로 복제해 전달한다. 상위 16비트는 예약 영역이라 무시되므로 ODR 하위 16비트에 원하는 값이 들어간다. 이 복제 때문에 BSRR에 반워드로 쓰면 안 된다(상위·하위가 같은 값이 되어 set과 reset이 동시에 걸림).

아래는 이 프로젝트가 빌드하는 STM32CubeF1 HAL의 stm32f1xx_hal_dma.c, stm32f1xx_hal_tim.c를 읽고 정리한 것이다.

이 예제는 HAL_DMA_RegisterCallback으로 HT·TC 콜백을 먼저 등록하고 나서 HAL_DMA_Start_IT를 부른다. 순서를 뒤집으면 두 가지가 어긋난다. (1) Start_IT 시점에 반 완료 콜백이 NULL이라 HTIE가 꺼진 채로 시작하여 HT 인터럽트가 영영 오지 않는다. (2) 원형 DMA는 시작 후 READY가 아니므로 나중에 하는 등록은 HAL_ERROR로 거부된다. 결과적으로 앞 절반이 한 번도 갱신되지 않는다.

7. ISR과 콜백

8. 코드 읽기

계층은 HAL + TIM + DMA이다. 사용자 코드는 모두 /* USER CODE BEGIN ... */ 영역 안에 있다. 오른쪽은 각 줄이 다루는 레지스터·비트이다.

Core/Src/main.c — USER CODE BEGIN PD / PV
#define N 64               /* 전체 (반 = 32) */

static uint16_t buf[N];
static volatile uint8_t  pattern;
static volatile uint32_t half_count, full_count;
  1. CNDTR2 = 64. 반 버퍼는 32샘플
  2. DMA 소스. 반워드(16비트) 배열이어야 MSIZE = 16과 맞다. 전역이어야 한다
  3. main이 쓰고 콜백이 읽음 → volatile
  4. 콜백이 올리고 main이 출력 → volatile
Core/Src/main.c — USER CODE BEGIN 0 (패턴과 콜백)
static void fill_half(uint16_t *p, uint32_t start)
{
  for (i = 0; i < N/2; i++) {
    k = start + i;
    switch (pattern) {
    case 0: v = 1u << ((k/4) & 7);      break;
    case 1: v = (k*4) & 0xFF;          break;
    default: t = k & 0x3F;
        v = (t < 32 ? t : 63 - t) * 8;
    }
    p[i] = v;
  }
}
static void half_cb(DMA_HandleTypeDef *h)
{ fill_half(&buf[0], 0);        half_count++; }
static void full_cb(DMA_HandleTypeDef *h)
{ fill_half(&buf[N/2], N/2);    full_count++; }
  1. start는 이 절반이 패턴 안에서 시작하는 샘플 번호이다. 앞 절반은 0, 뒤 절반은 32
  2. 나이트라이더: 4샘플(400 µs)마다 켜지는 비트가 한 칸 이동 (PC0→PC7 반복, 한 바퀴 3.2 ms)
  3. 이진 램프: 샘플마다 +4. 0에서 252까지 올라간 뒤 떨어지는 톱니파 (6.4 ms)
  4. 삼각파: 0..248..0 (피크 248이 2샘플 연속). 병렬 DAC에 연결하면 삼각 신호
  5. HT 콜백 = 앞 절반을 채움 (방금 앞 절반을 다 보냈다)
  6. TC 콜백 = 뒤 절반을 채움 (방금 뒤 절반을 다 보냈다). 둘 다 ISR 문맥에서 실행
Core/Src/main.c — USER CODE BEGIN 2 (시작 순서가 중요)
fill_half(&buf[0], 0);
fill_half(&buf[N/2], N/2);

HAL_DMA_RegisterCallback(&hdma_tim2_up,
    HAL_DMA_XFER_HALFCPLT_CB_ID, half_cb);
HAL_DMA_RegisterCallback(&hdma_tim2_up,
    HAL_DMA_XFER_CPLT_CB_ID, full_cb);

HAL_DMA_Start_IT(&hdma_tim2_up, (uint32_t)buf,
    (uint32_t)&GPIOC->ODR, N);
__HAL_TIM_ENABLE_DMA(&htim2, TIM_DMA_UPDATE);
HAL_TIM_Base_Start(&htim2);
  1. DMA가 읽기 시작하기 전에 두 절반을 첫 패턴(0)으로 채워 둔다
  2. 콜백 등록(레지스터는 안 건드림). Start_IT보다 먼저: HT 콜백이 있어야 CCR2.HTIE가 켜진다
  3. DMA 시작: CPAR2 = &GPIOC->ODR, CMAR2 = buf, CNDTR2 = 64, CCR2.EN = 1
  4. TIM2->DIER.UDE(bit 8) = 1: 업데이트마다 DMA 요청
  5. TIM2->CR1.CEN = 1: 이 줄에서 파형이 시작된다
Core/Src/main.c — USER CODE BEGIN 3 (main 루프)

  1. 1초마다 패턴을 바꾼다. 콜백은 다음에 채우는 절반부터 새 패턴을 쓴다
  2. t_sw += 1000: 누적 방식이라 UART 지연이 있어도 주기가 밀리지 않는다
  3. 출력되는 이름은 방금 바꾼 새 패턴이고, HT/TC는 부팅 이후 누적 횟수(초기화하지 않음)이다

9. 실험

배선: 1절의 PC0~PC7 + GND를 LED 또는 로직 분석기에 연결한다. 터미널은 115200 8N1이다. 아래 줄은 형식을 보여 주는 예이고 ...은 보드에서 읽는다.

실험 A. UART 출력으로 HT/TC 비율 확인

pattern=binary ramp  HT=~156 TC=~156 (기대: 각각 약 156/s)
pattern=triangle  HT=~312 TC=~312 ...
pattern=knight-rider  HT=~469 TC=~469 ...

값은 누적이므로 줄이 하나 올 때마다 약 156씩 늘어야 한다(156.25 × 시간). 첫 줄의 이름이 binary ramp인 것은 이상이 아니다. 부팅 직후의 패턴 0(나이트라이더)이 1초 동안 나간 뒤에 새 패턴 1의 이름이 찍히기 때문이다. HT와 TC 횟수가 같은 속도로 늘어나는지, 둘의 차이가 1을 넘지 않는지 본다.

실험 B. 로직 분석기로 세 패턴 보기

PC0~PC7을 8채널로 캡처한다(샘플링 ≥ 200 kHz). 확인할 것:

  • 나이트라이더: 한 번에 한 비트만 High, 400 µs마다 한 칸 이동, 8칸 한 바퀴가 3.2 ms
  • 이진 램프: PC0, PC1은 항상 Low. PC2는 샘플마다 토글(5 kHz 사각파), PC7은 3.2 ms High / 3.2 ms Low(156 Hz)
  • 삼각파: 하위 3비트(PC0~PC2)는 항상 Low (값에 8을 곱했기 때문). 패턴이 바뀔 때 한 바퀴(6.4 ms) 동안 앞뒤 절반이 다른 패턴인 것을 찾는다

실험 C. main이 오래 멈춰도 파형은 계속된다

main 루프에 HAL_Delay(500) 같은 긴 블로킹을 넣어도 LED/분석기의 파형은 끊기지 않고 같은 패턴을 반복한다. DMA와 타이머가 하드웨어로 돌기 때문이다. 단, 콜백(ISR)은 계속 불리므로 pattern을 바꾸는 main이 멈춘 동안은 패턴이 바뀌지 않을 뿐이다. 이 점을 CPU가 타이머 인터럽트로 직접 GPIO를 쓰는 방식과 비교한다. 후자는 인터럽트 지연의 흔들림이 파형에 그대로 나타난다.

실험 D. 채우기 시간 재기

fill_half() 호출 앞뒤에서 LD2(PA5)를 SET/RESET 하여 AD2 오실로스코프로 펄스 폭을 잰다. 이 폭이 3.2 ms 마감의 몇 %인지 계산한다. 이어서 fill_half() 안에 for (volatile int w = 0; w < 100000; w++) 같은 지연을 넣고 폭을 늘려 가며 파형이 깨지기 시작하는 지점을 찾는다. 반 주기(3.2 ms)를 넘기면 바로 깨지는 것이 아니라 대기가 쌓여 몇 바퀴 뒤부터 깨진다. 4절 시뮬레이터의 ‘채우기 시간’과 비교한다. 지연은 이렇게 반복문으로 만든다. 콜백 안에서 길게 기다리는 습관은 좋지 않다.

실험 E. BSRR로 필요한 비트만 쓰기

목적지를 &GPIOC->BSRR로, 버퍼를 uint32_t로, PSIZE=MSIZE를 32비트로 바꾼다(반워드 쓰기는 5절의 복제 때문에 안 된다). 8비트 값 v에 대한 워드는 v | ((~v & 0xFF) << 16)이다. 예를 들어 v = 0x05이면 0x00FA0005이다(하위 16비트 = 켤 비트, 상위 16비트 = 끌 비트). 이렇게 하면 PC8~PC15를 건드리지 않는다. N은 그대로 64이고 HT/TC 위치도 같다. 메모리 크기가 두 배가 된다는 점을 확인한다.

실험 F. 콜백을 빼 본다

두 콜백 등록 줄을 주석으로 막으면 처음 채운 패턴 0의 64샘플이 영원히 반복된다. 1초마다 pattern은 바뀌지만 아무도 버퍼를 다시 채우지 않기 때문이다. 이 구조는 ‘고정된 파형 테이블을 계속 내보내는’ 용도(사인 테이블 DAC 등)에서는 콜백 없이도 충분하다는 점을 보여 준다. HT/TC 카운트도 0으로 남는다.

실험 G. 샘플 속도 올리기

ARR을 49로 바꾸면(CubeMX Counter Period = 49) 20 kHz가 된다. 채우기 마감이 1.6 ms로 줄고 HT/TC 속도는 약 312/s가 된다. 실험 D에서 잰 채우기 시간과 비교해 여유가 얼마나 남는지 계산한다.

11. 확인 문제

먼저 스스로 답을 정해 본 뒤 펼쳐 확인한다.

문제 1. TIM2의 업데이트 주파수를 PCLK1 = 32 MHz에서 출발해 구하라. 왜 타이머 클럭이 32 MHz가 아닌가?

APB1 분주비가 2(≠1)이면 타이머 클럭은 PCLK1의 2배인 64 MHz이다. 업데이트 주파수 = 64 MHz ÷ 64 ÷ 100 = 10 kHz이다.

문제 2. HT와 TC가 각각 초당 몇 번 오는가? 인터럽트 간격은?

버퍼 한 바퀴 = 64 × 100 µs = 6.4 ms. HT, TC가 한 바퀴에 각각 한 번이므로 각각 1 ÷ 6.4 ms ≈ 156.25 /s이고, 두 종류가 번갈아 와서 인터럽트 간격은 3.2 ms이다.

문제 3. HT 콜백이 앞 절반을 채우는 이유는? 뒤 절반을 채우면 어떻게 되는가?

HT는 DMA가 앞 절반 32샘플을 다 보냈다는 신호이다. 이제 DMA는 뒤 절반을 읽으므로 앞 절반은 비어 있고 안전하게 고칠 수 있다. 뒤 절반을 채우면 DMA가 읽는 중인 곳을 고치게 되어 출력 값이 섞이고, 다음에 앞 절반으로 돌아왔을 때는 갱신되지 않은 옛 값이 나온다.

문제 4. HAL_TIM_Base_Start_DMA()를 쓰지 않은 이유는?

이 함수는 DMA 목적지를 TIMx->ARR로 고정하고 DMA 핸들의 완료·반 완료 콜백을 타이머 드라이버의 내부 함수로 덮어쓴다. GPIO 포트에 쓰려면 목적지를 &GPIOC->ODR로 직접 지정하고 콜백도 내 것을 써야 하므로 HAL_DMA_Start_IT()와 __HAL_TIM_ENABLE_DMA()를 따로 쓴다.

문제 5. RegisterCallback을 Start_IT 뒤에 호출하면 어떤 일이 생기는가? 두 가지를 들라.

(1) Start_IT 시점에 반 완료 콜백이 NULL이므로 CCR2.HTIE가 꺼진 채로 시작하여 HT 인터럽트가 오지 않는다(CCR2 = 0x25BB). (2) 원형 DMA는 시작 후 상태가 READY가 아니므로 이후의 등록은 HAL_ERROR를 반환하며 실패한다.

문제 6. 채우기 마감은 몇 ms인가? ARR을 49로 바꾸면?

반 버퍼 32샘플 × 100 µs = 3.2 ms. ARR = 49이면 샘플 간격 50 µs(20 kHz)이므로 32 × 50 µs = 1.6 ms이다.

문제 7. 8비트 값 v = 0xA3을 BSRR로 출력하려면 버퍼 원소 값은? 이때 PSIZE/MSIZE는?

v | ((~v & 0xFF) << 16) = 0x000000A3 | (0x5C << 16) = 0x005C00A3이다. 32비트 원소이므로 PSIZE = MSIZE = 32비트여야 한다. 반워드로 쓰면 APB 브리지가 데이터를 복제해 같은 비트에 set과 reset이 동시에 걸린다.

문제 8. 이 예제에서 PC13(B1)에 아무 영향이 없는 이유와, PC8~PC15를 풀업 입력으로 쓰고 있다면 생기는 문제는?

PC13은 이 프로젝트에서 따로 설정되지 않아 리셋 상태인 부동 입력이고, 부동 입력은 ODR 비트를 쓰지 않는다. 입력 풀업/풀다운 모드에서는 ODR 비트가 풀업(1)/풀다운(0) 선택이므로, 풀업 입력인 핀에 0이 쓰이면 풀다운으로 바뀐다.

문제 9. 1초마다 출력되는 줄의 HT, TC는 그 1초 동안의 횟수인가?

아니다. half_count, full_count는 부팅 이후 누적 횟수이며 초기화하지 않는다. 그래서 줄마다 약 156씩 늘어난다. 또 출력되는 패턴 이름은 방금 바뀐 새 패턴이다.
