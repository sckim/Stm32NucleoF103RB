bxCAN: 주소 없는 버스에서 ID가 우선순위가 되기까지

CAN(Controller Area Network, 제어기 영역 네트워크)은 여러 제어기가 선 한 쌍을 함께 쓰며 메시지를 방송하는 직렬 버스이다. STM32F103RB의 bxCAN(Basic Extended CAN)은 디지털논리에서 배운 와이어드 AND 버스, 비트 단위 비교기, 분주기와 시간 양자(tq) 카운터, 레지스터 묶음(메일박스)과 우선순위 선택기, 3칸 FIFO(First-In First-Out, 선입선출 버퍼), 마스크 비교기, 문턱값 비교기가 달린 오류 카운터를 묶어 이 일을 하드웨어로 처리한다. 이 개념설명은 CPU가 송신 메일박스에 넣은 메시지가 CAN_TX 핀의 비트열이 되고, CAN_RX 핀으로 들어온 비트열이 필터를 지나 수신 FIFO에 쌓이기까지의 경로를 원본 블록도 위에서 따라간다.

1. 문제 정의: bxCAN이 없으면 CPU가 무엇을 직접 해야 하는가

자동차나 공장 설비에는 제어기가 수십 개 있다. 이들을 일대일로 다 잇는 대신 선 한 쌍을 함께 쓰게 하려면 세 가지가 필요하다. 첫째, 누구나 아무 때나 말을 걸 수 있어야 한다(마스터가 따로 없음). 둘째, 둘 이상이 동시에 말을 시작해도 중요한 메시지가 깨지지 않고 먼저 나가야 한다. 셋째, 고장 난 한 노드가 버스 전체를 망가뜨리지 못해야 한다. CAN 제어기가 없다면 CPU가 GPIO 핀 하나로 이 모든 것을 비트 단위로 처리해야 한다.

2. 일반 개념

노드, 제어기, 트랜시버

그림에서 보듯 MCU는 버스에 직접 붙지 않는다. 칩의 CAN_TX 핀은 트랜시버에 "이번 비트를 무엇으로 낼지"를 알려 주고, CAN_RX 핀은 트랜시버가 읽은 버스 상태를 돌려받는다. 송신 중에도 CAN_RX로 버스를 계속 읽는다는 점이 중요하다. 내가 낸 비트와 버스에 실제로 나타난 비트를 비교할 수 있어야 중재와 오류 검출이 된다.

우성과 열성: 선 하나가 AND 게이트가 된다

CAN 버스의 두 상태는 우성(dominant)과 열성(recessive)이다. 누군가 우성을 내면 버스는 우성이 되고, 모두가 열성일 때만 열성이 된다. 우성 = 0, 열성 = 1로 놓으면 버스 값은 모든 노드 출력의 AND이다. I2C의 오픈드레인 선과 같은 와이어드 AND이다(04_I2C 2장).

RM0008도 이 대응을 쓴다. 필터 레지스터 비트 설명은 "0: Dominant bit is expected, 1: Recessive bit is expected"이고(p.694), 초기화 모드에서 "the status of the CAN bus output CANTX is recessive (high)"라고 적는다(p.657). 즉 칩의 CAN_TX 핀에서 0(Low)이 우성, 1(High)이 열성이다.

ID가 곧 우선순위: 깨지지 않는 중재

CAN 메시지에는 받는 노드의 주소가 없다. 대신 내용을 나타내는 ID가 있고 모든 노드가 모든 메시지를 듣는다. RM0008 24.7.4는 "the identifier of a message is not associated with the address of a node but related to the content of the message"라고 적는다(p.664).

둘 이상이 동시에 SOF(Start Of Frame)를 내면 ID를 최상위 비트부터 한 비트씩 낸다(비트 순서는 일반 개념이며 Figure 235의 필드 순서와 맞는다). 서로 같은 비트를 내는 동안은 아무 일도 없다. 처음으로 다른 비트에서 1(열성)을 낸 쪽은 버스에서 0을 보고 송신을 멈추고 수신자로 바뀐다(일반 개념. RM0008은 결과만 ALST로 보여 준다). 0을 낸 쪽은 아무것도 모른 채 계속 보낸다. 그래서 ID 값이 작을수록 이긴다. 이긴 메시지는 한 비트도 손상되지 않았으므로 다시 보낼 필요가 없다. RM0008은 송신 우선순위를 설명하며 "The message with the lowest identifier value has the highest priority according to the arbitration of the CAN protocol"이라고 적는다(p.661). 진 쪽은 버스가 다시 비면 자동으로 재도전한다(5장 NART). 두 노드의 중재는 7장 시나리오 ②에서 직접 실험한다.

프레임의 모양

그림에서 SOF는 우성 1비트이고 EOF는 열성 7비트이다. ACK 필드(2비트) 안의 ACK 슬롯은 수신자들이 채운다. 송신자는 이 자리에 열성을 내고, 프레임을 올바르게 받은 노드가 하나라도 있으면 우성으로 덮어쓴다(일반 개념). RM0008은 침묵 모드를 설명하며 bxCAN이 보내야 하는 우성 비트로 "ACK bit, overload flag, active error flag"를 들고, 루프백 모드에서는 "no dominant bit sampled in the acknowledge slot"인 승인 오류를 무시한다고 적는다(p.658~659). 버스에 나 혼자뿐이면 ACK가 오지 않아 송신이 계속 실패한다는 뜻이다(Q10).

오류 감시와 고장 격리

모든 노드는 송신 오류 카운터 TEC(Transmit Error Counter)와 수신 오류 카운터 REC(Receive Error Counter)를 가진다. 오류가 나면 크게 늘고 성공하면 조금 준다. 카운터가 커지면 노드는 스스로 목소리를 낮춘다(오류 능동 → 오류 수동). TEC가 255를 넘으면 버스에서 아예 빠진다(버스 오프). 이렇게 하면 고장 난 노드가 오류 프레임을 계속 내서 버스를 마비시키는 일을 막는다. F103에서의 문턱값과 복귀 조건은 6장 ③에서 RM0008 그림으로 본다.

일반 개념 (네 문서에는 없거나 일부만 있는 CAN 상식)
  • 차동 전압과 종단: 트랜시버는 우성일 때 CANH와 CANL 사이에 전압차를 만들고, 열성일 때는 두 선을 같은 전위로 놓아 둔다. 버스 양 끝에는 종단 저항을 둔다. 실제 버스에 연결하려면 칩 밖에 CAN 트랜시버가 반드시 필요하다. 전압값과 저항값은 이 네 문서에 없다.
  • 비트 스터핑: 같은 값이 5비트 이어지면 송신자가 반대 값 1비트를 끼워 넣고 수신자가 빼낸다. 재동기용 엣지를 보장하기 위해서이다. RM0008에는 규칙이 없고, LEC의 "Stuff Error" 코드로만 존재가 드러난다(p.682). Figure 235의 비트 수는 스터핑 비트를 뺀 값이다.
  • CRC: CRC 필드 16비트는 15비트 CRC와 구분자 1비트이다. 다항식은 RM0008에 없다.
  • 재동기 엣지 방향: 일반적인 CAN 설명에서는 열성→우성 엣지로 박자를 다시 맞춘다. RM0008 24.7.7은 유효 엣지를 "from dominant to recessive bus level"로 적어 방향이 반대이다(4장). 이 개념설명은 문서 문장을 그대로 옮기되, 방향 차이는 확인되지 않은 문서 오류 후보로 남긴다.

3. 내부 구현 블록도

F103에서 bxCAN 블록이 칩 안 어디에 있는지는 DS5319 Figure 1(p.11)에서 확인할 수 있다. APB1 버스에 bxCAN과 USB 2.0 FS가 나란히 있고, 그 사이에 "SRAM 512B"가 있으며, 핀 이름이 USBDP/CAN_TX, USBDM/CAN_RX로 함께 적혀 있다. 이 공유가 8장의 가장 큰 제약이 된다.

4. 클럭 경로와 시간 계산

CAN에는 클럭 선이 없다. 모든 노드가 같은 비트 시간을 약속하고, 각자 자기 클럭으로 그 시간을 잰다. bxCAN은 APB1 클럭을 BRP로 나누어 시간 양자 tq를 만들고, 한 비트를 tq 몇 개로 쪼개 세 구간으로 나눈다.

tq = (BRP[9:0] + 1) × t_PCLK t_PCLK = APB1 클럭 주기 t_BS1 = tq × (TS1[3:0] + 1) 1 ~ 16 tq t_BS2 = tq × (TS2[2:0] + 1) 1 ~ 8 tq 비트 시간 = 1 × tq + t_BS1 + t_BS2 → 3 ~ 25 tq 보레이트 = 1 / 비트 시간 (RM0008 Figure 234, p.671; CAN_BTR p.683~684) 샘플 지점 = (1 + TS1 + 1) / (1 + TS1 + 1 + TS2 + 1) ← Figure 234의 구간 위치에서 유도 등가 모델

레지스터에 쓰는 값(필드)과 실제 tq 수는 1씩 다르다. 예제들은 "Prescaler 4, BS1 13 tq, BS2 2 tq"처럼 tq 수로 말하는데, 이는 필드 BRP = 3, TS1 = 12, TS2 = 1이다. BTR은 초기화 모드에서만 쓸 수 있다(p.683). RM0008 24.7.7 본문은 같은 내용을 "only possible while the device is in Standby mode"라고 적는데, 24.9.1과 CAN_BTR 설명이 모두 initialization mode라고 하므로 Standby는 표기 오류로 보인다(p.671, p.674).

5. 제어 요소의 역할: 블록도의 스위치와 레지스터 비트

① 동작 모드 상태기계: 슬립 · 초기화 · 정상

  • 리셋 → Sleep: MCR의 SLEEP 비트가 리셋값 1이다. 이때 CANTX에는 내부 풀업이 켜져 있다(24.4, p.656). MSR 리셋값 0x0000 0C02는 SLAK = 1을 뜻한다(p.676).
  • Sleep → Initialization: 조건이 SLEEP̄ · INRQ · ACK이다. 그래서 INRQ = 1만 쓰고 SLEEP을 지우지 않으면 초기화 모드에 들어가지 않는다. 24.4.3은 "it must also clear the SLEEP bit"라고 적는다(p.657). 들어가면 INAK = 1로 확인된다.
  • Initialization → Normal: INRQ를 지우면 버스에서 열성 11비트를 본 뒤(SYNC) INAK가 0이 된다. 버스가 계속 바쁘면 정상 모드 진입이 늦어진다.
  • 왜 요청·확인 두 단계인가: 모드 전환은 지금 진행 중인 프레임이 끝나야 일어난다("waits until the current CAN activity ... is completed", p.676). 소프트웨어는 요청 비트를 쓰고, 하드웨어가 안전한 순간에 전환한 뒤 확인 비트로 알린다. 요청 플립플롭과 확인 플립플롭을 따로 둔 핸드셰이크이며, 소프트웨어는 확인 비트를 본 뒤에야 다음 단계로 넘어가야 한다.

② 시험 모드: 루프백과 침묵

세 그림은 두 개의 2:1 선택기로 읽을 수 있다. 하나는 코어 Rx 입력을 "핀 / 내부 Tx" 중에서 고르고(LBKM), 다른 하나는 CANTX 핀을 "코어 Tx / 상수 1" 중에서 고른다(SILM). 루프백에서는 승인 오류를 무시하므로 상대 노드 없이도 송신이 성공한다(24.5.2). 이 비트들은 BTR에 있어 초기화 모드에서만 바꿀 수 있다(24.5, p.658).

② DMA 요청은 없다

RM0008 24장에는 DMA(Direct Memory Access, 직접 메모리 접근) 요청에 관한 비트나 설명이 없고, DMA1 요청 표(Table 78, p.282)에도 CAN이 없다. 문서상 bxCAN의 메일박스는 CPU가 읽고 쓴다. 대신 하드웨어 FIFO 3칸과 필터가 CPU가 깨어나야 하는 횟수를 줄인다. RM0008 24.3은 "A receive FIFO scheme allows the CPU to be dedicated to application tasks for a long time period without losing messages"라고 적는다(p.654).

9. 이해 확인 문제

Q1. PCLK1 = 32 MHz에서 250 kbit/s, 비트당 16 tq, 샘플 지점 87.5 %로 맞추려면 BRP·TS1·TS2 필드는? SJW = 1 tq일 때 BTR 값은?

비트 시간 4 µs ÷ 16 = tq 250 ns이므로 32 MHz를 8로 나눈다. BRP = 7이다. 샘플 지점 87.5 % = 14/16이므로 1 + BS1 = 14 → BS1 = 13 tq(TS1 = 12), BS2 = 2 tq(TS2 = 1)이다. BTR = (SJW 0 << 24) | (1 << 20) | (12 << 16) | 7 = 0x001C 0007이다. 4장 계산기로 확인할 수 있다.

Q2. BTR 리셋값은 0x0123 0000이다. 리셋 직후 클럭(PCLK1 = 8 MHz)이라면 보레이트와 샘플 지점은?

필드를 풀면 SJW = 1(2 tq), TS2 = 2(3 tq), TS1 = 3(4 tq), BRP = 0(÷1)이다. tq = 125 ns, 비트 = 1 + 4 + 3 = 8 tq = 1 µs이므로 1 Mbit/s이고, 샘플 지점은 5/8 = 62.5 %이다(리셋값은 p.683). 리셋값을 그대로 쓰지 않고 반드시 설정하는 이유이다.

Q3. 노드 A는 ID 0x6A0, 노드 B는 ID 0x6A4 데이터 프레임을 동시에 보낸다. 누가 이기고, 진 쪽은 몇 번째 ID 비트에서 물러나는가?

0x6A0 = 110 1010 0000, 0x6A4 = 110 1010 0100이다. ID10부터 ID3까지 같고, ID2에서 A는 0(우성), B는 1(열성)을 낸다. B는 ID2에서 버스 0을 보고 물러난다. 값이 작은 A가 이긴다. B의 메일박스에는 ALST가 서고 NART = 0이면 버스가 빈 뒤 다시 시도한다. 7장 중재 실험에 넣어 확인할 수 있다.

Q4. 같은 ID 0x123으로 노드 A는 데이터 프레임, 노드 B는 원격 프레임을 동시에 보낸다. 결과는?

ID 11비트가 모두 같으므로 중재는 RTR 비트까지 간다. 데이터 프레임은 RTR = 0(우성), 원격 프레임은 RTR = 1(열성)이므로 데이터 프레임이 이긴다. B는 원하던 데이터를 바로 그 프레임으로 받게 된다.

Q5. 500 kbit/s에서 표준 ID, DLC 8 데이터 프레임 하나는 몇 µs인가? 버스에 이 프레임만 계속 흐른다면 초당 최대 몇 개인가?

44 + 8 × 8 = 108비트 × 2 µs = 216 µs이고, 간헐 3비트를 더하면 111비트 = 222 µs이다. 1 / 222 µs ≈ 4 500개/초이다. 스터핑 비트를 빼고 계산했으므로 실제로는 이보다 조금 적다.

Q6. FIFO 0에 메시지 M1~M5가 연달아 오는 동안 CPU가 한 번도 RFOM을 쓰지 못했다. RFLM = 0과 RFLM = 1일 때 FIFO에 남는 것은?

세 칸이 M1, M2, M3로 찬 뒤 넘침이 두 번 일어난다. RFLM = 0이면 마지막 저장 메시지가 매번 덮어써지므로 M1, M2, M5가 남는다. RFLM = 1이면 새 메시지를 버리므로 M1, M2, M3가 남는다. 두 경우 모두 FOVR0 = 1이고, 몇 개를 잃었는지는 알 수 없다(p.664).

Q7. 32비트 마스크 필터에 표준 ID 0x300, 마스크 0x700을 넣고 IDE·RTR 마스크 비트는 0(무시)으로 두었다. 어떤 프레임이 통과하는가?

STID 상위 3비트가 011인 표준 프레임(0x300~0x3FF)은 데이터·원격 가리지 않고 통과한다. 그런데 IDE도 무시하므로, EXID[28:18](32비트 스케일에서 STID 자리)의 상위 3비트가 011인 확장 프레임도 통과한다. 표준 프레임만 원하면 IDE를 마스크에 넣어 0과 일치시켜야 한다. 위 필터 시험기에서 "둘 다 무시"로 바꾸고 확장 ID 0C000000을 넣어 확인할 수 있다.

Q8. 슬립 상태(리셋 직후)에서 INRQ = 1만 쓰고 INAK를 기다렸더니 끝없이 기다린다. 왜인가?

Figure 224에서 Sleep → Initialization 전이 조건은 SLEEP̄ · INRQ · ACK이다. 리셋 직후 SLEEP = 1이므로 SLEEP을 함께 지워야 한다(24.4.3). 그렇지 않으면 상태기계가 Sleep에 머물러 INAK가 서지 않는다.

Q9. ESR의 TEC 필드가 0xF0(240)으로 읽혔다. 이 노드의 상태는? 이어서 BOFF = 1이 되었는데 TEC 필드가 작은 값으로 보일 수 있는 이유는?

240 > 127이므로 오류 수동이고 EWGF·EPVF가 서 있다. TEC가 255를 넘으면 버스 오프이다. TEC는 9비트 카운터인데 ESR로는 하위 8비트만 보이므로(p.682), 256 이상이 되면 필드 값만으로는 상태를 판단할 수 없다. 상태는 BOFF·EPVF 플래그로 확인해야 한다.

Q10. 루프백에서 잘 되던 프로그램을 정상 모드로 바꾸고 트랜시버를 달아 버스에 노드 하나만 연결했다. 송신은 어떻게 되는가?

ACK 슬롯에 우성을 내 줄 수신자가 없으므로 승인 오류가 난다. LEC = 011(Acknowledgment Error)이 기록되고, NART = 0이면 하드웨어가 계속 재전송한다. 메일박스는 EMPTY로 돌아오지 않고 TEC가 늘어 EWGF·EPVF가 설 수 있다. 오류마다 TEC가 얼마씩 늘고 어디서 멈추는지는 CAN 표준의 규칙이며 RM0008에는 없다. 루프백은 ACK 오류를 무시했기 때문에 이 문제를 보여 주지 못했다(24.5.2).

Q11. FIFO 0 인터럽트 처리에서 출력 메일박스의 데이터를 다 읽었는데도 인터럽트가 계속 다시 걸린다. 원인은?

FIFO 0 인터럽트의 원천 FMP0 ≠ 00은 메시지 수를 나타내는 상태이고, 읽기로는 줄지 않는다. RFOM0 = 1을 써서 출력 메일박스를 놓아 줘야 FMP가 1 줄어든다(p.680). 메시지가 더 남아 있으면 그다음 메시지가 출력 메일박스에 나타나고 인터럽트가 다시 걸리는 것이 정상이다.

Q12. 같은 프로그램에서 USB 장치 기능과 CAN을 둘 다 쓰고 싶다. 무엇이 문제이고 어떻게 해야 하는가?

두 장치는 전용 SRAM 512 B를 공유해 동시에 쓸 수 없다. 핀(PA11/PA12)과 인터럽트 벡터 두 개도 겹친다. RM0008은 "can be used in the same application but not at the same time"이라고 하므로, 한쪽을 끄고 다른 쪽을 켜는 식으로 시간을 나눠 써야 한다. 핀 충돌은 CAN을 PB8/PB9로 리맵하면 피할 수 있지만 SRAM 공유는 피할 수 없다.

  • CAN 버스는 우성(0)이 이기는 와이어드 AND이다. 모든 노드가 송신 중에도 버스를 읽어 비교하므로, ID가 작은 메시지가 손상 없이 중재에서 이긴다.

  • tq = (BRP+1) / PCLK1, 비트 = (1 + TS1+1 + TS2+1) tq, 샘플 지점은 BS1 끝이다. 재동기는 BS1을 늘이거나 BS2를 줄이며 그 한도가 SJW이다.
  • 모드는 Sleep(리셋) → Initialization → Normal의 요청·확인 상태기계이고, BTR과 시험 모드는 초기화 모드에서만 바꾼다. FMP는 RFOM으로만 줄어든다.
  • 벡터 4개(USB와 2개 공유), DMA 없음, USB와 SRAM·핀 공유로 동시 사용 불가. 정오표: TTCM 미지원, PA12의 USART1_RTS 충돌.

근거 문서와 인용·표기 규칙, 등가 모델 표시의 뜻은 교안의 활용법에 있다. 문서의 숫자로 직접 유도한 계산에도 등가 모델 표시를 달았다. RM0008은 CAN 프로토콜 자체(비트 스터핑 규칙, CRC 다항식, 오류 카운터 증감 규칙 등)를 "CAN 표준(ISO 11898)을 보라"며 설명하지 않는다. 그래서 문서에 없는 CAN 일반 상식은 2장의 일반 개념 상자에만 최소한으로 적고 출처를 달지 않았다. 와이어드 AND 버스와 중재의 기본 발상은 04_I2C 개념설명 2장에서, NVIC와 클럭 게이트는 01_GPIO 개념설명에서 다뤘다.

  • RM0008 Rev 21(참조 매뉴얼): 24장 Controller area network (bxCAN)
  • DS5319 Rev 19(데이터시트): CAN 개요, 핀 정의, 메모리 맵
  • PM0056 Rev 7(Cortex-M3 프로그래밍 매뉴얼): NVIC(Nested Vectored Interrupt Controller, 중첩 벡터 인터럽트 컨트롤러)
  • ES096 Rev 15(정오표)
